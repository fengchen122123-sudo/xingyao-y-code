# 星瑶对话可操作性审计

- 审计日期：2026-10-19
- 审计对象：本仓库（Y-CODE / 星瑶）
- 审计目标：系统中所有用户可用功能，是否都能仅凭「与星瑶对话」完成；不能的逐条列出。
- 判定口径：
  - **直接可操作**：存在对应 Agent 工具，对话即可完成。
  - **间接可操作**：无专用工具，但可用 `execute_command` / 文件读写安全变通，存在副作用或需重启。
  - **无法操作**：无工具，且变通方式不安全、不可行或会绕过安全机制。
  - **设计上不应操作**：属于用户授权/安全边界，Agent 代劳反而违规，单列不计入缺口。

### C. 设计上不应由 Agent 操作（合理缺口，不建议补）

本节是本轮补齐后**仍然保留**的安全边界清单。补齐的 21 个工具不仅没有打开这些口子，还在实现里显式拒绝对应操作：

- **权限档位切换（confirm / accept_edits / plan / full）**：属用户侧授权模型。`system_settings` 对权限模式相关键直接返回「属于安全策略项，不提供工具修改或读取」；`computer_control` 也注明「不提供权限档位或信任类操作」。若 Agent 能自行提权，等于取消用户对工具执行的最终否决权。
- **沙箱开关、项目白名单增删**：白名单决定哪些命令可免确认执行，Agent 自行加白等同于绕过确认流程；`system_settings` 同一处显式拒绝。
- **Hook 信任、插件信任**：信任是对「本机将执行的命令/代码」的授权。`hook_manage` 只做 `list`/`save`/`delete`/`set_disabled`，`plugin_manage` 只做启停与设置，两者都**故意不实现** grant/deny/revoke/trust；未信任插件无法经工具启用，hook 由模型写入后仍需用户自行信任才会执行，工具只把 `trust` 状态原样透出。
- **免责声明确认**：合规交互，必须由本人阅读并确认，Agent 代劳无意义且破坏合规链。
- **窗口最小化/最大化/关闭、侧栏分组排序、消息导航等纯界面交互**：无安全含义也无自动化价值，属用户个人视图偏好；不做工具化，避免占用模型注意力与工具位。

补充边界（非授权类，但同样刻意未做）：

- **会话消息排队（`/queue`）**：涉及用户对「何时发送」的即时控制，暂不做工具。
- **附件拖拽上传**：本质是 GUI 交互事件，`clipboard_image` 只覆盖剪贴板图片这一条路径。
- **主题编辑实时预览**：`theme_manage` 可保存并生效，但逐键预览仍依赖前端交互。

## 四、补齐优先级建议

1. **P0（日常高频，最影响「万事找星瑶」体验）**
   - 会话管理工具组：`session_rename` / `session_delete` / `session_archive` / `session_clear_history` / `session_move_workdir`
   - 模型管理工具组：`model_list` / `model_add` / `model_update` / `model_delete` / `provider_*` / `model_test`（密钥只写不回显）
   - 技能与插件工具组：`skill_list/enable/disable/restore`、`plugin_list/enable/disable/settings`
2. **P1（运维与分析）**
   - `usage_stats`、`session_export`、`update_check/install`、`checkpoint_list/restore`、`undo_list/preview/recover`、`compress_session`
3. **P2（边界能力）**
   - 截图与剪贴板、主题、人设、飞书、局域网、JEV、PTY、浏览器面板控制
4. **不建议补**
   - 权限档位、沙箱、白名单、信任确认、免责声明：这些是用户侧安全边界，Agent 代劳会破坏授权模型。

**2026-10-19 晚执行结果**（对照上述四档）：

- P0 三组**全部落地**，但实现形态与建议不同：没有拆成 `session_rename` / `model_add` 等细粒度工具，而是收敛为按域聚合的 `session_manage` / `model_manage` / `skill_manage` / `plugin_manage` / `hook_manage`，用 `action` 参数分派——减少工具位占用，也让同类操作共享参数校验与权限声明。
- P1 **全部落地**：`usage_stats`、`session_export`、`update_manage`、`session_manage` 的 `checkpoint_list`/`checkpoint_restore`/`undo_list`/`undo_preview`/`undo_recover`/`compress`。
- P2 **除附件拖拽上传外全部落地**：`screenshot_capture`、`clipboard_image`、`theme_manage`、`persona_manage`、`feishu_manage`、`lan_manage`、`decision_manage`、`pty_manage`、`browser_pane`，另加 `computer_control`、`system_settings`、`diagram_manage`、`doctor_run`。
- 「不建议补」**原样保留**，见第三节 C 的边界理由。

## 五、补充说明

- 本审计以仓库内工具注册表（`core/tool_registry.py`，39 个内置工具）与 GUI 桥接方法（`gui_bridge.py` + 3 个 mixin，数百个方法）为基线；插件工具数量随用户安装情况变化。（2026-10-19 晚更新：该基线已过时，注册表新增 21 个管理类工具；本机加载插件后 `build_default_registry()` 实测条目数为 71。）
- `dispatch_task` 可在指定/新建会话中派发任务，`open_session` 可切换会话，因此「新建会话 + 派活」已覆盖；但会话的改名、删除、归档、历史清空没有出口。（2026-10-19 晚更新：这些出口已由 `session_manage` 补齐。）
- 电脑操控类工具（computer_action）是否可用取决于设置项与平台，属于条件可用能力；`computer_control` 只补运行控制（status/pause/resume/stop/browser），不改变该条件可用性。
- 工具化后仍需注意：`session_manage` 的 `delete`/`clear_history`、`model_manage` 的 `delete_provider`/`delete_model`、`theme_manage` 的 `delete` 等动作不可逆或影响后续对话，执行前应显式确认目标对象。
