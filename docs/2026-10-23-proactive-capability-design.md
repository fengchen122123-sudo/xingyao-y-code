# 星瑶主动式能力 设计

日期：2026-10-23　状态：设计稿，未实现

## 一、现状与三条核心结论

现有能力全部是「用户问才动」：

- **星轨自动化**（`core/automation/`）：触发器只有 `interval/daily/weekly/startup` 四种（`scheduling.py`），提示词由用户写死。`AutomationEngine` 是 daemon 线程（30s 轮询 + `notify_changed` 唤醒），只做「读钟 → CAS 认领 → 回调派发」，绝不判断"这事该不该做"。
- **无人值守档位**：任务级 `permission_mode ∈ {confirm, accept_edits, plan, full}`，但对话/工具内只能建 `confirm`、`accept_edits`。自动化回合派生的一切权限请求一律自动拒绝、`ask_user` 自动取消。
- **错过触发**：`missed_run_policy = skip | run_once`，只在引擎首轮按 60 秒宽限判定；单飞机制避免同一任务并发。
- **hook**：仅 `SessionStart / PreToolUse / PostToolUse / Stop` 四事件，同步阻塞、fail-open、由用户配置的 shell 命令产生，无持久化、无频率控制、无「发起回合」能力。

**结论一：触发源新增、执行链复用。** 新增 `core/proactive/`（采集器 + 判定 + ticker 线程），投递复用 `_dispatch_automation_run` 的「锁内判忙 → 排队或起内部回合」，权限刹车直接继承现有的无人值守自动拒绝；不复用自动化任务表——触发器不该由用户写死。

**结论二：默认只记录。** 未经用户显式启用的主动行为一律 `record`；打扰要过三道闸（频率上限 / 在场与空闲 / opt-in），宁可漏提醒不可多打扰。

**结论三：hook 不当触发源，只当注入通道。** 唯一复用点是「回合准备的上下文注入」——把待办摘要塞进已存在的回合，而不是用 hook 去发起回合。

## 二、事项来源分类

| 源 | 判据（纯本地、可复算） | 默认档位 |
|---|---|---|
| 项目状态过期 | `projects/*.md` 的 `updated_at` 距今 >7 天且有未完成 `next_step` | record（>30 天仅标注） |
| 计划项长期阻塞 | `plan` 中 `status ∈ {pending, blocked}` 且 `updated_at` >24h | ask（一次性，不重复） |
| 任务失败待处理 | `task_manager` 的 `failed/timed_out`，或自动化 `run.status = error` | ask（一次） |
| 定时巡检 | 端口/磁盘/依赖/测试红、会话与缓存健康 | record；仅阈值越界才 ask |
| 外部事件 | 用户显式订阅的源（git 远端新提交、CI 结果、订阅新闻） | 订阅才采，未订阅不采 |

采集层是只读纯函数：不调 LLM、不写文件、不联网（外部源除外且需订阅）。判定层优先用本地规则，必要时交给一次只读小回合判断，结果落 `proactive_items` 持久化。

## 三、触发时机与频率上限

时机（全部是既有可挂点）：① 应用启动时在 `start_automation_engine()` 之后启动 ticker（daemon，与引擎同构，stop 时先停）；② 每 30 分钟一次 tick；③ 回合结束后的空闲窗口（用户在场、上下文新鲜，是投递的最佳窗口）；④ 会话首个回合准备阶段做一次轻量扫描（不打扰）。

频率上限（本地持久化计数，模型无权修改）：打扰窗口 09:00–22:00；单日打扰 ≤2 次；同类事项去重 24h；全局最小打扰间隔 4h；同一事项重复出现只更新计数不重复提醒。所有上限是硬编码常量。

## 四、打扰边界

- **只记录**：低置信、非阻塞、纯状态过期、外部事件未证实、用户近 24h 内拒绝过同类、用户近期在忙或在窗口外。
- **必须问**：任何不可逆动作（删除/覆盖/提交/推送/外发）、改动其他项目配置、花钱或代表用户对外发言、需要权限档位升级、偏好不明。ask 一律落成待办卡片 + notice，绝不阻塞回合。
- **可以直接做**：只读巡检、生成草稿/报告/摘要、跑测试与 lint、在用户本会话已明确授权范围内的同型操作、写自己的记忆与待办。

## 五、与自动化任务、hook 的关系

| 维度 | 决定 |
|---|---|
| 复用 | 内判忙/排队语义；运行状态机与单飞；无人值守权限自动拒绝；notice 事件通道；回合准备的上下文注入 |
| 新增 | `core/proactive/`（collectors / evaluator / ticker）、`proactive_items` 表（含档位、计数、`last_ask_at`）、`internal_kind="proactive"` 的内部回合 |
| 不复用 | 自动化任务表与四种触发器（用户写死 → 系统自主发现的语义冲突）；hook 作为触发源 |
| 边界 | 自动化任务 = 用户说「几点做什么」；主动式 = 系统说「有件事值得你看一眼」。共享执行与刹车，不共享触发 |

## 六、权限与安全

- 主动回合固定 `permission_mode = confirm`，不可由模型自选、不可升级到 `accept_edits/plan/full`。这让「需要确认的动作一律被拒」成为天然刹车：星瑶在无人干预时只能读取与起草。
- 绝不能做：删除/覆盖用户文件与仓库；`git push/reset/rebase`；对外发消息（邮件/飞书/公众号）；改配置、密钥、权限档位；增删改自动化任务；代表用户回复他人；绕过 permission broker；自行延长频率上限或关闭自身审计；递归给自己派新的主动事项。
- 每次主动动作写审计行（源、判据、档位、结果），用户可追溯、可一键关闭整层。

## 七、失败与降级

采集异常 → 跳过该源并记日志，其余源照常；tick 异常 → 本轮跳过；投递失败 → 事项退回 `pending`，最多重试 3 次后置 `abandoned`；数据源缺失 → 该源空跑不报错；应用未运行错过 tick → 按 `skip` 语义（主动事项过期不补打扰）；单飞命中 → 不重复投递；全部失败 → 静默，绝不弹错误框。

## 八、非目标

不做后台端到端替用户干活；不做跨设备/离线推送；不新增第 5 个 hook 事件；不自动创建或修改自动化任务；不做模型自由决定的唤醒频率；不引入「主动→派活→再主动」的递归循环；不对用户做静默的破坏性操作；不替代项目状态记忆与断点续跑。
