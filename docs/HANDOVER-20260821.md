## 一、项目概览（我对项目的理解）

Y-CODE（星瑶）是自研的 Windows 桌面 AI 编码助手，同一套后端同时提供 CLI（TUI）与 GUI 两种形态。

**技术栈与结构：**

| 层 | 技术 | 说明 |
|---|---|---|
| 后端 | Python 3.14 + litellm | LLM 统一调用层，支持 OpenAI / Anthropic 双协议、多厂商（DeepSeek、Kimi、阶跃星辰、基元律动等） |
| GUI 壳 | pywebview 6.2.1 + WebView2 | `gui_main.py`（入口/看门狗）+ `gui_bridge.py`（前后端桥，约 100+ API 方法） |
| 前端 | Vue 3 + TS + Vite + Pinia | `frontend/src/`，组件 + stores（appStore 为核心）+ utils，测试用 vitest |
| 持久化 | SQLite | **TUI 用 `~/.ycode/ycode.db`，GUI 用 `~/.ycode/ycode_gui.db`（两个独立的库！）** |
| 打包 | PyInstaller | `build_release.py` 5 步流水线：前端构建 → 双主程序编译 → 载荷压缩 → 卸载程序 → 两个安装向导，产物在 `dist/` |

**核心架构（core/）：**

- `harness/`：非插件化的固定主代理内核。`journal.py` 管理 Turn/Step 生命周期与事件序列（**只存状态/ID/哈希，严禁存正文**），`runtime.py` 协调一次 Turn，`tool_pipeline.py` 负责工具解析与有序执行（含 RepeatCallGuard 重复调用抑制）。
- `agent_service.py`：上下文维护中枢，四级水位线（0.60 snip / 0.80 elide / 0.95 LLM 摘要）；`build_stable_system_message` 构建跨轮不变的稳定前缀（约 6.5K token，撑满 DeepSeek 2048 倍数缓存块）。
- `memory.py` / `memory_compressor.py`：消息存储（messages 表是唯一事实源）与分段记忆压缩。
- 多会话并行 + 会话级隔离：TLS 绑定 workdir / 模型 / 计划 / 沙盒状态；文件与命令操作一律用线程级 workdir，不用进程 cwd。
- 插件体系（`plugin_loader.py` + `~/.ycode/plugins/`，指纹信任机制）与 MCP（command 白名单 + env 加密）。

**项目铁律（摘自 AGENTS.md，交接必守）：**

1. 修改请求构造、消息规范化、system prompt、tools、缓存亲和逻辑前，必须先跑 Provider 请求 byte-golden 与 prompt byte-stability 回归；黄金字节不得为迁就实现改写。
2. 请求路径绝不改写历史中间字节；任何历史改写必须一次性、幂等、DB 层完成。
3. GUI 侧 `evaluate_js` 只允许在 `gui_bridge.py` 的 gui-js-dispatcher 单消费者线程调用；后台线程只向队列 put_nowait。
4. 用户主动取消后，cancelled 任务绝不注入"接手完成"指令。
5. 日常提交只在 dev 分支；合并其他分支须用户明确要求。
6. 前端统一使用 FoldCard 折叠体系与 lucide 风格 SVG 图标（不用 Unicode 字符图标）；CLI 输出不用 Markdown 粗体/斜体。

## 二、对话 A：启动卡死排查与 1.2.5 功能批次

> session 97「为什么我启动的时候经常遇」，2026-08-19 15:52 ~ 08-20 15:41，约 1047 条消息，是近期信息量最大的对话。

### 1. 启动页永久卡死修复（核心成果）

- **现象**：GUI 启动后停在 Y-CODE 图标加载页永久转圈，9 分钟内重启 5 次，其中 2 次卡死（日志只有"日志初始化 + 插件加载"后一片空白）。
- **根因**（代码层面坐实）：pywebview 的桥注入分两步——先注入 `api.js`（此时 `window.pywebview.api` 只是空对象 `{}`），再注入 `finish.js` 才填充方法并触发 `pywebviewready`。而 `App.vue` 用 `window.pywebview && window.pywebview.api` 判断就绪，空对象为 truthy → 前端抢跑调用 `get_initial_state` → 桥通道未通、消息丢失 → Promise 永不 settle → `finally` 里的 `finishSplash()` 永不执行 → 永久转圈。
- **修复**：
  - `frontend/src/App.vue`：新增 `pywebviewApiReady()`——`get_initial_state` 是函数才算就绪；`onMounted` 与兜底轮询全部改用它。
  - `gui_main.py`：`_register_bridge_watchdog()` 探测条件同步为方法级；`webview.start()` 前后加日志。
  - `gui_bridge.py`：`get_initial_state` 入口加诊断日志（可一锤定音区分"前端没调进来"还是"调进来卡在入口"）。
- **注意**：用户明确要求"从源头修，不能靠超时报错"（安装包用户遇到超时报错无法接受），最终方案是消除竞态而非加超时。
- 恶性循环诱因：关窗口只是隐藏到托盘，残留 `msedgewebview2.exe` 抢用户数据目录。
- 提交：`397b31b`（含之前工作区的消息流回合分组渲染 TurnGroup 等，共 54 文件）。

### 2. 预置模型目录（core/model_catalog.py）

- 新增「阶跃星辰（Anthropic格式）」厂商（id `stepfun-anthropic`）：base_url `https://api.stepfun.com/step_plan`（无 `/v1`），anthropic 协议，模型 step-3.7-flash（256k，视觉）/ step-router-v1（256k）/ step-explore（100 万）。

- `Sidebar.vue` 文件夹图标加 `@click.stop` + hover 高亮。

### 4. 「文件更改」折叠面板（1.2.5 亮点功能，纯前端）

- **需求演进**：① 回合底部显示可折叠的"N 个文件已更改 +X −Y"面板 → ② 点击文件行展开红删/绿增 diff（改动 ±5 行上下文、真实行号）→ ③ （持久化，后被放弃，见下）。
- **实现**：
  - `frontend/src/utils/turnGroups.ts`：`countDiffChanges()`（与后端 `_count_diff_changes` 同口径）+ `collectFileChanges()`（按路径去重、行数累加，兼容 mutation 绑定 diff 与 legacy diff）。
  - `frontend/src/utils/diffView.ts`：解析标准 unified diff 的 `@@ -old,+new @@` hunk 头取真实行号，裁剪到改动 ±5 行，中间裁剪用 `⋯` 占位。
  - `frontend/src/components/ChangedFilesPanel.vue`：折叠面板组件（新建）。
  - `TurnGroup.vue`：回合结束（`!group.running`）且有改动时渲染。
- **数据源**：实时 `diff_ready` 事件（后端 `generate_diff` 产出的标准 unified diff），**无需改后端**。
- **已知局限**：+N/−N 是从 diff 展示文本启发式统计；单文件 diff 超 25 行被后端 `_show_file_diff` 截断（只显示前 25 行 + 省略提示）。

### 5. diff 持久化：完整实现后又按用户要求整体移除（重要决策）

- 曾完整实现"方案 A"：`session_diffs` 表（schema 迁移）+ `add/get/clear_session_diffs` 三方法 + `_show_file_diff` 落库 + `get_history` 恢复时挂回 `legacy_diffs` + `gui_bridge._load_session_messages` 透传，全量测试 1124 通过，功能闭环验证成功。
- **但排查"重启后看不到面板"期间，AI 查错了数据库（查 TUI 的 ycode.db，实际 GUI 数据在 ycode_gui.db），误判"没落库"，让用户反复重启、还两次误杀用户正在用的进程（见下方教训），用户最终失去耐心，明确决定：放弃持久化，只保留实时显示。**
- 移除内容：`session_diffs` 表与三个方法、`get_history` 恢复块、`_show_file_diff` 落库块、`legacy_diffs` 透传、持久化测试与 CHANGELOG 条目。前端实时显示逻辑（ChangedFilesPanel 等）全部保留。
- **若将来要恢复持久化**：方案 A 的完整实现曾在 git 历史中存在（约在 `0baeb9d` 之前的提交里），可直接找回。

### 6. 上下文压缩三个 bug 修复（gui_bridge.py + agent_service.py）

- **Bug 1 压缩后红圈不更新**：发消息时压缩发生在 `prepare_turn_messages`，压缩后无 token_usage 推送 → 修复为压缩后立即 recalc + emit。
- **Bug 2 大窗口切小窗口超限报错**：`set_model` 只重算显示值不压缩历史；且压缩基线优先用"上一轮真实 API 用量"（100 万窗口留下的约 60 万 token，对 256k 是过期高值）→ 修复：`set_model` 后若占用超新窗口阈值（0.95）立即压缩（新增 `_ensure_fits_active_window`）；`get_session_token_baseline` 基线改为**真实用量与本地估算取较小值**。
- 相应更新了 test_agent_service.py 中 3 个锁定旧行为的测试并新增"取小"场景测试。

### 7. 记忆压缩超限崩溃修复（memory_compressor.py）

- **用户反馈**：`ContextWindowExceededError: input (887727 tokens) > context length (262144)`。
- **根因**：超长消息按「2 字符 = 1 token」截断（`cut_chars = chunk_token_budget * 2`），中文实际 1 字符 ≈ 1~1.5 token，31.4 万字符的中文实际 31~47 万 token，撑爆 26 万窗口。
- **修复**：截断改为按 token 数二分查找最大前缀；分段预算从 0.6 降到 0.4（26 万窗口下每段 15.7 万 → 10.5 万）；新增中文截断回归测试。

### 8. 「提示」卡片空行修复（gui_bridge.py）

- 根因：`_strip_ansi_markup` 只剥颜色标签不去换行，压缩提示原文 `\n<ansigray>🧠...` 剥后开头留 `\n`，前端 `pre-wrap` 渲染成空行。修复：剥标签后 `.strip()`。

### 9. 本对话的两个重大教训（已沉淀长期记忆，交接必读）

1. **数据库边界**：GUI 数据在 `~/.ycode/ycode_gui.db`，TUI 在 `~/.ycode/ycode.db`。排查 GUI 问题查错库会得出完全错误的结论。教训已写入 `~/.ycode/memory/ycode-gui-db-boundary.md`。
2. **进程操作**：两次把用户当前对话所在的 venv GUI 进程当成"旧进程"杀掉（PID 27496、1340）。用户环境常同时跑两个 `gui_main.py`（venv + 系统 Python），且桌面快捷方式 `Y-code.lnk` 指向 `D:\app\Ycode\Y-code.exe`（1.2.4 安装版旧代码）——"用户看到的功能不生效"很多时候是**用户在用安装版旧代码**，而非源码 bug。动进程前必须先列 PID 让用户确认。

## 三、对话 B：会话级模型绑定

> session 99「我在新会话，更换模型之后」，2026-08-20 16:26 ~ 17:31。

### 需求

1. 新会话页切换模型时页面跳转（从空状态页跳到对话流页）——要求不跳转。
2. 模型与对话绑定：A 会话用 deepseek，新建 B 会话换 kimi 后，回到 A 会话时 A 也变成 kimi 了——要求 B 换模型不影响 A；新建会话默认沿用当前会话在用的模型。

### 根因分析

- **跳转**：前端 `appStore.setModel` 调 `notifyChat('已切换活动模型')` 往 messages push 一条 notice，`messages.length` 从 0 变 1，空状态页 `KimiEmptyState`（显示条件 `messages.length === 0`）消失。
- **污染**：后端 `gui_bridge.set_model` 其实**已有**会话级绑定（`set_session_model_id` 落库，`switch_session` 恢复），问题在前端 `activeModelId/activeModelName` 是全局单值，未随会话 runtime 保存/恢复；pending 新会话（未落库）切模型会写到上一个会话。

### 修复（纯前端）

| 文件 | 改动 |
|---|---|
| `frontend/src/stores/sessionRuntime.ts` | `SessionRuntimeState` 新增 `modelId/modelName`，每个会话（含 pending 草稿）独立记录 |
| `frontend/src/stores/appStore.ts` | `_captureRuntime` 存模型入会话 runtime；`_bindSessionRuntime` 切会话即时恢复；`setModel` 仅当已有真实对话内容（user/assistant 消息）时才插入提示 |
| `frontend/src/stores/appStore.modelSession.test.ts` | 新增 6 个测试（先红后绿） |

## 六、遗留事项与建议

1. **diff 持久化已移除但未完全清理**：`ycode_gui.db` 里的 `session_diffs` 表和旧数据还在（代码不再读写）。若确认不要持久化，可择机清理表；若将来恢复，git 历史里有完整实现。
2. **双进程问题未根治**：用户机器上经常同时存在 venv 与系统 Python 两个 `gui_main.py` 进程，单实例互斥锁似乎未完全挡住。值得排查为什么系统 Python 的实例会被拉起（疑似与安装版/源码版共存有关）。
3. **安装版与源码版并用是排查干扰源**：用户桌面快捷方式指向 `D:\app\Ycode\Y-code.exe`，改动源码后用户"重启"的可能是安装版。今后遇到"改了没生效"，先确认用户跑的是哪个版本（查进程 ExecutablePath），再查数据库（GUI 用 ycode_gui.db）。
4. **单文件 diff 25 行截断**：`_show_file_diff` 的展示截断上限还在，超大改动在面板里只能看到前 25 行，如需完整 diff 需提高上限或传完整文本。
5. **预置目录改动的同步局限**：改 `model_catalog.py` 不会同步到已添加过该厂商的用户 config.json，发布说明里应提示"删除厂商重新添加"。
6. **启动卡死修复的观察期**：源头竞态已消除，但 WebView2 残留进程诱因仍在。若用户再报启动卡死，第一步看 `~/.ycode/logs/gui-runtime.log` 的启动节点日志（`get_initial_state` 入口 / `webview.start()` 前后），可直接定位卡在哪一层。
