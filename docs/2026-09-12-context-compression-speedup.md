# 上下文压缩提速改造：修复说明 / 影响代码说明 / 功能说明

> 分支：`dev-compact` · 日期：2026-09-12
> 目标：在不改变上下文压缩**效果与逻辑**（压缩内容、marker/冻结、保护区、CAS 水位、
> 摘要注入格式、Prompt Ledger、稳定前缀字节全部不动）的前提下，消除用户可感知的
> 压缩等待。

---

## 一、修复说明

### 背景：用户可感知的慢在哪

| 慢点 | 现象 | 根因 |
|---|---|---|
| ① 0.95 水位摘要压缩 | 发消息后卡 2~3 分钟 | 分段串行滚雪球 + 每段间无条件 1.5s 延时 + 副模型 prefill 慢，且压缩挡在回合关键路径上 |
| ② 超窗兜底三连痛 | 先等一次失败请求，再等强制压缩，再等全价重发 | DeepSeek 账本路由下，水位线压缩对线上请求"隐身"（账本字节不变），空间压力积压到 provider 报超限才被动处理；估算基线取 `min(真实, 估算)` 被压缩后骤减的工作副本拉低，水位被低估 |
| ③ 冷启动首轮慢 | 轮换代/切模型后第一次回复首字延迟明显 | 前缀缓存全量失效，服务商必须全价重读前缀（物理规律，只能降频不能消除） |
| ④ 打开长会话首次估算慢 | 第一条消息多等一两秒 | token 估算增量缓存冷启动 |

### 本次落地的四项修复

**修复 1：0.85 预压缩（治①，体感收益最大）**

会话占用达到窗口 85%（`memory_compression.precompress_ratio`，0 关闭）且未到 95% 时，
在后台守护线程提前触发记忆压缩。压缩入口与 0.95 同步路径**完全相同**
（`compress_session_memory`：同一分段、同一 prompt、同一增量落库与 CAS 水位推进），
只把触发时机提前——0.95 关键水位到来时摘要通常已落库，回合零等待。

配套约束：
- 复用 `_compressing_sessions` 防重入守卫，后台已有压缩时直接跳过；
- 同会话两次预压缩尝试至少间隔 120 秒（`_PRECOMPRESS_COOLDOWN_SECONDS`），
  防止限流/超时导致每条消息重启一次注定失败的压缩；
- 传入当前回合的 `cancel_event`，用户取消回合则预压缩协式中止（增量进度保留，
  符合取消语义铁律：被取消的预压缩绝不向回合注入任何"接手完成"内容）；
- 预压缩异常只记日志，绝不影响对话主流程。

**修复 2：段间延时自适应（治①，零成本快赢）**

`COMPRESSION_INTER_CHUNK_DELAY_SECONDS` 默认值从 1.5 改为 0。段间无条件延时取消；
仅当本次压缩实际触发过 429 限流后，后续段间插入 2 秒自适应冷却
（`COMPRESSION_ADAPTIVE_INTER_CHUNK_DELAY_SECONDS`），给服务商令牌桶恢复时间。
用户在 config.json 显式配置 `inter_chunk_delay_seconds > 0` 时仍按配置无条件生效
（老配置完全兼容）。10 段压缩可直接省 13.5 秒。

**修复 3：副模型选型建议（治①，配置层面，无代码改动）**

压缩是"长输入短输出"负载，prefill 吞吐决定耗时。建议在设置中将副模型
（compression 角色）配置为 prefill 高速模型。本次不改选型代码，写入功能说明供用户操作。

**修复 4：估算基线修正（治②根因）**

`get_session_token_baseline` 新增 `api_base` 参数。**DeepSeek 账本路由**
（`is_deepseek_ledger_route`：官方 DeepSeek 家族）且真实用量与当前模型一致时，
**直接采信真实用量**（不再取 `min`）。原因：账本路由的实际请求字节来自不可变
Prompt Ledger，压缩只改工作副本（DB 历史），本地估算系统性偏低——摘要压缩后
工作副本骤减而账本字节不变，`min` 永远取被低估的估算，水位线失真、压缩被延迟，
直到爆窗。非账本路由与跨模型场景行为完全不变（`min` / 丢弃旧 real 的分支原样保留）。

**修复 5：主动账本轮换（治②表现）**

Tier3 压缩链（压缩 → 物理折叠 → 滑窗淘汰）完成后，若同时满足：
- 官方 DeepSeek 账本路由；
- 压缩成果安全落库（非熔断 `compress_unprotected`、无并发压缩 `compress_running`）；
- 占用已回到窗口内（`estimated_tokens <= window * SUMMARIZE_RATIO`，
  即无需内存级裁剪、没有未摘要轮次会被挤出）；

则登记一次"待轮换代"标记（`mark_deepseek_generation_rotation`）。下一笔账本请求
在 `_prepare_deepseek_ledger_request` 入口消费该标记，以压缩后历史 `force_new`
重建 generation——实际请求真正瘦身，把"等 provider 报超限才被动轮换"的三段等待
升级为计划内维护。标记幂等、一次消费；只记会话名，不写任何正文。

**修复 7：估算预热（治④）——确认已覆盖，无代码改动**

GUI 的 `_recalc_token_usage` 在切会话/清空历史/回合结束后均已调用
`get_session_token_baseline`（内含 `estimate_tokens`），估算增量缓存已被现有机制
预热。无需新增代码，在此记录结论。

### 预期收益（工程估算，建议上线后按日志校准）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 0.95 挡路等待（10 段典型） | 2~3 分钟（常撞 180s 预算部分完成） | 修复 2+3：约 40~80s；叠加修复 1：**接近 0** |
| 段间固定延时 | 10 段浪费 13.5s | 0（仅 429 后冷却 2s/段） |
| 超窗三连痛 | 分钟级事故 | 修复 4+5 使其基本不再发生 |
| 总压缩 LLM 耗时 | — | 不变（本改造不减算力，只挪时机/提速节奏） |

## 三、功能说明（面向使用者）

### UI 中的变化

本次改造**没有新增任何界面控件**（无新按钮、无新设置面板、无新弹窗），所有
提示复用现有的 notice 通知通道（GUI 插入对话流的 `notice` 消息 / CLI 直接打印）。
用户可见的变化只有以下三处：

**1. 压缩提示出现得更早了（原提示，时机前移）**

原有压缩进度提示——`🧠 正在后台智能压缩并整合长对话记忆...`、
`💾 已保存第 x/N 段压缩进度。`、`✔ 记忆压缩整合成功！...`——外观一字不变，
但出现时机从占用 95% 提前到 **85%**（`precompress_ratio` 可调）。关键区别：

- 以前：提示出现时，你的下一条消息**排队等待**压缩完成（卡 2~3 分钟）；
- 现在：提示出现时压缩在后台进行，**你的消息照常即时发出**，可以继续聊天。

**2. 新增一条提示：主动切换发送队列（唯一的新文案）**

DeepSeek 官方路由会话中，压缩安全落库后会看到一条新提示：

> ℹ 上下文已压缩：下一轮请求将以压缩后历史重建发送队列（前缀缓存会重建一次）。

含义：下一轮请求会把发送内容切换到压缩后的精简版（此前要等服务商报超限错误
才被动切换）。它意味着**下一轮**首字响应会稍慢一次（前缀缓存重建、按全价重读），
属计划内的一次性开销，之后恢复正常。除此之外无任何 UI 变化。

**3. 不变的部分（明确列出，避免误解）**

- **上下文占用量显示（圆圈/百分比）逻辑未动**：界面重算仍走原有
  `min(真实, 估算)` 口径（`_recalc_token_usage` 未传 `api_base`），显示数值
  与旧版一致。注意这与水位线判断口径（账本路由采信真实用量）是两套用途，
  本次有意不合并，避免改动用户已习惯的显示语义；
- 压缩提示的文案、颜色（黄色系 `<ansiyellow>`）、"notice 不自动消失"的行为
  全部沿用旧版；
- 手动命令不变：CLI `/compress`、`/compress force` 照旧可用；
  GUI 仍无手动压缩按钮（维持原设计）。

### 你会感受到的变化

1. **发消息不再被压缩卡住**：以前上下文用到 95% 时，下一条消息要等 AI 写完
   记忆总结（几分钟）才发得出去。现在上下文用到 **85%** 时系统就在后台悄悄
   提前压缩，等真正到 95% 时总结早就写好了——你的消息即时发出。
2. **压缩本身更快**：分段压缩之间的固定等待已取消，只在真的被服务商限流后
   才短暂喘息，多段压缩总耗时明显缩短。
3. **不再出现"等半天然后报上下文超限"**：以前 DeepSeek 会话里，压缩对实际
   发送的内容是"隐身"的，空间压力攒到服务商报错才爆发。现在压缩完成后会
   主动在下一轮把发送队列切换到压缩后的精简版，并提示：
   `ℹ 上下文已压缩：下一轮请求将以压缩后历史重建发送队列（前缀缓存会重建一次）。`
   这条提示意味着下一轮首字响应会稍慢一次（缓存重建），之后恢复正常。
4. **打开长会话的首条消息**：维持原有已优化行为（增量估算缓存），无变化。

### 需要你做的（可选，推荐）

- **给压缩配一个"读得快"的副模型**：设置 → 副模型（secondary），选择
  prefill 吞吐高、价格低的模型并勾选 compression 角色。压缩耗时主要由
  "读历史"决定，这一步通常比任何代码优化收益都大。
- 微调（一般不需要）：config.json 的 `memory_compression` 块——
  - `"precompress_ratio": 0.85`：预压缩触发水位，调低=更早提前压缩，`0` 关闭；
  - `"inter_chunk_delay_seconds": 0`：段间固定延时，默认关闭，被限流困扰时
    可设 1~2 秒。

### 边界与保证

- 压缩的**内容与质量逻辑完全不变**：压什么、怎么分段、摘要写什么、进度怎么
  存、水位怎么推进，与旧版逐字节一致；
- 用户主动取消（停止按钮 / Ctrl+C）后，预压缩随之中止，已完成段落保留、
  未完成的绝不复活，被取消的工作不会在后续回合注入任何内容；
- 所有历史改写仍遵循铁律：一次性、幂等、DB 层完成；请求路径绝不改写历史
  中间字节；`tests/test_prompt_byte_stability.py` 字节金样未改一字。

### 5. 真实 provider 墙钟对比（消耗真实 API 额度）

`scripts/bench_compression_timing.py`：合成会话 25 轮（≈16 万字符），压缩切 7 段
（每段 21~24k token），模型 `openai/qwen3.8-flash`（中转 128K 窗口），同一份代码
仅切换段间延时配置模拟新旧行为，各跑一轮：

| 行为 | 总耗时 | 状态 |
|---|---|---|
| 旧行为（段间无条件延时 1.5s） | **308.5s** | compressed |
| 新行为（自适应 0s） | **206.4s** | compressed |
| **实测差异** | **节省 102.1s（33%）** | |

分段耗时明细（新行为）：46.9 / 30.3 / 29.0 / 18.1 / 19.9 / 12.2 / 41.0 秒。

**归因与诚实话**：两项行为间**确定性的**差异只有 (7-1)×1.5s = 9 秒延时；实测
33% 的差距里其余部分来自中转服务商的逐段延迟波动（同一负载三次运行的分段
耗时可差 ±30%，末段 41s vs 14.6s 都出现过）。两点结论：
1. 段间延时修复收益确定但有限（N 段省 (N-1)×1.5s），**总墙钟的主导因素是
   provider 单段延迟波动**——这正说明"把压缩挪出关键路径"（修复 1 预压缩）
   才是体感收益的主体，因为它让波动发生在用户不等待的时段；
2. 单轮对比噪声大，后续校准应取多轮均值或看压缩日志的滚动统计。

三轮实测（链路验证 1 + 对比 2）共消耗中转额度约 48 万输入 token（每轮输出
仅几百字），成本在元级以内；验证脚本保留在 `scripts/` 可复跑。

### 6. 实测结论：改善与缺陷

#### 已验证的改善

| # | 改善 | 证据强度 | 说明 |
|---|---|---|---|
| 1 | **用户感知等待：0.95 挡路 2~3 分钟 → 约 0** | 机制已验证，量值为推算 | 预压缩把压缩挪到聊天间隙（生命周期冒烟 ✅ + 并发压测 ✅）。压缩任务自身耗时不变，但用户不再在场等待——这是本次改造的主体收益 |
| 2 | 段间固定延时归零 | 实测（确定性部分） | N 段省 (N-1)×1.5s；7 段=9s，占比小但零风险零副作用 |
| 3 | 水位线判断准确性：账本路由按真实占用触发 | 单测 ✅ | 修复前 min 口径被压缩后骤减的工作副本拉低，压缩被延迟到爆窗；修复后压缩更早介入 |
| 4 | 爆窗三连痛（失败请求+强压缩+全价重发）基本消失 | 单测 ✅，联网待验 | 主动轮换把被动爆窗升级为计划内维护 |
| 5 | 稳定性未受损 | 实测 ✅ | 并发压测零异常、守卫无泄漏、SQLite 无死锁；3021 回归全绿；字节金样一字未改 |

#### 已知的缺陷与局限（如实）

| # | 缺陷/局限 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **压缩任务自身墙钟未改善** | 后台总耗时仍 3~5 分钟量级，且 provider 单段延迟波动 ±30% 主导总耗时 | 这是"不改压缩逻辑"约束的直接结果；体感已由改善 #1 兜住。要压缩本身变快：配 prefill 快的副模型（配置即可，预估 2~4×），或放开约束做 Map-Reduce（预估再省 60~70%，二期） |
| 2 | 墙钟对比样本各仅 1 轮 | 33% 差距不能全归因于修复——确定性收益仅 9s，其余是服务商波动 | 后续按压缩日志滚动统计取均值校准；脚本已留 `scripts/` 可复跑 |
| 3 | 主动轮换联网链路未实测 | 无官方 DeepSeek key，"轮换后首请求被接受+缓存恢复"未在线验证 | 本地单测覆盖标记消费/force_new/账本重建；有官方 key 即可补测 |
| 4 | 轮换的固有代价：下一次请求全价重读前缀 | 轮换后首字响应变慢一次 | 一次性开销，且换来了"请求必定放得下"；notice 已明示用户 |
| 5 | 预压缩让 API 消耗提前 | 额度从 95% 水位起花变为 85% 起花（总量不变、时点提前）；无副模型时用的是主模型额度 | `precompress_ratio: 0` 可关闭；建议配便宜副模型 |
| 6 | 极端快节奏对话下预压缩可能来不及 | 预压缩进行中用户连发消息冲到 0.95 → 回退同步路径 | 防重入守卫使其安全降级为 already_running 分支（不阻塞、不重复压），单元+并发测试覆盖 |
| 7 | 账本轮换后第一轮基线滞后 | 旧真实用量（轮换前）虚高，可能触发一次多余的压缩尝试 | `compress_session_memory` 对少于 retain+2 条的会话快速 skipped 返回，单轮内自愈 |
| 8 | UI 占用显示与水位判断口径不一致 | 界面圆圈仍用旧 min 口径，可能出现"显示 60% 但已在后台预压缩" | 有意不合并（避免改动用户习惯的显示语义）；文档已说明 |

#### 一句话结论

**用户能感知的卡顿（发消息被压缩挡路）已基本消除且经过验证；压缩后台耗时按约束保持不变**——想连后台一起快，先配高速副模型（零代码），再考虑二期 Map-Reduce。
