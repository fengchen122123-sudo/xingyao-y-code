# 项目状态跨会话记忆 设计

日期：2026-10-23
状态：设计稿，未实现

## 一、要解决的问题

用户同时维护多个项目（iMOM、星瑶自身、公众号内容）。每次开新会话都要重新交代「这个项目做到哪了、下一步做什么」。现有机制覆盖不到这一段：

| 机制 | 管什么 | 不管什么 |
|---|---|---|
| KAIROS 长期记忆 | 事实、偏好、纠正、外部资源指针 | 项目进展、待办、阻塞项 |
| 断点续跑 | 单回合被中断后从哪一步接续 | 跨会话、跨天的项目状态 |
| 会话摘要压缩 | 单个会话内的历史压缩 | 跨会话聚合 |

结果是项目状态只存在于用户脑子里，每次都要人工复述。

## 二、数据模型

每个项目一份状态文件，字段固定：

| 字段 | 类型 | 说明 |
|---|---|---|
| project_key | string | 项目标识，取 workdir 规范化路径的哈希 |
| display_name | string | 展示名，如「星瑶 Code」 |
| phase | string | 当前阶段，一句话 |
| last_progress | string | 最近一次实质进展，一句话 |
| next_step | string | 下一步要做什么，一句话 |
| blockers | string[] | 阻塞项，最多 5 条 |
| updated_at | ISO8601 | 最后更新时间 |

约束：单份文件控制在 1KB 以内，超出按字段截断并优先保留 next_step。

## 三、存储位置

与 KAIROS 同根的文件系统：

```
~/.ycode/memory/projects/<project_key>.md
```

格式为带 frontmatter 的 Markdown：

```markdown
---
project_key: xingyao-y-code
display_name: 星瑶 Code
phase: 电脑操控点击精度修复
updated_at: 2026-10-23T15:40:00+08:00
---

## 最近进展
observe 自动补元素表已落地，212 项测试通过。

## 下一步
补 A5 局部放大引导，再做 B 批次步数实测。

## 阻塞
无
```

选择理由：可人读、可 git 追踪、损坏易恢复，不需要新建表或迁移。

## 四、写入时机

三个入口，按优先级：

1. **显式指令**：用户说「记一下这个项目到哪了」立即写。
2. **回合结束判定**：回合正常收尾且本轮有文件改动时，由模型判断是否更新，不是每回合都写。
3. **会话归档或切换工作目录前**：兜底写一次。

不做定时后台写：项目状态是语义信息，定时任务拿不到准确内容。

## 五、注入方式

在 `build_memory_system_section()` 里追加「当前项目状态」：

- 按当前会话 `workdir` 反查 `project_key`，命中才注入；
- 未命中（自由对话）不注入；
- 紧凑文本，上限 400 token；
- 位置在记忆索引之后、人设之前。

用户可见性：GUI 侧栏提供只读查看入口，允许手工编辑。

## 六、与 KAIROS 的边界

| 内容 | 归属 |
|---|---|
| 「用户偏好 4 空格缩进」 | KAIROS feedback |
| 「这个项目当前在修电脑操控」 | 项目状态 |
| 「上次那个 bug 的根因是坐标缩放」 | KAIROS project（技术事实） |
| 「下一步要跑回归测试」 | 项目状态 |

判定口径：**会长期成立的事实进 KAIROS，会随进展变化的状态进项目状态。**

## 七、失败与过期

- **过期**：`updated_at` 超过 30 天时，注入时标注「状态可能已过期」，不自动删除。
- **损坏**：frontmatter 解析失败时跳过注入并记日志，不让整个记忆段落失效。
- **并发写**：沿用 `_atomic_write_text` 原子写，最后写入者胜出，不做文件锁。
- **项目移动**：`project_key` 基于 workdir 规范化路径，移动后视为新项目，旧文件保留。

## 八、非目标

- 不做跨机器同步；
- 不做项目状态的时间线可视化；
- 不自动从 git 提交历史推断状态（容易臆造）；
- 不替代会话摘要与断点续跑。
