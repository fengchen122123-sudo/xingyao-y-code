# Y-code CodeBuddy 式工具进度设计

## 目标

把当前“思考完成”连续刷屏、工具过程几乎完全不可见的 TUI 输出，改造成已经确认的 B+C 组合：

- 当前正在执行的工具以 CodeBuddy 风格动态显示；
- 连续读取和搜索按类型合并，避免每个文件各占一行；
- 命令、文件修改和失败操作单独留痕；
- 命令显示中文摘要，并在下一行显示经过安全截断的原始命令；
- 单个工具失败后，失败结果返回模型，Agent 可以分析原因并继续任务；
- 不把模型私有思考写入终端历史，也不再为每个工具轮打印孤立的“思考完成”。

## 非目标

- 不展示或持久化模型私有思考正文。
- 不重做输入框、欢迎卡、会话选择器、模型选择器或 GUI 页面。
- 不引入自动降级算法、静默兜底、盲目重试或基于字符串猜测的通用错误修复。
- 不改变工具权限、沙盒、取消、数据库事务或工具执行顺序。
- 本设计不处理发布打包；源码验证完成后是否重新构建安装包单独决定。

## 交互设计

### 1. 当前工具动态状态

工具开始时，底部现有活动区域显示当前动作、目标和耗时，不把运行中状态写入滚动历史：

```text
⠹ 正在运行测试 · 8.4s · Ctrl+C 中断
  └─ venv\Scripts\python -m pytest -q
```

显示规则：

- 第一行使用人类可读的中文动作摘要；
- `execute_command` 在第二行显示原始命令，超过终端安全宽度时按字符上限截断并追加省略号；
- 其他工具只在目标有诊断价值时显示第二行，例如文件路径、搜索词或 URL；
- 并行工具同时运行时显示“正在并行读取 N 个文件”等聚合状态，不轮流闪烁单个文件名；
- `Ctrl+C` 继续使用现有取消链路，不新增第二套中断机制。

### 2. 完成结果留痕

成功完成后，静态历史使用以下规则：

```text
✓ 已读取 8 个文件 · 1.6s
✓ 已完成 3 次代码搜索 · 0.9s
✓ 已修改 core\turn_renderer.py · +28 / -14 行
✓ 已运行测试 · 12 passed · 4.7s
```

聚合边界必须确定且可测试：

- 连续成功的 `read_file` 合并为一个“已读取 N 个文件”分组；
- 连续成功的 `search_code`、`glob_files` 合并为一个“已完成 N 次搜索”分组；
- `list_directory` 独立显示，避免把目录扫描误报成文件读取；
- `execute_command`、`write_file`、`edit_file`、`fetch_url`、`run_subagent`、权限交互和任何失败操作永远单独显示；
- 工具类别变化、思考开始、正文开始、错误、取消或回合结束时，立即冲刷待输出分组；
- 分组只合并相邻事件，不跨越命令、修改、失败、正文或新的模型思考段。

聚合统计只使用工具事件中的结构化字段。缺少结构化计数时只显示已知数量和耗时，不从任意工具文本中用正则猜测“行数”“匹配数”或“通过数”。

### 3. 失败显示与连续执行

工具失败时，先冲刷已有成功分组，再单独显示失败：

```text
✗ 运行测试失败 · exit 1 · 3.2s
  └─ ModuleNotFoundError: pytest
● 正在改用项目测试环境 · 0.1s
```

行为边界：

- 显示一行稳定错误摘要和第一条关键原因；完整工具结果继续进入会话历史；
- 普通工具失败仍作为 `tool` 结果返回模型，不转换成 `turn_error`，不结束工具循环；
- 模型必须显式分析失败并决定下一步，渲染层不自动重试、不替换命令、不选择降级工具；
- 用户取消、模型/API 无法继续、权限系统内部故障或状态一致性异常仍结束整轮任务；
- 用户拒绝授权是明确的工具结果，可以由模型解释或调整方案，不伪装成成功。

### 4. 思考显示

- `thinking_delta` 继续只进入底部临时思考面板；
- `thinking_finished` 不再向滚动历史打印“思考完成 · 用时 X”；
- 工具开始、正文开始或回合结束时清理临时思考面板；
- 终端历史只保留用户可验证的动作、结果、错误和最终正文。

### 5. 回合收尾

- 最终正文出现前先冲刷所有待聚合工具分组；
- 有最终正文时不再额外打印“共执行 N 项操作”的重复统计；
- 模型没有返回最终正文时，保留本地明确提示，并引用本轮已经显示的工具结果，不制造成功结论；
- 取消和异常结束时同样先冲刷分组，再显示取消或异常原因。

## 架构设计

### `core/tool_progress.py`

新增纯状态与格式化模块，避免继续扩大 `TurnRenderer` 的职责：

- `ToolDisplayEvent`：从现有事件 payload 规范化出工具 ID、类别、动作、目标、原始命令、成功状态、耗时和错误摘要；
- `ToolProgressAggregator`：维护活动工具、待输出聚合分组和已完成记录；
- `start(payload)`：登记活动工具并返回动态状态所需数据；
- `finish(payload)`：完成工具，决定合并、单独输出或失败输出；
- `flush(boundary)`：在类别变化、思考、正文和回合收尾边界冲刷分组；
- 格式化方法只返回 ANSI 文本片段或无样式结构，不直接调用终端 I/O。

聚合器接受可注入的单调时钟，便于测试耗时；生产环境优先使用事件源提供的 `duration_ms`，缺失时才用本地单调时钟计算显示耗时。

### `core/tool_presenter.py`

保留现有中文摘要入口，补充稳定的结构化展示信息：

- 工具类别；
- 人类可读动作；
- 目标；
- 命令预览；
- 已知的结构化统计；
- 稳定错误摘要。

每种工具由显式分支生成展示字段。未知工具使用工具名和目标，不解析任意文本推断指标。

### `core/llm.py`

现有 `tool_requested`、`tool_started`、`tool_finished` 事件顺序保持不变。`tool_finished` 增加可选的结构化展示字段和 `duration_ms`；原有 `summary`、`result`、`arguments` 保留，GUI 和其他消费者继续兼容。

普通工具失败的控制流保持现状：失败结果追加到消息历史并进入下一次模型调用。渲染改动不得改变 Agent 是否继续执行。

### `core/turn_renderer.py`

`TurnRenderer` 委托 `ToolProgressAggregator` 处理工具状态：

- `tool_started` 登记活动工具；
- `tool_finished` 生成静态完成、聚合或失败片段；
- `thinking_started`、`assistant_delta`、`turn_finished`、`turn_cancelled` 和 `turn_error` 触发分组冲刷；
- 删除“所有工具调用保持静默”的固定策略；
- 技能读取提示纳入普通读取聚合之外，仍单独显示“使用技能”。

### `main.py`

- 当前活动区从只保存 `_current_tool_name` 改为保存活动工具结构；
- 并行活动工具按类别和数量显示；
- 移除 `thinking_finished` 写入滚动历史的分隔行；
- 所有终端写入继续在 prompt_toolkit 主线程执行；后台线程只投递事件；
- 继续使用现有 `Ctrl+C`、状态栏和 UI 事件队列。

## 数据流

```text
模型产生工具调用
  → core.llm 发送 tool_requested / tool_started
  → main.py 更新底部动态活动区
  → 工具执行完成并发送 tool_finished
  → ToolProgressAggregator 分类
      → 连续读取/搜索：更新待聚合分组
      → 命令/修改：立即生成单独完成行
      → 失败：冲刷分组并立即生成错误行
  → 工具结果原样回传模型
  → 模型继续工具调用或输出最终正文
  → 正文/回合结束前冲刷剩余分组
```

## 兼容性与安全

- 新增事件字段均为可选字段，现有 GUI 消费者忽略后不会受影响。
- 原始命令展示必须去除 ANSI 控制字符、回车和不可见控制字符，并按显示长度截断。
- 错误摘要不得输出 API Key、授权头或配置文件密钥；沿用现有敏感信息清理规则。
- 聚合器不改变消息持久化内容；数据库仍保存完整工具消息。
- 聚合只影响显示，不影响工具执行顺序、并发批次或错误传播。

## 测试设计

### 单元测试

- 连续 8 个成功 `read_file` 只生成一条读取分组；
- 连续搜索生成一条搜索分组，类别变化时立即冲刷；
- 命令显示中文摘要和截断后的原始命令；
- 修改工具单独显示文件与 diff 统计；
- 失败先冲刷成功分组，再显示错误摘要；
- 失败后接收新的 `tool_started`，状态机保持可用；
- 并行读取显示正确数量，不重复或丢失完成事件；
- 思考、正文、取消和异常边界均冲刷分组；
- 未知工具不触发启发式文本解析。

### UI 测试

- `thinking_finished` 不再写入“思考完成”历史行；
- 底部活动区显示动作、目标、耗时和中断提示；
- 工具结束后动态状态清理，静态结果只打印一次；
- 所有 UI 更新仍在主线程调度。

### 端到端测试

使用确定性假模型执行：

```text
思考 → 连续读取 3 个文件 → 搜索 2 次 → 命令失败
→ 模型读取失败结果 → 修正命令成功 → 修改文件 → 最终正文
```

断言：

- 读取和搜索分别只出现一条分组；
- 失败可见且其后工具继续执行；
- 命令摘要和原命令均可见；
- 没有连续“思考完成”空白行；
- 最终正文只输出一次；
- 工具消息和最终正文正常持久化。

### 回归验证

- 运行工具渲染、UI 事件、LLM 事件和 Agent 端到端相关测试；
- 运行完整 pytest；
- 运行项目规定的 `py_compile`；
- 手工执行一次 K3 多工具检查任务，确认运行中状态、失败续跑和最终正文。

## 验收标准

1. 多工具任务执行期间，用户始终能看到当前动作，不再只有“思考完成”。
2. 连续读取和搜索不会逐项刷屏，而是按相邻类别合并。
3. 命令、修改和失败操作具有可审查的独立记录。
4. 单工具失败不会让整个任务无故结束，模型能够收到失败并继续。
5. 私有思考不进入终端历史。
6. 所有测试通过，GUI 事件兼容，消息持久化不变。
