# 任务先拆解与计划编排设计

## 状态

- 日期：2026-09-28
- 目标分支：`dev`
- 设计状态：待评审
- 触发判据决策：由「3+ 文件、50+ 行改动、架构调整」替换为「拆解出的子任务超过 3 条」；≤3 条直接执行，闲聊、纯问答豁免
- 可见性决策：子任务超过 3 条 → 建计划后自动逐条执行、不打断用户；拆解在内部完成、不单独输出
- 兜底决策：运行时软提醒（多步操作未建计划时拉一把），每回合最多 1 次、阈值默认 3 次实质操作
- 兼容性决策：计划机制本体（core/plan.py）、计划门禁、收尾续推、权限体系零改动

## 1. 背景

当前星瑶是否编排任务完全靠模型自估：系统提示词的「工作流」与「计划编排」段规定「复杂任务（3+ 文件、50+ 行改动、架构调整）先列计划」，但「决策与行动规则」第 1 条又写着「明确且简单的任务只做一次判断，然后立即执行，不为已经清楚的目标增加额外流程」。两条规则互相拉扯，实测表现是「不太爱编排」——大量任务直接埋头干，只在明显大工程时才会 `plan_write`。

harness 侧不存在任何自动检测或提醒机制（已核实：`core/` 内无「任务拆解」「建立计划」相关注入逻辑；hooks 只有 4 个事件、无回合开始注入点）。编排能力（计划门禁、依赖调度、收尾续推、执行租约）本身完备，缺的只是「何时进入编排」的判据与拉力。

## 2. 目标

1. 把「先拆解、再执行」变成默认流程：除闲聊、纯问答外，接到请求先拆解子任务。
2. 拆解结果超过 3 条子任务时，必须先用 `plan_write` 建立计划、按依赖逐条执行；3 条及以内直接执行。
3. 增加运行时兜底：主代理回合内连续多步实质操作但仍未建计划时，注入一次软提醒，把「纯自觉」升级为「有提醒」。
4. 全部改动可测、可回滚，不破坏现有行为契约与缓存口径。

## 3. 非目标

- 不改计划机制本体：`core/plan.py`、计划门禁 `_plan_constraint`、收尾续推 nudge、执行租约（delegated / main_takeover / takeover_queued）全部维持现状。
- 不做「结构化两段式」强制拆解（先强制输出拆解清单再执行）——交互断裂、成本过高，不采用。
- 不改权限体系与「计划模式」权限档位语义。
- 不改除本设计涉及条款外的任何提示词文本与既有守护测试锚点。

## 4. 行为契约（已确认）

1. **适用范围**：闲聊、纯问答豁免；其余请求先拆解。
2. **触发规则**：子任务超过 3 条（即 ≥4 条）→ 必须 `plan_write`；3 条及以内直接执行。
3. **可见性**：拆解内部完成、不单独展示；计划建立后自动逐条执行、不打断、不新增确认环节。
4. **兜底**：检测到「多步未建计划」时注入软提醒（可忽略，不强制）。

### 5.2 运行时兜底（`core/llm.py` 驱动循环）

- **落点**：工具批次执行提交后、`progress_guard.observe(...)` 同一区域（当前约 :2890–2905），每个工具批次后检查一次。
- **计数**：主代理回合内累计「实质操作」次数（per-turn 计数器，回合开始处初始化，与 `plan_continue_nudges` 同区）。计入集合：
  - `write_file`、`edit_file`（按调用次数累计）；
  - `execute_command` 中非只读调用（复用 `classify_command_risk` 的 `PermissionRisk.QUERY` 判定，与 `tool_pipeline._plan_constraint` 同口径）。
  - 成功与失败的调用均计入（宁可多计、不可漏计，提醒可忽略）；不做成败区分。
- **触发条件（全部满足）**：
  1. 计数 ≥ 阈值（常量，默认 3，可调）；
  2. 当前会话无未完成计划（`has_pending_plan` 为假）且非计划回合（`is_plan_turn` 为假）；
  3. 本回合尚未提醒过（每回合最多 1 次，防打转）；
  4. 主代理回合（子代理自身循环不触发；实施时以驱动循环内可用的主/子标识为准，并加用例锁定）。
- **动作**：注入一条 user 角色提醒（与既有 nudge 同模式：`messages.append` + `pending_persistence` 落库 + `flush_persistence`），并触发一次 `notice` 事件（提示词建议：「已提醒模型评估是否需要建立任务计划。」）。提醒本身按既有约定计入进展观察。
- **提醒文案（定稿）**：

  > 本回合已连续执行多步操作，仍未建立任务计划。若任务拆解后超过 3 条子任务，请立即用 plan_write 建立计划并逐条执行；不超过 3 条可忽略本提醒，直接完成。

- **建议命名（实施时按代码风格微调）**：常量 `_ORCHESTRATION_NUDGE_THRESHOLD = 3`；计数集合与提醒文案常量就近声明；回合级 `orchestration_nudge_sent` 布尔标记 + `substantive_op_count` 计数器。

### 5.5 生效与验收

- **生效时机**：提示词 `.md` 文件每轮现读，改动下一轮即生效；`core/context_builder.py`、`core/llm.py`、`core/injection_markers.py` 为进程内代码，需重启应用生效。
- **测试**：`python -m pytest tests/test_prompt_behavior_clauses.py tests/test_context_builder.py tests/test_prompt_byte_stability.py tests/test_context_injection.py tests/test_injection_markers.py`（含新增用例；如环境允许再跑 llm 事件相关子集）。
- **实测（重启后，四场景）**：
  1. 4+ 步任务 → 先建计划、自动逐条执行；
  2. 2 步小任务 → 不建计划、直接完成；
  3. 闲聊 / 纯问答 → 行为无变化；
  4. 3 条内小任务但连续操作达阈值 → 兜底提醒出现且模型可忽略继续（观察误报成本）。

## 6. 风险与权衡

- **规则层仍是软约束**：遵守度取决于模型；兜底是其缓解手段，但兜底为启发式（计数的是「活动量」而非「拆解条数」，存在误报与漏报）。已将提醒设计为可忽略、每回合一次，成本受控。
- **执行变重**：>3 条子任务将走「子代理逐条执行」路径，比直接干更重、更慢——规则的自然结果，先按此观察，阈值与文案均留在常量/文本层可随时调整。
- **缓存与账本**：兜底提醒会改变请求字节，与既有 nudge 同类；有计划在途时不触发，避免与收尾续推叠加。
- **测试更新纪律**：golden 重算必须与文本变更同一次提交完成，不留下「测试红」的中间态；新增条款须带守护断言，防止后续编辑误删。
