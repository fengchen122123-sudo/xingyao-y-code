# 反模式与改写示例

## 一、反模式速查（按危害排序）

| 反模式 | 症状 | 为什么坏 | 改法 |
|---|---|---|---|
| 只改措辞不改信息 | 读起来更顺，缺口一个没补 | 模型该不知道的还是不知道 | 先补信息，最后再润色 |
| 编造业务事实 | 写出具体价格、客户名、日期 | 错误事实成为模型的事实基准，一路传下去 | 留占位符 |
| 用框架标题充结构 | CONTEXT: / TASK: / RULES: 堆一堆 | 标题不产生约束，只稀释注意力 | 用自然段落承载理由 |
| 把判断换成步骤 | 需要权衡的活写成八步清单 | 遇到清单外的情况就卡住 | 只写结果和验收 |
| 形容词当标准 | "高质量""稳定""美观" | 无法验收，模型只能自选一种理解 | 换成数字或可判定条件 |
| 只写正常路径 | 只描述顺利情况 | 真实数据、真实环境下必崩 | 补边界：空、超限、冲突、失败、无权限 |
| 堆砌施压词 | 全大写、必须、千万、极其重要 | 制造过度反应，模型为满足语气加戏 | 正常音量，约束带理由 |
| 复述需求充篇幅 | 把用户的话换个说法再说一遍 | 不约束任何执行行为 | 每句自问能拦住哪个错，拦不住就删 |
| 一次问太多 | 一次抛八个问题 | 用户放弃回答 | 最多 3 个，按价值排序 |
| 重复项目规则 | 把 AGENTS.md 条款再抄一遍 | 两套措辞要模型自己调和 | 只写该规则在本任务的具体应用 |
| 什么都想覆盖 | 把十种可能情况全写进去 | 注意力被摊薄，主线反而做不好 | 只写本任务真会遇到的分支 |
| 把示例当模板 | 给完整样例并要求照着做 | 模型会连长度、语气、结构一起抄 | 只给格式骨架，或注明"仅示意格式" |

## 二、改写前后对照

### 编码改动：补验证方式与不变量

原句：`帮我加个导出功能`

改写后：

> 订单列表页需要一个导出按钮，导出**当前筛选结果**，不是全部订单。
> 现有筛选逻辑在 `src/orders/filters.ts`，直接复用它，不要另写一套。
> 导出上限 10 万行，超过时提示用户缩小范围，不要静默截断。
> CSV 列顺序跟页面表格一致，金额保留两位小数，时间用 ISO 8601。
> 完成后跑 `npm test -- orders` 和 `npm run build`，两个都过才算完成。

补了什么：范围（当前筛选结果）、不变量（复用现有筛选逻辑）、边界（10 万行上限）、格式、验收命令。

### 调试排查：补复现路径

原句：`这个接口老是报错，帮我看看`

改写后：

> `POST /api/orders` 在并发导入时返回 500，报错原文：[待填：完整堆栈]
> 可稳定复现：用 `tests/fixtures/bulk_import.csv`（3200 行）跑导入脚本，三次里挂两次。
> 上周把订单号生成从数据库自增改成雪花算法之后开始出现，之前版本没这问题。
> 修好的标准：同一脚本连跑 5 次不报错，现有单测全过，接口的请求与响应格式不变。

补了什么：精确入口、报错原文、最小复现路径、变更时间点、可勾选的验收标准。

### 分析判断：补判据

原句：`分析一下这两个方案`

改写后：

> 要在两个方案里选一个作为明年的主推方案，按四个维度比较，权重为：
> 实施成本 40%、维护负担 30%、用户迁移难度 20%、扩展性 10%。
> 每个维度给出判断依据（数据、团队现有经验、厂商承诺），没有依据的写"无数据"，不要估算。
> 结论放第一段，直接说选哪个；之后才是支撑。
> 分歧大的维度单独列出，说明这个取舍为什么值得。

补了什么：决策用途、判据与权重、缺数据时怎么写、输出顺序。

### 写作生成：补读者与用途

原句：`写个季度总结`

改写后：

> 写一份 Q3 总结，读者是公司管理层，他们要用这份材料决定 Q4 的预算分配。
> 重点不是罗列做了什么，而是哪几件事带来了可量化的结果、哪几件没达到预期以及原因。
> 相关数据：[待填：Q3 实际指标]
> 篇幅两页内，结论在前、支撑在后。不要用"赋能""闭环"这类词。

补了什么：读者、用途、写作重点、数据占位、篇幅、语言限制。

## 三、长度判断

| 任务 | 合理长度 |
|---|---|
| 一句话机械操作（改名、翻译、格式转换） | 一到两句，不补上下文 |
| 单文件小改动、单段文案 | 三到五句 |
| 多文件功能、一篇文档、一次分析 | 半屏到一屏 |
| 迁移、审计、无人值守多步任务 | 一屏以上，值得展开 |

判断法：写完问自己一句——"再删一句，会不会有某种做法变得不确定？"不会，就删。
