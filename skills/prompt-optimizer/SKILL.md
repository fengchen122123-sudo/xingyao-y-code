# 提示词优化（Prompt Optimizer）

## 解决什么

用户的一句话到模型输出之间，缺口只有两处：**模型不知道的上下文**，和**模型猜不到的完成标准**。改写只做两件事——把前者补进去，把后者写清楚。其余都是噪音。

唯一验收标准：**换一个人或一个模型，只看这份提示词，能不能做出用户想要的同一个东西。**

## 何时不接活

没有缺口就没有工作。遇到以下情况，直接说"这条已经够好了"，然后照原样执行：

- 纯事实查询（"法国首都"）
- 纯对话、闲聊、情绪表达
- 一句话能完成的机械操作（"把这句翻成西语"）
- 提示词已含目标、上下文、完成标准、输出形态
- 用户明说"别废话，直接做"

不要为了显得有用而硬改。改坏了比不改更糟。

## 流程（五步）

### 1. 定任务类型

按 `references/task-types.md` 归类：编码改动 / 调试排查 / 研究调查 / 分析判断 / 写作生成 / 设计前端 / 数据处理 / 多步代理执行。跨类任务取主类，次类只补它独有的槽位。

归类的作用是知道**该问什么**：调试类缺复现路径，写作类缺受众和篇幅，决策类缺判据。任务类型不同，必补的槽位也不同。

### 2. 找缺口

逐项对照四问，缺哪项补哪项：

- **目标**：做完之后，什么东西变成什么样？
- **上下文**：模型不知道、但决定做法的事实有哪些？
- **完成标准**：怎么判断做对了？（测试命令、可勾选清单、对比基准、验收人是谁）
- **边界**：什么不在范围内？哪些动作要先问、哪些可以自己定？

四项都齐 = 不用改。

### 3. 补事实，不造事实

- 先去项目里找：读 `AGENTS.md` / `CLAUDE.md` / 现有代码 / 相关文档，把真实路径、真实规则、真实约束写进提示词。真实路径比占位符有用得多。
- **项目规则里已有的，不要重复**。同一条规则写两遍，模型要去调和两套措辞，纯亏。要写就写成该项目规则的具体应用（"规则要求动线上系统前确认" → "本次只读，停在 `git push` 之前"）。
- 只有用户知道的事实（价格、客户名、期限、内部流程、账号信息）**不许猜**：留 `[待填：具体要什么]`，并在交付时单列。
- 你自己记得但不确定的事实（API 签名、版本号、平台行为）：写成"先核实"，不要断言。把风险说出来，让执行者去查。

### 4. 提问（最多 3 个）

只在答案会显著改变提示词时才问。每个问题给出具体选项、并说明补上能换来什么。能从文件里读到的绝不问，能在提示词里留占位符的也不必问。

问的顺序按价值排：完成标准 > 上下文 > 边界 > 输出形态。

### 5. 改写并交付

按下面七条原则重写，跑一遍自检，再交付。

## 七条改写原则

1. **目标和理由放最前**。一到三句说清要做什么、为什么做。理由让模型在你没写到的分支上也能做对判断。
2. **上下文给足**。路径、背景、受众、数据来源、之前试过什么、已知的坑——这是提示词里最值钱的部分。上下文不足，模型只能退回安全而平庸的默认做法。
3. **把"完成"定义成可验收的**。交付物是什么、放在哪、怎么检查（测试命令、验收清单、与参照物对比）。一句具体的检查胜过十句"要仔细"。
4. **描述结果，不描述过程**。只有顺序真的重要时才编号（数据迁移、破坏性操作、合规步骤、多阶段依赖）。需要判断的活，让模型自己定计划，它往往比你的脚本更合适。
5. **约束带理由，正常音量**。不用全大写，不用"必须""极其""千万"。正面表述优先："公共 API 保持不变，因为三个服务在调"胜过一串禁止项。只有在确实踩过坑时才写死禁令，并说明那次是怎么出事的。
6. **划清自主权**。哪些能自己决定、哪些必须先问（破坏性命令、动线上系统、对外发消息、花钱）。没写的部分默认它可以自己推进到底。
7. **说清最终报告要有什么**。改了什么、怎么验证的、还有什么没解决、替你做了哪些假设。

## 必删清单

上一代提示词的遗留物，对现在的模型是负收益：

| 删掉 | 原因 |
|---|---|
| `think step by step` / `逐步思考` / `<scratchpad>` | 推理已内置。当指令写进去只会让输出变啰嗦，部分模型还会拒答"展示推理" |
| `你是一位世界级专家……` 拿来当上下文 | 角色不提供信息。一行角色可以，但替代不了真实上下文 |
| 全大写、`非常重要`、`必须`、`千万` | 制造过度反应，模型为满足语气而加戏 |
| `请尽量`、`如果可以` 用在硬要求上 | 把硬约束说成软建议，等于没有约束 |
| 字数上限（除非格式强制） | 改成描述长度："一分钟能扫完" |
| 笼统禁令（"不要输出解释""不要展示过程"） | 会连带砍掉有用的结论说明。要限制就限制具体项 |
| 评分官话术（"我会按……打分"） | 对现代模型无效，只是占篇幅 |
| 重复项目已有规则 | 两套措辞要模型自己调和 |

## 自检（交付前逐条过）

- [ ] 目标、上下文、完成标准、边界，四样齐了？
- [ ] 有没有形容词没落到数字或可判定条件？（"快" → "首屏 <1.2s"）
- [ ] 完成标准能被人照着勾选吗？
- [ ] 有没有把用户未知的事实写成断言？
- [ ] 有没有重复项目已有规则？
- [ ] 施压词、CoT 指令、字数上限、评分话术，清干净了吗？
- [ ] 输出语言跟用户一致吗？（提示词的语言跟原提示词走，说明部分跟对话语言走）
- [ ] 比原文长出来的部分，每一句都能拦住一个具体错误吗？拦不住就删

## 交付格式

```text
## 优化后的提示词

<裸文本，可直接复制粘贴；不加 markdown 修饰，除非提示词本身需要>

## 改了什么

3–6 条，每条对应哪条原则、解决了什么问题

## 需要你确认

- 只有你能填的 [占位符]，逐条列出；没有就省略这节
```

**提示词是交付物，说明部分要短。** 不要把分析过程铺在提示词前面让人往下翻。

## 常见错法

| 错法 | 后果 | 改法 |
|---|---|---|
| 把提示词写长当写好 | 注意力被稀释，执行反而变差 | 一句能拦住的错，别写三句 |
| 用框架标题硬套结构（CONTEXT: / TASK: / ...） | 标题不产生约束，只占篇幅 | 用自然段落承载理由，真需要分段才用小标题 |
| 替用户编业务事实 | 错误事实会成为模型的"事实基准"一路传下去 | 留占位符 |
| 把"你自己判断"换成具体步骤 | 限制了模型的判断空间 | 只写结果和验收，过程让它定 |
| 一次问十个问题 | 用户放弃回答 | 最多 3 个，按价值排序 |
| 只改措辞不改信息 | 换了说法，缺口还在 | 先补信息，再调措辞 |
