# 提示词扩写执行法（Prompt Expansion）

把用户一句话需求，扩写成「复现级」详细执行提示词，再严格按它执行。
判定标准只有一条：**换一个执行者，只看这份文档，能做出与预期一致的东西。**

## 能力从哪来（三个都不能少）

多数扩写失败不是因为格式不对，而是因为内容空。本技能的能力来自三根支柱，缺任何一根都是空壳：

1. **领域参数库** `references/domain-specs.md`
   扩写前必须先查目标领域的「必填槽位」与「领域坑位」。参数不是拍脑袋想的，是从库里取的默认值再按需求调整。没查库就动笔 = 编造规格。
2. **质量门禁** `references/quality-rubric.md` + `scripts/spec_lint.py`
   文档落盘后必须跑：`python scripts/spec_lint.py <文档路径>`。分数 < 16/20 不许进入执行阶段，按报告逐项补，补完重跑。
3. **对照范例** `references/example.md`
   先读范例再动笔，模仿它的密度与锐度，不是模仿它的段落标题。

## 硬门禁（五条，任一不过不许开工）

- **G1 选型唯一**：技术栈不得出现"或/建议/可以考虑/视情况"。出现一处即不合格。
- **G2 量化达标**：每个形容词都有对应数字或可判定条件（"美观"→色值与字号；"流畅"→帧率与上限；"快"→毫秒数）。
- **G3 边界齐全**：空输入、超限、同名冲突、失败、无权限、离线/断网——逐条给出行为，不能只写正常路径。
- **G4 验收可勾选**：每条验收项都是一个"做什么→看什么"的断言，含具体检查手段（命令/操作序列/截图点位）。
- **G5 假设显式**：用户没指定的项，我定的默认值必须进「假设清单」，且每条都写清推翻后会改什么。

## 文档结构（五段式，按任务裁剪）

落盘：`<AI生成内容目录>/<任务短名>/执行提示词.md`（用户指定路径时从其指定）。

```markdown
# <任务名> · 完整执行提示词
> 原始需求（用户原话，一字不改）

## 一、总提示词与交付形态
一句话目标；交付物：文件数与路径、形态、体积上限、依赖策略、运行环境与兼容边界。

## 二、素材与资源规格（无素材任务整节省略）
每项素材：工具与模型、完整生成提示词原文、尺寸/时长/码率、压缩命令。标注可否并行。

## 三、技术规格
- 工程与打包：依赖及精确版本、构建命令、产物组装方式
- 核心参数表：坐标、色值、阈值、上限、时长、物理量——能写数的一律写数
- 行为规则：正常路径 + 边界路径（对照 G3 逐条）
- 安全红线：不许删除什么、不许越界到哪、不许覆盖什么

## 四、交互与边界矩阵
一张表：每个输入（键/按钮/参数/异常）→ 具体行为。移动端与降级单列。

## 五、验证与交付清单
- [ ] 可勾选项：动作 + 期望观察结果 + 检查手段
- 未验证项须如实标注，不得默认通过
- 已知坑：执行中踩到并修复的，回写这里
```

## 执行流程

1. **判定触发**：创造性任务或 >5 分钟 → 走本流程；否则直接执行。
2. **查库定槽**：读 `references/domain-specs.md`，按任务性质取出对应领域的必填槽位与坑位清单。跨领域任务取多张表。
3. **补事实**：缺口先查项目现状（读文件/搜索/查版本号）；仍缺且影响方向的才问用户，其余进假设清单。不得凭空编造版本号、API 签名、路径。
4. **落盘**：比照 `references/example.md` 的密度写文档。
5. **跑门禁**：`python scripts/spec_lint.py <文档>` → 分数 ≥16 且无 G 级硬失败才继续；否则按报告补齐重跑。
6. **亮规格**：3–6 行向用户汇报交付形态 + 关键假设 + 预计产物 + lint 分数，然后直接执行（已授权本工作流，不必等批准；用户喊停即停）。
7. **按文档执行**：>3 个子任务先 plan_write；派子代理时把文档相关章节原文投喂，不许口头转述。
8. **按清单验证**：逐条执行第五节；通过/未执行/失败如实分列。
9. **经验回写**：踩到的坑与修复追加到文档「已知坑」，并把可复用的新领域槽位补进 `references/domain-specs.md`。

## 裁剪规则

| 任务规模 | 文档形态 |
|---|---|
| 小创意任务（单页/单脚本） | 五段式精简版，一屏内，省略素材节，验收项 ≥6 条 |
| 中型任务（多文件功能/工具） | 完整五段式，验收项 ≥10 条 |
| 大型任务（多子系统） | 先拆子项目，每个子项目一份五段式 + 一份总纲（依赖顺序与联调点） |

## 反模式（出现任意一条即判定扩写失败）

| 反模式 | 为什么失败 | 改法 |
|---|---|---|
| 复述需求充篇幅 | 不约束任何执行行为 | 每句自问"这句能拦住哪个错误做法"，拦不住就删 |
| 留活口（"可以用 A 或 B"） | 把方案选择推给执行者，结果不可复现 | 定死一个，另一方案进「备选与代价」一节，注明何时才换 |
| 参数靠形容词（"响应要快"） | 无法验收 | 改成"首屏 <1.2s、交互反馈 ≤100ms" |
| 只写正常路径 | 真正出问题全在边界 | 按 G3 六项逐条扫一遍 |
| 验收写成愿望（"确保稳定"） | 不可勾选 | 改成"连续点 50 次不崩，控制台无 error" |
| 假设藏起来 | 用户不知道我替他做了决定 | 全部列进假设清单，附推翻影响 |
| 抄范例段落标题 | 形似神不似 | 学密度与锐度，不学排版 |

## 常见失败信号

- 写完后自己都说不清"这文档比需求多约束了什么" → 回去查库，槽位没填满。
- 文档里数字少得可怜，却有很多"合理""适当""尽量" → 未过 G2。
- lint 分数高但内容空 → 有意识地把形容词换成数字再编造，属作弊；以"能否据此复现"为准。
