## 补充说明（不用粘贴）

**为什么这次不做"让阿里云达到 99%"的承诺。** 修掉域名兜底能拿回的只是"星瑶自己制造的那部分损失"。数据里还有一半是上游责任：阿里云 keepalive 反复发送**完全相同的字节**时命中在 `0 / 58,880 / 2,048 / 4,096 / 0` 之间翻转（另有一会话 `prompt=70,482` 重复 23 次，稳态命中 81.9% 后转成成片 0）——客户端解释不了这个。加上同端点的 qwen3.8-flash main 也只有 86.39%，说明这个端点的天花板本身就不高。**所以 Task 8 的结论完全可能是"修完从 82.7% 升到 93% 左右，仍低于基元律动的 97%"**，那就是真实答案，如实写进报告，然后转「网关缓存亲和专项」（另一个工作包），不要为了凑数继续往请求上加参数。

**Task 6 为什么建议后置。** `prompt_cache_key` 只有 OpenAI 与 Kimi 有官方文档背书（OpenRouter 把它当 sticky routing 的 fallback key），Qwen / GLM / MiMo 官方文档全都没提，而且**没有任何一家承诺"未知字段会被忽略而不是报错"**。你现在有 16 个 provider，默认发等于把全部押在"大概会被忽略"上。用 `route_request_overrides` 手工 A/B 一遍，用几百 token 换一个确定结论，比先写实现再猜去哪几个车道要划算。

**观察期别把 R1 当回归。** Task 1 落地后阿里云 deepseek 车道的请求头少 1 个、messages 少 3 个 content 标记，缓存前缀**必然重建一次**，首次请求全量 miss。诊断曲线必须标注切点，否则会误判成"改动把命中率改坏了"——这正是 2026-09-23 那次 `bench_tr_before/after` 76.66% vs 64.91% 被误读成回归的同类陷阱（实为上游时点抖动，见 `docs/adapt-report-deepseek-tokenrhythm-cache.md`）。

**旧结论已作废。** 排查中无法从当前库复现 2026-09-23 记录的 `93.84% / 96.22% / 60.54%` 等数字（按 session×lane、session×lane×day、热轮口径、诊断表口径、小时桶全部扫过一遍均不出现）。那些数字很可能来自当期某个滚动窗口快照，**不要拿它们当基线**。本文档 §1.2 的三渠道数字是当前基线。
