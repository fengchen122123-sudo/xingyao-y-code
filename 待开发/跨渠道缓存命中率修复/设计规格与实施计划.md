## 一、背景与问题证据

### 1.1 触发观察

用户观察到：星瑶用**阿里云 token-plan 的 deepseek 模型**命中率明显偏低，用**基元律动（tokenrhythm.studio）**的更高。这与 2026-09-23 那次排查的结论方向相反，因此重新做了一次全量数据考古，用真实库定死"谁高谁低、差多少、差在哪"。

### 1.2 三渠道实测对照（`ycode_gui.db` 全量，只读）

| 车道 | scope | 轮次 | prompt | cached | 累计命中率 | 热轮（排除冷启动） |
|---|---|---|---|---|---|---|

| 对照：基元律动 / deepseek-v4-pro-0813 | main | 1,295 | 144,765,852 | 142,028,672 | 98.11% | — |
| 对照：api.kimi.com/coding/v1 / k3 | main | 2,730 | 377,118,076 | 362,996,596 | 96.26% | — |

同一批模型在 **keepalive** scope 下的表现（这是本次最刺眼的一组对比）：

### 1.3 归因分解：14.5pp 的差距从哪来

| 因素 | 贡献 | 依据 |
|---|---|---|
| 冷启动 | **≤0.5pp** | 阿里云冷启动 token 占本车道 0.4%，排除后仅 +0.26pp；基元律动同量级 |
| 客户端换代/历史重写 | **−1.5pp（帮了阿里云）** | 阿里云纯追加 321 轮、**0 条历史重写**；基元律动反而有压缩轮（main 189 轮）把自身从 98.73% 拖到 97.01% |
| **上游"纯追加却整段丢前缀"** | **≈15.5pp，占几乎全部差距** | 见下表 |

**核心指标：上游整段丢前缀率**——只在 `request_reason == ''`（纯追加、客户端字节零改动）的轮次里统计 `cached_tokens < min(上一轮 prompt_tokens, 本轮 prompt_tokens) × 0.6`：

| 车道 | 纯追加轮 | 上游丢前缀轮 | 占比 |
|---|---|---|---|
| 基元律动 / deepseek-flash main | 4,527 | 22 | **0.5%** |
| 阿里云 / deepseek-v4.1-flash main | 299 | 42 | **14.0%** |
| 基元律动 / deepseek-flash subagent:implement | 2,561 | 117 | 4.6% |

逐轮 `cached / 上一轮 prompt` 分桶（同一车道内）：

| 车道 | n | ≥99% | 90–99% | 60–90% | <60% | =0 |
|---|---|---|---|---|---|---|
| 阿里云 main | 319 | 212 | 43 | 15 | 30 | **11** |
| 基元律动 ds-flash main | 4,527 | 4,394 | 18 | 4 | 20 | 2 |

形态是**整段蒸发**，不是块粒度截断：

- `prev=254,057 → cached=6,144`
- `prev=226,647 → cached=0`
- `prev=164,945 → cached=0`

token 权重：这 56 个 <90% 的轮次占阿里云车道 **17.4% 的 prompt token**，且**阿里云全部"未命中 token"的 96.7% 来自它们**。

间隔相关性（说明不只是 TTL）：命中轮中位间隔 20s、未命中轮 56s；间隔 >300s 的 8 次全部未命中；**但 31/56 次未命中发生在 <60s 内**。

### 1.4 星瑶自己造成的那一半：域名兜底把 deepseek 拽进了 Qwen 家族

只读方言探针实测（同一模型、两种渠道）：

| 探测项 | 阿里云 token-plan | 基元律动 |
|---|---|---|
| `_is_deepseek_family` | True | True |
| `_is_qwen_family` | **True（域名兜底）** | False |
| `_supports_cache_control` | **True** | False |
| `_apply_cache_control` 断点数 | **3**（system / 最后一条可标记 assistant / 尾部 user）；**工具轮退化为 1（只剩 system）** | **0（messages 逐字节不变）** |
| `_provider_request_options(...).extra_headers` | `{'x-dashscope-session-cache': 'enable'}` | `{}` |
| `harness_steps.cache_lane_sha256` 非空比例 | **97.6%**（170 步中 166） | **2.5%**（1,439 步中 36） |
| 工具字母序 / 账本 / 保活 | 有 / 有 / 有 | 有 / 有 / 有（**无差异**） |

**成因链（读码确认）**：
`_is_official_dashscope_route`（`core/llm_dialects.py:123-146`，`:144-145` 匹配 `.maas.aliyuncs.com` 后缀）→ `_is_qwen_family`（`:149-160`，`:160` 的域名兜底**无条件生效**）→ `_supports_cache_control`（`:836-851`）→ `_qwen_cache_control_configured`（`:284-290`，只看家族）→ `_apply_cache_control`（`:865`，唯一调用点 `core/llm.py:1736`）→ 消息 content 由字符串被改写为 `[{"type":"text","text":…,"cache_control":{"type":"ephemeral"}}]` 数组。

实测 `_apply_cache_control` 返回后的断点位置：

```
breakpoint 1 = system          （:931-932）
breakpoint 2 = 最后一条可标记 assistant（:944-949）
breakpoint 3 = 尾部 user       （:960-963，仅 Qwen 分支，is_qwen 判定在 :895）
```

工具轮真实形状（system + user + `assistant(content="", tool_calls)` + tool 结果）：空文本 assistant 打不上 content 块断点、tool 消息被协议约束不可标记，**只剩 system 一个断点**。

**两个后果**：

1. **前缀字节被改写**。`RequestEnvelope.messages_sha256` 实测由 `ce796db1…` 变为 `81fdbbb6…`，`request_bytes` 188 → 374。任何按原始字节做前缀匹配的缓存都会把这条请求视为**不同前缀**。
2. **被推到显式缓存路径**。阿里云官方文档明确"显式缓存与隐式缓存**互斥，单个请求只能应用其中一种**"（help.aliyun.com/zh/model-studio/context-cache）。带上 `cache_control` 后请求走显式缓存（最小缓存块 1024 token、TTL 5 分钟命中重置、可缓存范围由断点框定），而工具轮里断点只剩 system 一个，显式缓存**只覆盖到系统提示词为止**，其余又回落隐式——不是"完全替换"，而是"前缀头部被改写 + 头部区间被显式接管"。

**这不是实现疏漏，而是作者明示意图被域名兜底打破**。`core/llm_dialects.py:697-702` 的注释原话：

> 其余 OpenAI 兼容网关默认不标记——隐式缓存本就命中，而显式标记可能被严格校验的网关拒绝为 400（真被拒绝时由 `_disable_cache_control_route` 临时降级兜底）。

### 1.5 归因不可信：诊断指纹与线上字节是两个口径

| | 诊断表 `cache_request_diagnostics` | `RequestEnvelope`（落 `harness_steps`） |
|---|---|---|
| 计算时机 | 打标**前**（`core/llm.py:1704` / `:1713-1724`） | 打标**后**（`core/llm.py:1785`） |
| `messages_sha256` | `ce796db1…`，188 B | `81fdbbb6…`，374 B |
| 对 content 块内的 `cache_control` | `_cache_message_fingerprints`（`core/llm_diagnostics.py:66-76`）只过滤**消息顶层** `cache_control` 键，content 列表原样进 sha256 | 原样哈希 |

**结论**：同一次请求，诊断表与 envelope 记录的不是同一批字节（诊断系统性偏小）。所以"诊断显示字节没变、上游却没命中"这类判断，在 Qwen 这种 content 块标记的请求上是**不成立的**。2026-09-23 那次归因判断即受此影响。

补充：`_cache_message_fingerprints` 只剥顶层这一限制，对 Anthropic 形式（消息顶层标记）是够用的，对 Qwen 形式（content 块标记）不够——**这是"一套代码服务两种标记形态"留下的口径缝**。

### 1.6 保活失控：120 秒一次的全价前缀

阿里云保活命中率 24.04%（118 轮），基元律动 90.15%（61 轮）。更强的证据是**阿里云保活请求是"反复发送完全相同的字节"**：

- 某会话 `prompt=58,945` 重复 46 次，`cached` 在 `0 / 58,880 / 2,048 / 4,096 / 0` 之间来回翻转；
- 另一会话 `prompt=70,482` 重复 23 次，稳态命中 57,753（81.9%）后转为成片 0。

**字节相同、端点相同、命中在翻转**——这是上游侧的缓存保留行为，客户端无法解释。而保活是每 120 秒一次的全价前缀请求，在亏损车道上纯属烧 token。

### 1.7 口径：状态栏的假跌

`main.py:4509-4522`（`get_status`）用的是**进程级累计**——取 `core/llm_diagnostics.py` 全局 `session_token_usage.process` 的 `cumulative_cached / cumulative_prompt`，把本进程内**所有会话、所有渠道、所有 scope** 混算。

| 车道 | main 命中率 | 全 scope 命中率 | 差 |
|---|---|---|---|
| 阿里云 / deepseek-v4.1-flash | 82.45% | 70.96% | **−11.5pp** |
| 基元律动 / deepseek-flash | 97.01% | 96.36% | −0.65pp |

**保活污染 main，在阿里云上凭空多掉 11.5pp。** 而车道级命中率其实已经算好了——`_cache_usage_states[state_key]` 里有 `latest/hot/session_all` 三个口径（`core/llm_diagnostics.py:305-380`），状态栏就是没用它。

### 1.8 同名反义字段（未来踩雷点）

| 字段 | OpenAI | Kimi |
|---|---|---|
| `prompt_cache_options` | 认（显式缓存，GPT-5.6+） | 认（仅 `mode=implicit`，ttl `5m`/`1h`） |
| `prompt_cache_breakpoint` | 认（显式断点） | **收到即 400**（官方文档原话：content 中出现 `prompt_cache_breakpoint` 时请求会被拒绝） |
| `prompt_cache_key` | 认（字段定义者） | 认（Kimi Code Plan 下**必填**） |
| `prompt_cache_retention` | 认（`in_memory` / `24h`） | 文档未提及 |

**「统一按 OpenAI 协议发」会在这里撞车**——同一组字段名在两个"OpenAI 兼容"家族里语义相反，必须渠道级 opt-in。这也是为什么 §4.3 的 `prompt_cache_key` 推广必须默认关闭。

### 1.9 数据可靠性与局限（必须连带读）

- **阿里云车道是 2026-09-23 06:18 UTC 才出现的新车道**，只有 2 天 / 307 轮；基元律动那 97% 由两周 8.36 亿 token 支撑，非常扎实。所以"阿里云低"可信，但"低多少"会波动。
- **无法从当前库复现** 2026-09-23 记录的 `93.84% / 96.22% / 90.19% / 96.20% / 60.54%`：按 `(session, model, api_base, scope)`、`(session, lane, day)`、热轮口径、诊断表口径、小时桶全部扫过一遍均不出现；`prompt 合计 269,540 / cached 10,496` 的组合也找不到。旧结论很可能来自当期特定时点的滚动窗口快照，**不作为本计划依据**。
- CLI 库（`~/.ycode/ycode.db`）**没有阿里云车道**，数据截止 2026-09-17，对本次对比无证据价值。
- `harness_steps.model` / `api_base` **两库 100% 为空**（GUI 5,214 行、CLI 338 行全 NULL），且与 `cache_request_diagnostics` 按 sha 三元组 JOIN 匹配 0 行。§1.4 的机制指纹是用**发送时间戳对齐**（`started_at_ms/1000` 与 `token_usage.ts` 相差 ≤3s）得出的——这是**推断性对齐**，不是表间外键，引用时注意。

## 二、目标与非目标

### 2.1 目标

1. **止血**：让每条车道发出的请求形状回到"隐式缓存可用时只保证前缀字节稳定"的最小共同集合，不再因为域名兜底给非本族模型强加显式缓存参数；
2. **可度量**：把"渠道天花板"变成可读数字——上游整段丢前缀率、分 scope 命中率、保活独立命中率；
3. **按证据开关**：保活与亲和键的启用由**车道实测证据**决定，而不是由模型名硬编码的家族表决定。

### 2.2 非目标（明确不做）

- **不发明新机制**：不加任何我们没有证据支持的缓存参数；
- **不改** DeepSeek 不可变 Prompt Ledger、**不改**工具字母序、**不改**三级水位线（0.60/0.80/0.95）、**不改** `route_request_overrides` 本身；
- **不改任何现有请求字节金样**；
- 不做 UI 编辑入口（配置写 `config.json`，改动即热生效）；
- 不追求"让阿里云一定达到 99%"——渠道天花板不由客户端决定，客户端只负责**不自己制造损失**并把天花板量出来。

## 四、设计

### 4.1 名称优先的家族归属

**现状语义**：`模型名匹配 OR 官方域名匹配`。四条判定**都不要求模型名与域名同时命中**，于是任何挂在官方域名上的模型都会被归入该家族。

**问题**：域名兜底对**多模型聚合域**（`.maas.aliyuncs.com` 同时托管 deepseek / qwen / glm / kimi 第三方部署）无条件生效，正是 §1.4 的成因。

**新语义（四族对称）**：

```
名称命中本族            → True（不变，保证本族名优先）
名称已属其他已知族      → 域名兜底不生效 → False
名称无任何归属          → 域名兜底照旧
```

**硬性实现要求（防递归是第一位）**：

1. 新增**纯字符串**判定 `_family_names(model_name) -> frozenset[str]`：只做名称匹配（复用 `_KIMI_NAME_RE`），**绝对不调用**四个 family 函数，从结构上排除 `qwen → kimi → qwen` 的互相递归；
2. 四族各自的域名兜底分支前加同一道门；
3. **域名兜底不能整体删掉**——`tests/test_qwen_cache.py:50` 断言 `_is_qwen_family("custom-model", dashscope) is True`；
4. **不能动 `_is_official_dashscope_route`（`:123-146`）本体**——`tests/test_qwen_cache.py:30` 断言它匹配 maas 域为 True；
5. 名称分支（`:158` 的 `"qwen" in model or "dashscope" in model`）必须**保持在最前**，保证 `openai/qwen3.8-flash` 这类本族名不受影响；
6. 名称命中多族时维持现状（各自独立判定，**不引入单值家族概念**）——`openai/deepseek-r1-qwen-distill` 这类混合名现状是双 True，不在本计划改变范围内。

**为什么四族都要做**：实测 `openai/kimi-k2.6`、`openai/glm-5.3` 挂在 maas 域上同样是双家族。真实配置里目前只有 1 个模型受影响（阿里云 `deepseek-v4.1-flash`），但这是**语义自洽性**问题，留着就是下一次同类事故的种子。

### 4.2 车道健康与「上游整段丢前缀率」

lane = `(model, canonical_api_base, cache_scope)`（与 `_cache_usage_key` 一致）。

```python
@dataclass(frozen=True)
class LaneHealth:
    model: str
    api_base: str
    cache_scope: str
    reported: bool            # 窗口内是否出现过 cache_reported=1
    samples: int              # 计入分母的轮次
    hot_prompt: int
    hot_cached: int
    hot_hit_rate: float       # token 加权 sum(cached)/sum(prompt)
    upstream_loss_rate: float # ★核心：纯追加轮里丢前缀的比例
    consecutive_loss: int     # 连续丢前缀轮次
    client_rewrite_count: int
    verdict: str              # healthy | unreported | upstream_lossy | client_rewrite | insufficient
```

**判定规则（全部写成测试）**：

| 条件 | 处理 |
|---|---|
| `request_reason == '冷启动'` | 不入分母（但计数，供展示） |
| `cache_reported = 0` 或 `usage_valid = 0` | 不入分母；窗口内全为此类 → `verdict = unreported`（**绝不记 0**） |
| `request_reason != ''` | 计入 `client_rewrite_count`，不入健康分母 |
| `request_reason == ''` 且 `cached < min(上一轮 prompt, 本轮 prompt) × 0.6` | 计一次 upstream loss |
| 连续 ≥2 次 upstream loss | `verdict = upstream_lossy` |
| 样本不足（阈值待定，建议 <20 轮） | `verdict = insufficient`，**Task 5 不得据此动作** |

**为什么这是核心指标**：命中率百分比把"新增长的 token""冷启动""客户端换代""上游驱逐"全部混在一个分母里；上游整段丢前缀率只保留"客户端字节零改动"的轮次，是**渠道责任**的最干净度量。基线即 基元律动 0.5% vs 阿里云 14.0%。

### 4.3 证据开关

| 机制 | 当前判定来源 | 改为 |
|---|---|---|
| 保活 | 四族名 ∪ `cache_keepalive_routes` 显式白名单（`_supports_cache_keepalive:659-671`） | 上述判定**不变**，但加一道**车道证据门**：该车道 keepalive scope 的独立命中率低于阈值且样本足够 → 停该车道保活，TTL 取小时级自愈 |
| `prompt_cache_key`（亲和键） | `_is_kimi_family`（`_attach_kimi_request_extras:1286`） | **默认关闭**；顶层 `cache_affinity_lanes` 白名单开启；开启后沿用 `_strip_cache_affinity_options` + 400 拉黑 |

**为什么默认关闭而不是默认开**：`prompt_cache_key` 只有 OpenAI 与 Kimi 有文档背书（OpenRouter 把它作为 sticky routing 的 fallback key），Qwen / GLM / MiMo 官方文档均未提及；而**没有任何一家承诺"未知字段会被忽略而不是报错"**。默认开等于把 16 个 provider 全部押在"大概会被忽略"上。
