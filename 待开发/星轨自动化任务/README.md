# 星轨自动化任务工作包

状态：待开发（本计划书仅为设计文档，未经用户明确同意不得开始开发）
设计日期：2026-09-12
目标：为星瑶 GUI 增加常驻的「自动化任务」能力——用户可以把一段提示词绑定到定时/启动触发器上，由调度引擎在指定时间自动向指定会话发起一次完整的 agent 回合，并留下可追溯的运行历史。

命名说明：「星轨」为本工作包代号（沿用星瑶/星璇命名习惯），如需更名只改本目录名与文档内代号，不影响设计内容。

## 文件说明

- [01-完整设计规格.md](01-完整设计规格.md)：功能、架构、数据模型、触发语义、权限安全、GUI、异常与测试设计，以及按阶段拆分的实施任务分解，是实现的唯一需求基线。
- [02-Agent开发提示词.md](02-Agent开发提示词.md)：可直接复制给开发、评审和验收 Agent 的提示词。
- [03-验收清单.md](03-验收清单.md)：完成定义和人工验收场景。

## 使用顺序

1. 用户确认本计划书（或提出修改意见，先改规格再开发）。
2. 将「主开发 Agent 提示词」交给负责实现的 Agent。
3. 开发完成后，将「代码评审 Agent 提示词」交给独立评审 Agent。
4. 修复评审发现后，使用「最终验收 Agent 提示词」执行全量验证。
5. 只有 [03-验收清单.md](03-验收清单.md) 中所有适用项目通过，才视为完成。

## 不可改变的产品决定

1. 调度引擎只存在于 GUI 常驻进程内：定时触发仅在星瑶应用运行期间生效（含最小化到托盘驻留）。应用未运行时错过的任务按每个任务的 `missed_run_policy` 处理（默认跳过并记录），绝不在启动时静默补跑一堆过期任务。
2. 自动化回合必须走既有回合管线（`gui_bridge._run_turn_worker` → `prepare_turn_messages` → `chat_with_model_events`），绝不旁路 Harness、绝不绕过消息落库、绝不引入第二种「无界面执行引擎」。自动化任务的提示词以真实 user 消息落库，是运行痕迹的一部分。
3. 无人值守权限安全：自动化回合遇到需要人工确认（ASK）的权限请求时立即自动拒绝并记录，绝不无限等待、绝不静默提权。若用户希望自动化任务能改文件/执行命令，必须在任务上显式选择 `accept_edits` 或 `full` 档位并承担相应风险；这两个档位的选择只能由用户在任务表单中主动做出。
4. 用户取消的自动化回合绝不自动重放、绝不注入接手指令（对齐 AGENTS.md 取消语义铁律）；崩溃/退出时未完成的运行标记为 `interrupted`，绝不自动重跑（对齐 Harness 崩溃恢复铁律）。
5. 同一任务上一次运行未结束（queued/running）时，本次触发跳过并记录 `skipped`，不排队堆积、不并发重入。
6. 自动化相关表只存任务元数据与运行状态（谁、何时、结果如何）；对话正文、工具参数与结果的唯一事实源仍是 `messages` 表与既有管线，调度层绝不复制对话内容。
7. v1 只做 GUI 端；CLI 管理命令（`/automation` 等）列为二期另行立项。`next_run_at` 的 CAS 认领设计保证未来即使 CLI 也托管引擎，同一任务也不会被两个进程重复触发。
8. 遇到错误显式失败：触发分发失败、会话缺失、触发器配置非法都要留下可读的错误记录，禁止静默降级或自动重试。
9. 不做 MVP 或分版交付；按完整设计实现。实施过程可拆分提交，但最终交付必须覆盖规格全部范围。
10. 引擎线程绝不做 LLM 请求、文件 IO（除自身 SQLite 记录）等重活；它只负责「到点 → 原子认领 → 交给既有回合管线」，重活全部由既有回合 worker 承担。

## Git 分支约束

项目 `AGENTS.md` 规定日常代码拉取与提交只在 `dev` 分支进行。开发 Agent 开始修改前必须确认当前分支；若不是 `dev`，不得自行在其他分支提交，也不得擅自合并到 `master`。

实施过程必须使用持久化实施计划并按 01 规格第 14 节的阶段推进，持续更新 `待开发/星轨自动化任务/实施进度.md`。阶段只用于降低实施风险，不代表分版交付，也不能用于推迟规格内功能。
