# 星瑶 GUI + CLI 完整 Git 管理设计规格

状态：待开发
日期：2026-09-03
适用项目：Y-CODE / 星瑶

## 1. 背景

星瑶已经具备：

- GUI 与 CLI 双端；
- 会话关联工作目录；
- 文件树与 Diff 展示；
- `execute_command` 及现有权限系统；
- 基础 `/worktree` 命令和 `core/worktree.py`；
- 多会话并行与线程本地工作目录。

目前用户可以让模型通过 `execute_command` 执行 Git，也可以手工打开终端执行 Git，但缺少统一、可视化、可直接操作的 Git 工作台。现有 `core/worktree.py` 返回面向人的文本，不能作为完整 GUI/CLI Git 状态模型。

## 2. 目标

构建一个两端共用的专业 Git 工作台：

- 始终显示当前真实仓库、分支和工作区状态；
- 支持日常及高级 Git 工作流；
- GUI 使用点击、表单、Diff 与提交图交互；
- CLI 使用状态栏、全屏管理器与明确的 `/git` 子命令；
- 支持通过 Worktree 同时处理多个分支；
- 能识别其他终端、IDE 或 Git 客户端产生的外部变化；
- 以 Git 仓库为唯一事实源，不持久化一份可能过期的镜像状态；
- 与现有模型工具和权限体系兼容，不改变模型侧 Git 使用方式。

## 3. 非目标

以下能力不纳入本 Git 工作台：

- Git LFS 管理；
- Submodule 的创建、更新和删除；
- Bisect；
- Hooks 编辑器；
- GPG/SSH 私钥、证书和密码管理；
- `filter-branch`、`gc`、`fsck` 修复等底层仓库维护；
- GitHub、Gitee 等平台的 PR、Issue、Review、分支保护管理；
- 任意 Git 参数透传入口。

遇到 Submodule 或 LFS 状态时必须正确显示并标记为“不由 Git 工作台管理”，不能误当普通文件修改。

## 4. 核心产品原则

### 4.1 真实状态原则

分支属于真实 Worktree，不属于聊天会话。同一工作目录的全部会话必须显示同一个真实分支。切换分支必须真正执行 Git，并在成功后刷新文件树与状态。

### 4.2 并行分支原则

同一目录不能同时处于多个分支。并行分支必须通过 Git Worktree 实现：

```text
E:\project                  -> dev
E:\project-worktrees\login -> feature/login
E:\project-worktrees\fix   -> fix/payment
```

不同 Worktree 可以并行编辑、测试和提交。Git 的共享引用、对象库、Remote 与 Worktree 占用约束仍必须遵守。

### 4.3 显式失败原则

- 不自动 Stash；
- 不自动强制切换；
- 不自动解决冲突；
- 不自动改用另一种 Pull 策略；
- 不自动重试网络操作；
- 不删除 Git 锁文件；
- Git 版本不支持某能力时明确报错，不用旧命令静默模拟；
- Patch 预检失败时不尝试模糊应用或三方补救。

### 4.4 模型兼容原则

用户在对话中说“提交”“切换分支”“拉取”等，模型仍通过现有 `execute_command` 执行，并继续接受现有权限拦截。`GitService` 只供 GUI 与 CLI 的手动功能调用，不注册新的模型工具，不改变 system prompt 和 tools schema。

### 4.5 仓库信任原则

“通过参数数组调用 Git”只能防止参数被 Shell 重新解释，不能阻止 Git 自身调用 Hooks、Filter、fsmonitor Hook、外部 Diff/Textconv、Credential Helper 或 Remote Helper。手动 Git 工作台必须增加独立的仓库信任策略：

- 信任对象绑定规范化的 Common Git Dir、Worktree 和安全相关配置指纹；
- Hooks、`core.hooksPath`、`core.fsmonitor` 可执行路径、`filter.*`、`diff.external`、Textconv、带 `!` 的 Credential Helper 和外部 Remote Helper 发生变化时，已有信任失效；
- 未信任仓库只允许经过硬化的元数据查询；
- 可能触发仓库脚本、过滤器或外部程序的操作在执行前必须展示来源并要求“允许本次”或“信任此仓库”；
- 信任不能绕过灾难操作拒绝、沙盒边界、参数校验、快照校验或高风险确认；
- 不支持的外部执行机制明确拒绝，用户仍可在自己的终端中手工处理。

“允许本次”只保存在当前任务内存中；“信任此仓库”持久化到 `YCODE_DATA_DIR/git_trust.json`，未设置 `YCODE_DATA_DIR` 时使用 `~/.ycode/git_trust.json`。文件必须原子写入，只保存规范化仓库标识、安全配置指纹、确认时间和信任范围，不保存凭据或 Hook 内容。任一安全配置指纹变化都使该记录失效并重新询问。

仓库信任与模型权限是两套不同边界：前者约束手动 Git 工作台可能间接执行的程序，后者继续约束模型调用 `execute_command`。

## 5. 完整功能范围

### 5.1 仓库发现与能力检测

- 检测 Git 是否安装、Git 版本与能力；
- 完整 Git 工作台最低支持 Git 2.36.0；版本低于基线时工作台明确不可用，并显示检测版本、最低版本和升级指引，不调用旧命令模拟；
- 基线之上仍维护逐操作能力表，启动时通过版本与安全探测确认能力，不能假设发行版回移植行为；
- 从工作区子目录解析真实仓库根目录；
- 解析 Worktree Git 目录与 Common Git 目录；
- 识别普通仓库、Worktree、Bare Repository、Detached HEAD、Unborn Branch；
- 一个工作区包含多个已知仓库时提供仓库选择器；
- 不递归扫描整块磁盘，只管理用户打开或明确加入的仓库；
- 非 Git 目录支持 `git init`，允许指定初始分支名；
- 支持 Clone，并提供目标目录、分支、完整/浅克隆选择、进度与取消。

Clone 和 Remote URL 仅允许 `https`、`http`、`ssh`、SCP 风格 SSH 和用户明确选择的本地路径；匿名 `git` 协议默认拒绝并说明其无传输加密，`ext` 和未知 Remote Helper 一律拒绝。`file`/本地路径必须经过沙盒与路径边界检查。仓库安全查询必须禁用外部 Diff/Textconv 并覆盖可执行 fsmonitor 配置；可能触发 Hook、Filter 或 Helper 的操作进入仓库信任流程。

### 5.2 状态总览

- 当前仓库和 Worktree 路径；
- 当前分支或 Detached HEAD；
- HEAD OID；
- 上游分支；
- ahead/behind；
- 暂存、未暂存、未跟踪、忽略、冲突文件数量；
- Stash 数量；
- Merge、Rebase、Cherry-pick、Revert 等进行中状态；
- Remote 摘要与星瑶本进程实际观察到的最近一次成功 Fetch 时间；该时间仅作界面提示，不作为仓库事实或同步判断依据；
- Git 身份是否可用于提交；
- 外部状态变化提示。

状态读取使用 Git 官方稳定的 Porcelain v2 与 NUL 分隔格式。文件名不得依赖本地化文本解析或引号转义猜测。

### 5.3 变更、Diff 与暂存区

- 分组显示冲突、已暂存、未暂存、未跟踪和忽略文件；
- 支持新增、修改、删除、重命名、复制、类型变化、执行位变化和二进制文件；
- 查看工作区 Diff、暂存区 Diff和任意两个引用之间的 Diff；
- 单栏与并排 Diff；
- 按文件暂存、取消暂存；
- 按 Hunk 或选中行暂存、取消暂存；
- Stage All；
- Restore 文件或 Hunk；
- Clean 未跟踪文件前先使用 dry-run 显示准确清单；
- 大 Diff 分页或按需加载，超过限制必须明确提示截断；
- 二进制文件只显示元数据和可用预览，不伪造文本 Diff。

Hunk 操作必须从当前快照生成精确 Patch，先执行 `git apply --check` 或等价预检，再应用。快照过期或上下文不匹配时直接拒绝并刷新。

### 5.4 提交

- 提交已暂存内容；
- 提交信息标题和正文；
- Amend 最近一次提交；
- Undo 最近一次本地提交，可选择保留修改或保留暂存状态；
- 显示作者、提交者、时间、父提交和签名状态；
- 用户已经配置签名环境时允许签名提交；
- Git 用户名或邮箱缺失时阻止提交并给出仓库级/全局设置指引；
- 禁止把未暂存内容暗中加入提交；
- 提交前显示准确的已暂存文件和 Diff 摘要。

### 5.5 分支

- 本地与远程分支列表、搜索、最近使用；
- 显示当前分支、默认分支、上游、ahead/behind、是否被 Worktree 占用；
- 从分支、标签或提交创建分支；
- 仅创建分支，或创建后真实切换；
- 切换本地分支；
- 从远程分支创建跟踪分支；
- 重命名本地分支；
- 设置或取消上游；
- 安全删除本地分支；
- 删除远程分支；
- 从指定提交进入 Detached HEAD，并提供“从此处创建分支”出口；
- 比较任意两个分支、标签或提交；
- 以 Merge Base 为基线查看当前分支相对目标分支的真实改动。

分支名必须由 `git check-ref-format --branch` 校验。不得用自行维护的正则替代 Git 的规则。

### 5.6 分支切换硬规则

星瑶发起分支切换前必须重新获取状态。存在下列任一情况时一律拒绝：

- 已暂存修改；
- 未暂存修改；
- 未跟踪文件；
- 未解决冲突；
- 进行中的 Merge、Rebase、Cherry-pick 或 Revert；
- 目标分支被其他 Worktree 占用；
- 当前界面快照已经过期。

界面可以提示用户先提交或显式执行 Stash，但不得自动处理。外部工具成功切换分支后，星瑶尊重真实状态并刷新，不擅自切回。

### 5.7 Remote 与同步

- Remote 列表；
- 添加、修改、删除 Remote；
- Remote URL 凭据脱敏；
- Fetch、Fetch All、Prune；
- Pull；
- Push；
- 首次发布分支并设置上游；
- 推送单个或全部标签；
- 删除远程分支或标签；
- 显示 incoming/outgoing 提交并允许先审阅；
- 网络操作展示进度、支持取消和明确超时；
- 不保存密码、Token 或私钥，认证交给系统 Git Credential Manager；
- 子进程不得等待不可见的终端输入。

Pull 默认只允许 Fast-forward。无法 Fast-forward 时停止，并要求用户明确选择 Merge 或 Rebase。Force Push 不提供普通 `--force`，只允许在展示影响范围并二次确认后使用 `--force-with-lease`。

### 5.8 Stash

- 创建命名 Stash；
- 明确选择是否包含未跟踪文件；
- Stash 列表、详情与 Diff；
- Apply、Pop、Drop；
- 从 Stash 创建新分支；
- 冲突时进入显式冲突状态，不自动恢复或重试；
- Drop 前二次确认。

### 5.9 提交历史与图

- 拓扑顺序的提交 DAG；
- 分支、Remote、Tag 标记；
- 分页加载；
- 按作者、时间、说明、路径筛选；
- 提交详情与提交 Diff；
- 文件历史；
- 跟踪重命名前历史；
- 单行 Blame；
- 查看某次提交中的文件内容；
- 复制完整或短 Hash；
- 从任意提交创建分支或标签；
- 比较任意两个提交。

提交图必须根据父提交关系计算，不解析面向终端的 ASCII `--graph` 文本。

### 5.10 Merge、Rebase 与冲突

- Merge、Fast-forward、No-ff；
- Rebase 当前分支到目标引用；
- Interactive Rebase 计划编辑：Pick、Reword、Squash、Fixup、Drop、Reorder；
- Cherry-pick 一个或多个提交；
- Revert 一个或多个提交；
- 所有适用操作提供 Continue、Skip、Abort；
- 操作前展示待引入、待改写或待删除的提交；
- 已发布历史发生改写时显示高风险警告。

冲突界面必须支持：

- 冲突文件列表与冲突类型；
- Base、Current/Ours、Incoming/Theirs 和 Result；
- 接受 Current、Incoming 或 Both；
- 手工编辑 Result；
- 二进制冲突选择一侧；
- 未解决计数；
- 全部解决后显式标记并 Continue；
- Abort 恢复到 Git 定义的操作前状态。

不得用 AI 结果自动覆盖冲突文件。AI 只能给出建议，由用户确认后再通过正常编辑流程落盘。

### 5.11 历史恢复

- Reflog 列表；
- 查看 Reset、Rebase、分支切换等历史位置；
- 从 Reflog 项创建恢复分支；
- 恢复误删分支；
- Reset Soft、Mixed、Hard；
- Revert 作为不改写历史的首选撤销方式；
- Hard Reset 前展示将丢失的提交和工作区内容，并要求输入目标分支名或短 Hash 二次确认。

必须明确告知：Reflog 不能恢复被 Restore 或 Clean 删除且从未提交的文件。

### 5.12 Tag

- 本地与远程 Tag 列表、搜索；
- 创建轻量标签和附注标签；
- 用户已配置签名环境时允许签名标签；
- 推送标签；
- 删除本地或远程标签；
- 查看标签目标与说明；
- 删除和远程变更二次确认。

### 5.13 `.gitignore` 与 Patch

- 查看忽略规则来源；
- 忽略当前文件、同扩展名或用户输入的项目规则；
- 编辑项目 `.gitignore`；
- 不自动修改全局 Ignore；
- 将工作区、暂存区或提交导出为 Patch；
- Apply Patch 前检查目标仓库、路径和上下文；
- Patch 应用失败时明确失败，不自动三方合并。

### 5.14 Worktree

- 列表、创建、打开、移动/重命名、移除、Prune；
- 从已有分支打开新 Worktree；
- 创建新分支并在新 Worktree 打开；
- 自动加入星瑶项目分组；
- 创建或切换到对应会话；
- 状态栏显示分支与 Worktree 标识；
- 移除前检查未提交内容和运行中的任务；
- 正被 Worktree 使用的分支禁止删除；
- 不强制移除脏 Worktree，除非经过高风险确认。

默认 Worktree 根目录使用配置项 `git_worktree_root`。未配置时不自行猜测或在仓库内部创建目录，而是在首次创建时要求用户选择；选择结果按用户配置持久化。创建路径规则：

- 目标必须是规范化后的绝对路径；
- 禁止仓库根目录本身、任何 Git Dir/Common Git Dir 内部和已有非空目录；
- 分支名只用于建议目录名，必须经过确定性安全编码，不能直接拼接为路径；
- 路径冲突时明确失败并要求用户重新选择，不自动追加随机后缀；
- 沙盒外路径继续遵守现有沙盒授权；
- GUI、CLI 与现有 `/worktree` 使用同一套路径校验。

现有 `core/worktree.py` 的用户可见行为需保持兼容，但实现应迁移到共享安全执行与结构化模型，避免维持两套 Git 逻辑。

### 5.15 星瑶 AI 辅助入口

Git 面板可以提供以下显式按钮：

- 根据已暂存 Diff 生成提交说明；
- 提交前审查暂存内容；
- 解释提交或 Diff；
- 总结 incoming/outgoing 提交；
- 分析冲突并给出解决建议。

这些按钮只创建用户可见的普通星瑶对话消息，不允许注入隐藏 System Message、修改 Prompt Ledger 或直接把 Diff 塞入稳定前缀。固定流程：

1. 界面展示即将请求 AI 的用途、仓库和范围；
2. 用户确认后发送可见模板消息，例如“请审查当前仓库已暂存的修改并生成提交说明”；
3. 模型按现有权限使用 `execute_command` 读取限定范围的暂存 Diff；
4. 大 Diff、二进制内容和疑似凭据沿用现有大小限制与敏感信息策略，超限或命中敏感规则时明确停止并提示用户缩小范围；
5. AI 输出只是建议，Git 修改仍通过现有工具和权限流程完成。

不得让 AI 辅助按钮直接获得额外权限，也不得在用户不可见的请求中上传源码或 Diff。

## 6. 架构

```text
GUI GitPanel / History / Conflict ─┐
                                   ├── GitApplicationService
CLI /git Manager / Subcommands ────┘          │
                                              ├── GitRepositoryResolver
                                              ├── GitCapabilityService
                                              ├── GitQueryService
                                              ├── GitMutationService
                                              ├── GitPatchService
                                              ├── GitOperationCoordinator
                                              ├── GitRiskPolicy
                                              ├── GitRepositoryTrustPolicy
                                              ├── GitStateMonitor
                                              └── GitProcessRunner ── git executable
```

建议文件边界：

- `core/git/models.py`：不可变值对象、枚举和错误码；
- `core/git/runner.py`：唯一 Git 进程执行器；
- `core/git/repository.py`：仓库、Worktree 与能力解析；
- `core/git/query.py`：状态、分支、历史、Diff、Blame、Reflog 等只读查询；
- `core/git/mutation.py`：白名单写操作；
- `core/git/patch.py`：Hunk/行级 Patch 的生成、预检与应用；
- `core/git/coordinator.py`：锁、快照版本和运行命令协调；
- `core/git/risk.py`：风险分级、操作预览、一次性确认令牌与服务端校验；
- `core/git/trust.py`：仓库信任、安全相关配置指纹和外部执行策略；
- `core/git/monitor.py`：外部变化监控与失效通知；
- `core/git/service.py`：供 GUI/CLI 使用的应用服务；
- `core/worktree.py`：保留兼容门面，委托新服务；
- `core/git_cli.py` 或同等模块：CLI 全屏管理器和命令路由；
- `frontend/src/components/GitPanel.vue`：源代码管理主面板；
- `frontend/src/components/GitHistory.vue`：提交图与历史；
- `frontend/src/components/GitDiffView.vue`：Diff；
- `frontend/src/components/GitConflictResolver.vue`：三方冲突；
- `frontend/src/stores/gitStore.ts`：仅保存当前界面快照和加载状态；
- `gui_bridge.py`：窄接口与事件转发，不放 Git 业务逻辑。

如实现过程中发现文件职责过大，可以继续按上述边界拆分，但不能把所有功能堆进 `gui_bridge.py`、`main.py` 或单个超大 `git_service.py`。

## 7. 核心数据模型

### 7.1 RepositoryIdentity

- `workspace_path`
- `worktree_root`
- `git_dir`
- `common_git_dir`
- `is_bare`
- `is_linked_worktree`
- `git_version`
- `capabilities`

### 7.2 GitSnapshot

- `repository`
- `head_oid`
- `branch_name`
- `head_state`
- `upstream`
- `ahead`
- `behind`
- `operation_kind`
- `operation_phase`
- `changes`
- `conflicts`
- `stash_count`
- `identity_state`
- `worktree_version`
- `refs_version`

快照版本拆为两个作用域：

- `worktree_version`：对规范化 Repository Identity、HEAD OID、Index 校验材料、原始 `git status --porcelain=v2 -z --branch --show-stash` 字节、操作状态标记和冲突阶段数据计算 SHA-256；不读取或哈希工作区文件正文；
- `refs_version`：对 Common Git Dir 身份、目标 Ref 当前 OID、相关上游/Remote Ref OID、Packed Refs 版本材料和 Remote 配置安全摘要计算 SHA-256。

操作按影响范围携带一个或两个版本。前端不得自行计算；服务端在锁内重新计算并使用恒定格式比较。仅依赖 mtime、界面时间戳或递增内存计数均不合法。Monitor 事件只负责使快照失效，不能直接生成新版本。

## 8. Git 进程执行规则

- 使用参数数组启动 Git，不使用 Shell；
- 固定可执行文件和白名单子命令；
- 启动参数显式设置 `--no-optional-locks` 或等价安全配置，不继承会改变机器协议的 Alias；
- 路径参数前使用 `--` 终止选项解析；
- Ref 使用 Git 自身校验；
- 只读查询尽量使用 `GIT_OPTIONAL_LOCKS=0`；
- 需要稳定解析的命令使用机器格式和 NUL 分隔；
- 不解析本地化的面向人类输出作为成功协议；
- 状态等安全查询覆盖 `core.fsmonitor=false`；Diff/Log/Show 默认使用 `--no-ext-diff --no-textconv`，不执行仓库或全局配置的外部 Diff；
- `protocol.ext.allow=never`，未知 Remote Helper 默认拒绝；允许协议以规格 5.1 的白名单为准；
- 可能触发 Hook、Filter、Credential Helper 或其他外部程序的命令必须先经过 GitRepositoryTrustPolicy；不通过时拒绝，不自动添加 `--no-verify` 改变仓库语义；
- 标准输入默认关闭，避免 GUI 隐形等待；
- Remote URL、Header、Token 和凭据在日志与错误中脱敏；
- 网络操作可取消，取消时终止对应进程树；
- 本地变更操作只有在 Git 文档保证进程终止安全时才提供主动取消；若进程被终止、应用崩溃或 Hook/Filter 中断，结果必须标记为 `interrupted`，随后重新读取真实 Git 状态并只展示合法的 Continue/Skip/Abort，不宣称已自动回滚；
- 每个操作有明确超时，超时直接失败；
- 不自动重试；
- 保留必要的可诊断日志，但不记录敏感信息。

## 9. 并发与一致性

### 9.1 两级锁

- Worktree 锁：保护该 Worktree 的工作区和 Index 操作；
- Common Repository 锁：保护 Remote 配置、Fetch/Prune、Worktree 增删、跨引用拓扑操作等共享状态。

同时需要两把锁时必须采用固定获取顺序，避免死锁。不同 Worktree 的编辑、测试和可安全独立的 Git 操作允许并行；共享仓库操作串行。

### 9.2 与现有命令执行协调

星瑶现有多会话可以并行执行 `execute_command`，仅给 Git 面板加锁不够。需要新增 Workspace Process Registry：

- `execute_command`、GUI 内嵌终端和后台任务启动/结束时登记工作目录、前后台类型、是否长期运行和可识别风险类别；
- 不使用“存在任意进程就拒绝全部 Git 写操作”的全局规则，而是依据下表判断兼容性；
- 可安全识别的直接 `git ...` 命令接入 GitOperationCoordinator；
- 任意外部系统终端无法被星瑶锁住，因此写操作前仍必须执行快照校验，并尊重 Git 自身锁失败。

操作兼容矩阵：

| Git 操作类别 | 示例 | 同 Worktree 活动命令策略 |
|---|---|---|
| 只读 | status/diff/log/blame | 允许；读取后标注快照版本 |
| Index | stage/unstage/commit | 对可识别只读或长期监听服务允许，但必须在锁内重新校验 Index/快照；存在未知前台变更命令时拒绝 |
| Ref-only | 创建未切换分支、Tag | 对不修改仓库的长期服务允许；共享 Ref 操作持有相应锁和 `refs_version` |
| Worktree rewrite | switch/restore/clean/reset/stash apply/pop/merge/rebase/cherry-pick/revert | 同 Worktree 存在任何活动命令或后台服务时拒绝，并列出需要停止的任务 |
| Common repository | fetch/prune/remote/worktree add/remove | 持有 Common Repository 锁；与会修改共享配置或 Worktree 注册表的任务互斥 |

无法可靠分类的命令按“未知前台变更命令”处理。长期后台服务不会永久阻止 Stage/Commit，但会阻止分支切换和其他工作区重写操作。反向规则同样成立：Worktree rewrite 进行中时，不允许同 Worktree 启动新命令。

不得声称能绝对控制星瑶进程之外的 Git 客户端。

### 9.3 乐观并发

每个写请求必须携带其操作需要的 `worktree_version` 和/或 `refs_version`。执行步骤：

1. 解析真实仓库；
2. 获取所需锁；
3. 重新读取权威状态；
4. 比较对应作用域的快照版本；
5. 检查操作前置条件；
6. 执行单个白名单 Git 操作；
7. 重新读取结果；
8. 发布状态失效与刷新事件；
9. 释放锁。

状态过期时拒绝执行，前端刷新后由用户重新确认。已经生成的风险确认令牌随快照过期立即失效。

## 10. 外部 Git 状态同步

增加 `GitStateMonitor`，按 Worktree 建立监控订阅：

- 通过 Git 解析实际 Git Dir/Common Git Dir，不能假设 `.git` 一定是目录；
- 监控 HEAD、当前引用、Index、Packed Refs、Remote Refs 与操作状态文件变化；
- 监控工作区文件变化，用于失效变更列表与文件树；
- 文件事件只触发失效，最终分支和状态必须重新调用 Git 获取；
- 大量事件需要 Debounce/Coalesce；
- 应用窗口重新聚焦时立即做一次权威校验；
- 后台执行轻量 HEAD/OID 一致性校验，发现变化才加载完整状态；
- 自身 Git 操作完成后合并成一次刷新，避免重复闪烁；
- 同一 Worktree 的全部会话同时接收更新；
- 其他 Worktree 独立刷新。

目标：应用活跃时外部分支切换通常在 1 秒内显示；窗口重新聚焦时立即校准。监控线程不得直接更新 prompt_toolkit 或 pywebview，必须投递到各自 UI 主线程/既有事件队列。

## 13. 权限与确认策略

用户点击按钮或输入 `/git` 子命令属于明确的手动操作，不经过模型权限 Broker，但必须经过服务端 `GitRiskPolicy`。不同风险采用不同确认：

- 只读：直接执行；
- 可逆本地操作：用户触发后执行，并显示结果；
- 远程写操作：执行前显示 Remote、源引用、目标引用和提交范围；
- 历史改写：高风险确认；
- 不可恢复操作：二次确认，并要求输入分支名或短 Hash；
- Force Push：只允许 `--force-with-lease`，高风险确认；
- 模型通过 `execute_command` 发起的 Git：继续使用现有权限策略。

高风险操作包括但不限于：Restore 未提交内容、Clean、Drop Stash、Hard Reset、强制删除未合并分支、删除远程分支/Tag、删除 Remote、强制移除脏 Worktree、改写已发布历史。

高风险操作使用两段式协议：

1. GUI/CLI 请求 `preview`，服务端在锁内读取真实状态并返回结构化影响范围、风险级别、所需确认文本、快照版本和短时有效的一次性 `confirmation_token`；
2. 用户完成确认后提交原始结构化参数和令牌；服务端验证调用会话、Repository Identity、参数摘要、快照版本、有效期和未使用状态，全部一致才执行。

确认令牌由进程内随机密钥进行认证，有效期 60 秒且只能使用一次，不能由前端构造或复用。前端弹窗只是交互层，删掉弹窗、直接调用 pywebview 桥或重放旧请求都不能绕过服务端验证。普通操作也必须由服务端重新检查风险等级，客户端无权自行降级。

## 14. 操作状态机

操作类型、阶段和冲突是三个正交维度，不能把 `conflicted` 与 Rebase/Merge 设成互斥顶层状态：

```text
operation_kind:
  idle | merge | rebase | cherry_pick | revert | unsupported_external

operation_phase:
  none | running | paused_for_conflict | paused_for_edit | interrupted

conflicts:
  [] | [ConflictEntry...]
```

例如 Rebase 冲突表示 `operation_kind=rebase`、`operation_phase=paused_for_conflict` 且 `conflicts` 非空；Rebase 停在 Edit 步骤时可以没有冲突。每种组合只开放 Git 实际允许的 Continue、Skip、Abort 或编辑动作，非法状态转换显式失败。

Bisect、Am、外部 Sequencer 或未来 Git 状态即使不在工作台功能范围，也必须识别为 `unsupported_external`，显示可诊断说明并阻止不兼容写操作；不得误判为 Idle。崩溃、取消或应用重启后不自动继续操作，重新读取 Git 状态并展示真实合法动作。

## 15. 性能要求

- 状态查询不得读取文件正文；

## 18. 验收标准

以下条件必须同时满足：

1. GUI 与 CLI 显示同一真实状态；
2. 星瑶界面切换分支会真实改变磁盘代码；
3. 脏工作区切换被严格拒绝；
4. 外部 Git 客户端切换后星瑶自动更新；
5. 同一 Worktree 多会话同步；
6. 不同 Worktree 可以并行分支工作；
7. 所有写操作使用白名单参数数组；
8. 快照过期不会执行旧操作；
9. Merge/Rebase 等状态与冲突正交显示，可恢复识别但不自动重放；
10. 不可逆操作均有服务端影响预览和不可重放的一次性确认；
11. 模型仍通过 `execute_command` 使用 Git；
12. 凭据不进入界面、日志或错误；
13. 未信任仓库不能借 Hooks、Filter、外部 Diff、fsmonitor 或 Remote Helper 绕过安全边界；
14. 适用测试通过；
15. `README.md` 与 `/help` 更新；
16. 无静默降级、隐式 Stash、自动强制或自动冲突解决。

详细人工场景见 [03-验收清单.md](03-验收清单.md)。
