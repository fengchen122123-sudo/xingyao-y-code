# 星瑶 Git 管理工作包

状态：待开发
设计日期：2026-09-03
目标：为星瑶 GUI 与 CLI 增加完整的手动 Git 工作台，同时保持模型侧现有 `execute_command` 流程不变。

## 文件说明

- [01-完整设计规格.md](01-完整设计规格.md)：功能、架构、安全、并发、界面、异常处理与测试设计，是实现的唯一需求基线。
- [02-Agent开发提示词.md](02-Agent开发提示词.md)：可直接复制给开发、评审和验收 Agent 的提示词。
- [03-验收清单.md](03-验收清单.md)：完成定义和人工验收场景。

## 使用顺序

1. 将“主开发 Agent 提示词”交给负责实现的 Agent。
2. 开发完成后，将“代码评审 Agent 提示词”交给独立评审 Agent。
3. 修复评审发现后，使用“最终验收 Agent 提示词”执行全量验证。
4. 只有 [03-验收清单.md](03-验收清单.md) 中所有适用项目通过，才视为完成。

## 不可改变的产品决定

1. GUI 与 CLI 共用同一个结构化 Git 服务层，不复制业务逻辑。
2. 用户在界面中进行的 Git 操作是真实仓库操作，不是仅修改显示状态。
3. 有任何未提交、已暂存或未跟踪内容时，星瑶发起的分支切换必须拒绝；不自动 Stash、不强制切换。
4. 同一个 Worktree 只能显示其真实分支；并行分支通过独立 Git Worktree 实现。
5. 外部终端或其他 Git 客户端改变仓库后，星瑶必须自动识别并刷新。
6. 模型在对话中执行 Git 继续走现有 `execute_command` 与权限流程，不新增重复的模型工具。
7. 不做 MVP 或分版交付；按完整设计实现。实现过程可以拆分提交，但最终交付必须覆盖全部范围。
8. 遇到错误显式失败，禁止自动降级、静默重试、自动强制执行或隐式补救。
9. Git 参数数组不能消除 Hooks、Filter、外部 Diff、fsmonitor 和 Remote Helper 的执行风险；手动 Git 工作台必须有独立的仓库信任策略。
10. 高风险确认必须由后端验证一次性确认令牌，不能只依赖前端弹窗。

## Git 分支约束

项目 `AGENTS.md` 规定日常代码拉取与提交只在 `dev` 分支进行。开发 Agent 开始修改前必须确认当前分支；若不是 `dev`，不得自行在其他分支提交，也不得擅自合并到 `master`。

由于完整范围较大，开发过程必须使用持久化实施计划和阶段检查点。阶段只用于降低实施风险，不代表分版交付，也不能用于推迟规格内功能。
