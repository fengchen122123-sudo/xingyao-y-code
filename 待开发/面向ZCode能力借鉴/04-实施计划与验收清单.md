## 一、总览

| 项 | 文档 | 依赖 | 风险 | 收益 | 建议顺序 |
|---|---|---|---|---|---|
| **工具调度拓扑化** | [03](03-工具调度拓扑化设计规格.md) | 无 | 中 | 基础设施（直接收益有限） | 可随时 |
| **上下文注入分类治理** | [02](02-上下文注入分类治理设计规格.md) | 无 | **高** | 守护缓存优势 | 第二 |
| **Hooks 体系** | [01](01-Hooks体系设计规格.md) | 02（注入通道） | 中 | 可扩展性（价值最大） | 第三 |

**推荐实施顺序**：03 → 02 → 01

理由：

- **03 最独立**，且能产出有价值资产（对拍测试 + 契约完整性），随时可做；
- **02 优先于 01**，因为 01 的上下文注入需要 02 的通道；
- **01 风险收益比最好**，但依赖 02。

**若 02 因高风险被推迟**：01 可以用临时通道实现（内联 user 消息），后续迁移。

## 四、人工验收场景

### 场景 1：Hook 拦截危险命令

1. 配置项目级 `PreToolUse` hook，matcher `execute_command`，命令为"检测到 rm -rf 则返回 deny"。
2. 信任该 hook。
3. 让星瑶执行 `rm -rf /tmp/x`。
4. **期望**：工具被拒绝，模型收到拒绝原因，用户看到提示。

### 场景 2：Hook 自动格式化

1. 配置 `PostToolUse` hook，matcher `write_file|edit_file`，命令为调用 formatter。
2. 让星瑶写一个格式混乱的 Python 文件。
3. **期望**：文件写完后被自动格式化。

### 场景 3：Stop 续跑

1. 配置 `Stop` hook，检查"任务是否真的完成"，未完成返回 `continue: true`。
2. 让星瑶做一个需要多步的任务，故意让它提前想收尾。
3. **期望**：回合不结束，星瑶继续执行。
4. 让 hook 永远返回 continue。
5. **期望**：5 次后强制结束并提示用户。

### 场景 4：信任机制

1. 放一个项目级 hook 配置。
2. **期望**：首次加载弹出确认卡片，未确认不执行。
3. 确认后执行。
4. 修改 hook 的 `command`。
5. **期望**：信任失效，重新弹确认。
6. 只修改 `status_message`。
7. **期望**：信任**不**失效（纯展示字段）。

### 场景 5：权限不可提权

1. 用户档位为 `plan`（只读）。
2. 配置 `PreToolUse` hook 返回 `permission_decision: "allow"`。
3. 让星瑶尝试写文件。
4. **期望**：**仍被拒绝**（hook 不能突破档位）。

### 场景 6：缓存亲和

1. 改 02 的全部代码。
2. 运行 `pytest tests/test_prompt_byte_stability.py`。
3. **期望**：全部通过，且该文件未被修改。
4. 开一轮对话，检查 `system_sha256` 跨轮稳定。

### 场景 7：调度等价

1. 让星瑶一次发起 3 个只读工具 + 1 个写工具。
2. 对比改造前后的批次分组（可用日志）。
3. **期望**：完全一致。

## 七、决策点（需用户确认）

1. **三项是否全做？**
   - 全做：按 03 → 02 → 01 顺序
   - 只做两项：建议 02 + 01（放弃 03，因其实质收益有限）
   - 只做一项：建议 01（Hooks，价值最大）

2. **02 的高风险是否接受？**
   - 若担心破坏缓存，可只做 B1~B3（建立描述符 + 登记，不接管渲染），把收益延后
   - 这样风险归零，但收益也归零（只是为未来铺路）

3. **01 的 v1 事件范围是否认可？**
   - 当前设计：4 个事件（SessionStart / PreToolUse / PostToolUse / Stop）
   - 是否补充 `PermissionRequest` / `PostToolUseFailure`？

4. **项目级 hook 是否默认禁用完整 tool_input？**
   - 当前设计：默认禁用（防数据窃取）
   - 若用户认为过于保守，可改为配置项控制

5. **03 是否值得做？**
   - 若认为"直接收益有限"不可接受，可跳过
