## 1. 背景与目标

### 1.1 星瑶现状

**已有的调度实现**（`core/harness/tool_pipeline.py:255`）：

```python
def group_tool_batches(tool_calls: list[dict], registry: ToolRegistry) -> tuple[ToolBatch, ...]:
    batches: list[ToolBatch] = []
    for tool_call in tool_calls:
        name = tool_call["function"]["name"]
        try:
            parallel = bool(registry.get(name).parallel_safe)
        except KeyError:
            parallel = False
        if batches and batches[-1].parallel and parallel:
            previous = batches[-1]
            batches[-1] = ToolBatch(True, (*previous.calls, tool_call))
        else:
            batches.append(ToolBatch(parallel, (tool_call,)))
    return tuple(batches)
```

**逻辑**：相邻的 `parallel_safe` 调用合并成一批并行，遇到非 `parallel_safe` 断开。

**已有的配套设施（比预想成熟）**：

| 设施 | 位置 | 说明 |
|---|---|---|
| `ToolSpec.parallel_safe` | `core/tool_protocol.py` | 已有 11 个工具标记为 True |
| 6 个安全元数据字段 | `core/tool_protocol.py` | `read_only` / `mutates_files` / `requires_permission` / `cancellable` / `parallel_safe` / `activity_description` |
| 并发上限 | `tool_pipeline.py:326` | `BoundedSemaphore(max_parallel=4)` |
| 结果保序 | `tool_pipeline.py:294` | "Execute adjacent safe tools concurrently and **return model-ordered records**" |
| 重复调用守卫 | `tool_pipeline.py:176` | `RepeatCallGuard` |
| 权限/计划/租约校验 | `ToolPipeline.execute_decoded` | 在批次执行中被逐个调用 |

**这说明星瑶的并发执行框架已经很完整，缺的只是"批次规划算法"。**

### 1.2 问题

`[read_a, write_b, read_c, read_d]` 会被切成：

```
[[read_a], [write_b], [read_c, read_d]]
```

但实际上 `read_c` / `read_d` 与 `read_a` 之间**没有任何依赖**，完全可以并行。当前实现浪费了并行机会。

### 1.3 目标

- 引入**依赖声明**与**拓扑分层**
- 对**无依赖声明**的输入，输出必须与现有实现**完全一致**（零回归）
- 支持显式声明的依赖关系（为未来的"读后写"等场景铺路）

### 1.4 非目标（重要）

**v1 绝不实现"跨位置自动合并"。**

理由：模型输出的工具调用顺序**隐含了意图顺序**。擅自重排可能改变语义：

- `write_a → read_a`：模型可能明确要"先写后读"验证；
- `edit_a → test_a`：必须先改再测。

ZCode 的实现有元数据支撑（`destructive` / `concurrentSafe`）且无此顾虑，但星瑶的工具多数没有这些细粒度声明。**保守起见，v1 只做"不改变相对顺序的优化"**。

**自动拓扑重排列为二期，需单独评估。**

## 2. 核心设计

### 2.1 扩展 ToolSpec

```python
# core/tool_protocol.py

@dataclass(frozen=True)
class ToolSpec:
    # ... 现有 6 个字段保持不变 ...

    # 新增：声明本工具调用依赖哪些调用（按调用序号索引）。
    # None = 无依赖声明，落回「同层可并行」的旧语义。
    # 空元组 () = 显式声明「无依赖」（与 None 同效，但语义更清晰）。
    depends_on: tuple[int, ...] | None = None

    # 新增：副作用范围，供调度与权限系统读取。
    # none | workspace | git | network | system
    side_effect_scope: str = "none"
```

**字段追加位置**：必须追加到 `ToolSpec` 字段列表**末尾**（dataclass 的默认值约束），且全量搜索确认无以下写法：

- 位置参数构造：`ToolSpec("name", "desc", schema, fn, True, False, ...)`
- 下标访问：`args[6]` / `spec[7]`

### 2.2 拓扑分层算法

```python
# core/harness/tool_scheduler.py

def plan_tool_batches(
    tool_calls: list[dict],
    registry: ToolRegistry,
    *,
    max_concurrency: int = 4,
) -> tuple[ToolBatch, ...]:
    """按依赖拓扑分层 + 并行安全元数据分组。

    ===== 兼容性契约（最高优先级）=====
    对「所有 depends_on 均为 None」的输入，本函数输出必须与
    group_tool_batches() 逐批、逐项、逐顺序完全一致。

    ===== 算法 =====
    1. 计算每个调用的层号：
       - depends_on 为 None → 层号 0
       - 否则 → max(依赖调用层号) + 1
       （依赖序号必须小于自身序号，否则抛错——不支持前向依赖）

    2. 按层号升序处理，每层内：
       - 遍历该层的调用（保持原始相对顺序）
       - parallel_safe=True 的累积到当前并行批
       - parallel_safe=False 的：先 flush 当前并行批，再单独成批
       - 并行批达到 max_concurrency 时 flush

    3. 跨层不合并：层 N 的所有批次必须在层 N+1 之前。

    ===== 校验 =====
    - 依赖成环 → 抛 CoreError
    - 依赖序号指向不存在的调用 → 抛 CoreError
    - 同一批内存在依赖关系 → 抛 CoreError（防御）
    """
```

### 2.3 兼容性证明

**关键洞察**：当所有 `depends_on` 均为 `None` 时，所有调用都在**层 0**。此时算法退化为：

```
层 0 内按原始顺序遍历，parallel_safe 相邻合并、非 parallel_safe 切开
```

这**正好等于**现有 `group_tool_batches()` 的行为。

**形式化说明**：

| 输入 | 旧实现 | 新实现（全 None） |
|---|---|---|
| `[r1, r2]` | `[[r1,r2]]` | 层0 → `[[r1,r2]]` ✓ |
| `[r1, w1, r2]` | `[[r1],[w1],[r2]]` | 层0 → `[[r1],[w1],[r2]]` ✓ |
| `[r1, w1, r2, r3]` | `[[r1],[w1],[r2,r3]]` | 层0 → `[[r1],[w1],[r2,r3]]` ✓ |
| `[w1, r1, r2]` | `[[w1],[r1,r2]]` | 层0 → `[[w1],[r1,r2]]` ✓ |

**结论**：无需特判分支，算法天然兼容。但**仍必须写对拍测试**（见 4.1）。

### 2.4 批次数据结构

保持现有 `ToolBatch` 不变：

```python
@dataclass(frozen=True)
class ToolBatch:
    parallel: bool
    calls: tuple[dict, ...]
```

**不新增批次元数据**（如批次级别、依赖信息），因为：

- 执行层不需要它们；
- 增加字段会影响 `_PreparedToolBatch` 的构造与测试。

### 2.5 兼容包装

```python
# core/harness/tool_pipeline.py

def group_tool_batches(
    tool_calls: list[dict],
    registry: ToolRegistry,
) -> tuple[ToolBatch, ...]:
    """兼容包装：委托给 plan_tool_batches。

    保留本函数是为了：
      1. 现有调用方（ToolBatchExecutor.prepare）与测试无需改动；
      2. 出问题时可以快速切回旧实现（保留旧实现于 _legacy_group_tool_batches）。
    """
    return plan_tool_batches(tool_calls, registry)
```

**同时保留旧实现**为 `_legacy_group_tool_batches`（私有），仅用于对拍测试与紧急回退。

### 2.6 与执行层的接口

**不改动** `ToolBatchExecutor`。它继续接收 `tuple[ToolBatch, ...]`，只是生产批次的方式变了。

```
ToolBatchExecutor.prepare()
    ↓ 调用
plan_tool_batches()  ← 新
    ↓ 返回
tuple[ToolBatch, ...]  ← 格式不变
    ↓ 送入
execute_batch()  ← 不变
```

## 3. side_effect_scope 的补充

### 3.1 用途

`side_effect_scope` 在本设计中**不参与调度决策**（v1），但：

1. 为二期"自动拓扑重排"提供元数据基础；
2. 作为权限系统的补充信号（读取，不改变既有判定）；
3. 提升工具契约的自我描述性。

### 3.2 取值表

| scope | 工具 |
|---|---|
| `none` | read_file / list_directory / search_code / find_definition / glob_files / plan_read / manage_task / ask_user / get_weather |
| `network` | fetch_url / search_news / fetch_image / hunyuan_generate_image / tokenrhythm_* |
| `workspace` | write_file / edit_file / undo_turn / bash（受限）/ 自动化任务工具 |
| `system` | execute_command / computer_action |

**注意**：`execute_command` 归 `system` 而非 `workspace`，因为它可以执行任意命令；`computer_action` 同理。

### 3.3 MCP 工具

MCP 工具的 `side_effect_scope` 默认 `"system"`（保守——外部工具行为不可知）。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 调度顺序变化引发语义问题 | v1 不自动重排；对拍测试兜底 |
| 对拍测试通过但实际有差异（测试覆盖不足） | 随机用例 ≥1000，覆盖多种 parallel_safe 分布 |
| 拓扑排序性能 | 工具调用数通常 <20，O(n²) 完全可接受 |
| `depends_on` 无人使用（过度设计） | 承认：v1 主要价值在于**为二期铺路** + 契约完整性。若用户认为无必要，可只做 `side_effect_scope` 部分 |

---

## 7. 关于"值不值得做"的说明

**诚实评估**：

本项的**直接收益有限**——因为 v1 不自动重排，实际能合并的批次与旧实现相同。

**真正的价值在于**：

1. `side_effect_scope` 让工具契约更完整（为权限、审计、二期的自动调度铺路）；
2. 拓扑分层框架就位后，二期（自动重排）才有基础；
3. 对拍测试本身就是有价值的资产（守住调度语义）。

**如果用户只想做两项**，建议 **Hooks（01）+ 上下文注入（02）** 优先于本项。本项的价值更多是"补齐基础设施"，而非"立即可见的收益"。
