## 1. 背景与目标

### 1.1 星瑶现状（比预想成熟）

星瑶的上下文构建**已经实现了 ZCode System Reminder 的核心目标**，只是没有抽象成体系：

**已有机制**（`core/context_builder.py`，全文仅 190 行，但设计密度极高）：

| 函数 | 作用 | 缓存策略 |
|---|---|---|
| `build_stable_prompt` | 稳定前缀（base_prompt + `_DECISION_POLICY`） | **不计入每轮变化，安全用于 provider 前缀缓存** |
| `build_dynamic_prompt` | 每轮动态块（模型 / 权限模式 / 工作目录 / 计划快照） | **内容不变时不再重复注入**，保证跨轮 prefix 连续 |
| `build_time_note` | 每轮时间注记 | **内联到最后一条 user 消息**，不做独立 system 消息 |
| `without_system_messages` | 过滤历史中的旧 system 提示词 | 防止过期 system 污染 |

**最关键的已有设计**（`build_time_note` 的 docstring）：

> 不再作为独立 role=system 消息持久化——那样会使 `system_sha256` 每轮变化，导致 provider 侧前缀缓存从 system 块开始整体失效。内联到 user 消息后，`system_messages` 数组跨轮稳定，前缀缓存可覆盖整个对话历史。

**这说明星瑶已经踩过"独立 system 消息破坏缓存"的坑并修复了。**

### 1.2 那还缺什么

缺的是**统一的抽象层**。当前问题：

1. **注入点分散**：`build_stable_prompt` / `build_dynamic_prompt` / `build_time_note` / `build_stable_system_message`（`core/agent_service.py:179`）/ `input_parser.py` 的 `@` 引用，各自独立，没有统一描述符；
2. **没有"这条注入该不该进历史"的显式声明**：目前靠注释和人工约定；
3. **压缩时无法按类保留**：`core/memory_compressor.py` 不知道该保留哪些注入内容；
4. **新注入点无落点**：Hooks 的 `additional_context`、未来的 todo 提醒等，没有统一的接入方式。

### 1.3 目标

- 引入**注入描述符**，统一描述每条注入的「持久化策略」与「投递通道」
- 把现有全部注入点**逐一归类**
- 压缩时能按描述符决定保留/丢弃
- 为 Hooks 等新注入点提供统一落点
- **不改变任何现有注入的实际字节输出**（有 sha256 golden 守着）

### 1.4 非目标

- **不照搬 ZCode 的 27 种 source**（那是为多端产品设计的）
- **不引入 provider_hidden 概念**（星瑶是 GUI+CLI，没有 ZCode 那种多端渲染差异）
- **不重构 `build_stable_prompt` 的字节输出**（缓存契约红线）

## 2. 核心设计

### 2.1 注入描述符

只保留两个维度：

```python
# core/context_injection.py

class Persistence(str, Enum):
    """这条注入在会话历史中的存活策略。"""
    PREFIX = "prefix"          # 稳定前缀：每请求重注入，必须字节稳定（计入缓存前缀）
    PERSISTED = "persisted"    # 持久化：进历史，压缩时保留
    PER_REQUEST = "per_request"  # 仅当前请求：不落历史

class Channel(str, Enum):
    """这条注入的投递形态。"""
    SYSTEM = "system"          # 进 system prompt
    USER_REMINDER = "user_reminder"  # 作为 user 消息内联
    TOOL_RESULT = "tool_result"      # 内联进工具结果

@dataclass(frozen=True)
class InjectionSpec:
    source: str                # 来源标识，如 "context_prefix" / "time_note" / "hook_context"
    persistence: Persistence
    channel: Channel
    section_builder: Callable[[], str]   # 返回注入文本（空串表示不注入）
```

### 2.2 三类归分（把现有注入点逐一归类）

| 现有注入点 | 位置 | persistence | channel | 理由 |
|---|---|---|---|---|
| base_prompt + 决策规则 | `context_builder.build_stable_prompt` | `PREFIX` | `SYSTEM` | 已计入缓存前缀 |
| 记忆目录 / 技能目录 / 子 Agent 清单 | `agent_service.build_stable_system_message:179` | `PREFIX` | `SYSTEM` | 跨轮基本不变，并入稳定提示词 |
| 运行上下文块（模型/权限/目录/计划） | `context_builder.build_dynamic_prompt` | `PERSISTED` | `SYSTEM` | 内容不变时不重复注入，本身已是"半持久化" |
| 时间注记 | `context_builder.build_time_note` | `PER_REQUEST` | `USER_REMINDER` | 每轮必变，内联 user 消息 |
| `@` 文件引用 | `input_parser.py` | `PER_REQUEST` | `USER_REMINDER` | 单次引用 |
| 电脑操控说明 | `context_builder._build_computer_prompt_section` | `PERSISTED` | `SYSTEM` | 跟随动态块 |
| 按回合撤销纠正 | `context_builder` 的 `workspace_corrections` | `PERSISTED` | `SYSTEM` | 跟随动态块 |
| **Hooks 上下文注入（新增）** | `core/hooks/runner.py` | `PER_REQUEST` | `USER_REMINDER` | 不该污染历史 |
| **（未来）todo 提醒** | — | `PERSISTED` | `USER_REMINDER` | 语义是历史事实 |

### 2.3 关键判定原则

**`PREFIX` 的准入条件**（极严）：

1. 内容跨轮**完全不变**（不含时间、会话 ID、随机值）；
2. 位置固定在 messages 数组**最前面**；
3. 任何改动都要同步更新 `test_prompt_byte_stability.py` 的 sha256 golden。

**`PER_REQUEST` 的准入条件**（宽松）：

1. 内容每轮可能变（时间、动态状态）；
2. 或者是"一次性提醒"，语义上不属于历史事实。

**`PERSISTED` 的准入条件**：

1. 内容在会话内稳定（如"当前权限模式"）；
2. 或语义上是**历史事实**（如"用户在此时打断了"）；
3. 重复注入是幂等的（内容不变时不重复 append）。

### 2.4 为什么 `PER_REQUEST` 必须内联 user 消息

这是星瑶已有的正确做法，新注入点必须遵循：

- 若作为独立 `role=system` 消息 append → `system_sha256` 每轮变化 → 前缀缓存从 system 块开始整体失效；
- 内联到最后一条 user 消息 content 末尾 → `system_messages` 数组跨轮稳定 → 前缀缓存覆盖整个历史。

**代码依据**：`core/context_builder.py:build_time_note` 的 docstring 已记录此设计决策。

### 2.5 渲染管线

```python
# core/context_injection.py

class ContextInjectionRegistry:
    """注入点注册表。"""

    def register(self, spec: InjectionSpec) -> None:
        """注册一个注入点。重复 source 抛错。"""

    def build_prefix_sections(self) -> list[str]:
        """构建所有 PREFIX + SYSTEM 的注入（进稳定前缀）。"""

    def build_persisted_sections(self) -> list[str]:
        """构建所有 PERSISTED + SYSTEM 的注入（进动态块）。"""

    def build_per_request_reminders(self) -> list[str]:
        """构建所有 PER_REQUEST + USER_REMINDER 的注入（内联 user 消息）。"""

    def persisted_sources(self) -> frozenset[str]:
        """返回所有 PERSISTED 类注入的 source 名，供压缩保留逻辑使用。"""
```

### 2.6 与压缩的协同

`core/memory_compressor.py` 的压缩逻辑需要知道"哪些注入内容必须保留"。

**当前状态**：压缩时按消息位置/类型处理，没有"注入来源"的概念。

**改造后**：

```python
# 压缩时，标记了 PERSISTED 的注入内容保留。
# 注意：由于 PERSISTED + SYSTEM 的注入都在动态块里（一条 system 消息），
# 压缩只需保证该消息不被丢弃即可，粒度不需要到 source 级。
```

**关键**：星瑶的 `PERSISTED` 注入基本都合并进了 `build_dynamic_prompt` 的**单条 system 消息**，所以压缩保留的粒度就是"这条消息"。**不需要引入 ZCode 那种 source 级的保留白名单**——这是星瑶规模下更简洁的做法。

> **实现裁决注记（2026-09-21 复核）**：实测动态块承载形态为「内联于（最后一条）承载 user 消息」
> （`_append_context_suffix_to_last_user`），压缩锚点 `_persisted_context_anchor_index` 亦按 user 消息定位；
> 本节所称「单条 system 消息」以实际承载形态为准。字节与行为由 byte-stability / provider golden 全量守护。

## 3. 实施方式

### 3.1 原则：包装而非重写

**绝对不重写 `context_builder.py`**。原因：

- 它的字节输出被 `test_prompt_byte_stability.py` 的 sha256 golden 守着；
- 缓存亲和是最脆弱的契约，重写风险极高。

**做法**：

1. 新增 `core/context_injection.py`，定义描述符与注册表；
2. 把现有函数**注册进去**，但**不改它们的实现**；
3. 新增注入点走注册表；
4. 逐步把散落的注入点"登记"到注册表（登记不改变行为）。

### 3.2 分步实施

**步骤 1（无行为变化）**：建立 `InjectionSpec` 与注册表，把现有 7 个注入点**登记**进去（`section_builder` 直接指向现有函数）。此时注册表只是"一张清单"，不参与渲染。

**步骤 2（无行为变化）**：渲染管线接管——`build_stable_prompt` / `build_dynamic_prompt` / 时间注记的组装改为遍历注册表。**必须通过 sha256 golden 测试**。

**步骤 3（行为增强）**：Hooks 等新注入点接入。

**步骤 4（行为增强）**：压缩逻辑读取 `persisted_sources()`。

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 破坏缓存亲和 | 分 4 步走，每步都用 sha256 golden 验证；步骤 2 是关键风险点 |
| 重构引入行为漂移 | 步骤 1 只登记不渲染，步骤 2 才接管；两步之间的 diff 应极小 |
| 注册表成为新的复杂度源 | 严格限制描述符字段（只 2 个维度），不添加 |
| 与 Hooks 的耦合 | Hooks 通过注册表注入，不直接 append 消息 |

**最重要的风险提示**：这是三项改革里**风险最高**的一项。触碰的是缓存契约。若在实施中发现 golden 无法保持，应**立即回退**并重新评估——宁可放弃这层抽象，也不能破坏已经建立起来的缓存优势。

---

## 6. 与 ZCode 的差异说明

| 维度 | ZCode | 星瑶（本设计） |
|---|---|---|
| source 数量 | 27 种 | 7 种（现有注入点） |
| 维度 | 来源 × 通道 × 生命周期（3 维） | persistence × channel（2 维） |
| provider 可见性 | 有（provider_visible / hidden） | 无（GUI+CLI 无双端渲染差异） |
| 持久化保留 | source 级白名单 | 消息级（因星瑶 PERSISTED 注入合并进单条 system 消息） |
| mid-turn 上浮 | 有（复杂边界处理） | 无（星瑶无 mid-turn 注入需求） |

**结论**：星瑶的极简版覆盖了 ZCode 设计的**核心收益**（缓存亲和 + 历史洁净），但舍弃了为多端产品设计的复杂度。这是正确的规模匹配。
