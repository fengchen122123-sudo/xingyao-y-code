## 待用户确认的决策点

1. **是否四项全做**？
   - 建议：E3（几乎免费）→ E1+E2（核心）→ E4（收尾）
   - E5 明确不在范围内

2. **浏览器是否提供独立的 `list_elements` 动作**？
   - 本设计：**不提供**，由 `observe` 自动携带元素列表
   - 理由：减少动作数量 = 减少模型往返；且浏览器收集很快，不需要独立时机
   - 若用户希望与桌面完全对称，可改为独立动作（会稍增往返次数）

3. **元素 ref 的实现方式**：
   - 本设计：DOM 属性标记（`data-ycode-ref`）
   - 代价：修改页面 DOM（仅一个属性）
   - 收益：Playwright locator 的自动等待/可点击检查/滚动全部白送
   - 若用户不接受改 DOM，可改为「索引定位」（实现更简单但可靠性略低）

4. **只收集视口内元素是否可接受**？
   - 本设计：只收集视口内（视口外元素模型看不到也无法点击）
   - 需要视口外元素时，模型先滚动再 observe

5. **是否接受「有元素就不发截图」**？
   - 沿用现有投影逻辑（不新增例外）
   - 代价：模型看不到画面布局（只有元素列表）
   - 收益：token 大幅减少 + 对齐 ZCode 原则

## 已知限制（不在本工作包内）

| 限制 | 影响 | 后续 |
|---|---|---|
| 无 iframe 穿透 | 内嵌 iframe 的页面元素收集不到 | 二期 |
| 无 Shadow DOM 穿透 | 使用 Web Components 的页面可能收集不全 | 二期 |
| 桌面 UIA 覆盖有限 | 自绘应用（微信等）仍靠截图 | E5，另行立项 |
| 元素无图像信息 | 纯视觉判断（如「哪个按钮更醒目」）无法完成 | 有意的设计权衡 |
