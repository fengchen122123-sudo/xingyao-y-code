# 飞书集成到星瑶 · 设计规格与实施计划

> 设计日期：2026-09-29 ｜ 分支：`dev-feishu` ｜ 状态：实施中
> 参考实现：`D:\pxx\opencode-mobile`（Node/TS 插件，官方 SDK 长连接 + 卡片 2.0 交互）

## 一、背景

### 1.1 目标

星瑶目前的交互都发生在"电脑前"（桌面 GUI / 手机扫码）。目标是把飞书变成星瑶的远程入口：**在飞书里发消息 → 星瑶跑一轮 agent → 结果回发飞书**，并把 opencode-mobile 已实测的整套卡片交互（执行完成卡、权限审批卡、提问卡、待拍板收件箱、卡住提醒、指令面板、会话/模型/智能体切换）一并落地。

成功标准（用户可验收）：

| # | 验收标准 | 验证方式 |
|---|---|---|
| G1 | 飞书单聊发一言 → 星瑶跑完一轮 → 收到「执行完成卡」；桌面端同一会话可见这轮 | 真机 |
| G2 | 敏感操作触发「审批卡」→「批准一次 / 总是批准 / 拒绝」三按钮生效 | 真机逐个按钮 |
| G3 | 多个飞书会话绑定独立星瑶会话，互不串味 | 真机双会话 |
| G4 | 不配置飞书时星瑶零变化 | LAN 测试全绿、websockets 版本不变、GUI 正常启动 |
| G5 | 设置页可配置并测试连接；密钥加密存储、界面不回显明文 | 真机走设置页 |

### 1.2 现状对照

- 星瑶没有 IM/webhook 运行时集成（全仓检索仅 MCP 预设模板命中 `core/mcp_selector.py:70`）。
- 星瑶唯一外部通道范式 = 手机端 LAN 服务（`core/lan_server.py`），本次架构直接照抄其生命周期与事件广播模式。
- 消息转回合唯一入口 `AppBridge.send_user_message`（`gui_bridge.py:4541`），`turn_source` 白名单 `("local", "lan")`（`:4549`）。
- 后端事件唯一广播出口 `emit_event`（`gui_bridge.py:2019`）→ `_emit_raw`（`:2027`）→ `lan.broadcast`（`:2042-2044`）。
- 审批接口已存在：`respond_permission`（`:4426`）/ `respond_permission_choice`（`:4444`）/ `get_active_permission`（`:4282`）。
- 敏感凭据加密：`core/credentials.py`（DPAPI/keyring 前缀）。
- 配置键登记：`config.py:426 KNOWN_CONFIG_KEYS`（漏登记 → strict_config 启动失败）。

### 1.3 非目标

- 不做流式卡片刷新（回合结束推送一次，与 opencode-mobile 一致）。
- 不做手机端飞书配置（用户只选了桌面设置页）。
- 不做回调地址（webhook）通道（需要公网/内网穿透）。
- 不支持同时服务多个项目目录（opencode-mobile 同样只服务第一个项目）。
- **绝对不允许改动 `websockets` 版本**（用户红线，见 §二）。

## 二、全局约束

1. **`websockets` 版本任何情况下不允许变动**——不可谈判。方案内所有路线与回退都不含降级。
2. 不配置飞书时，星瑶现有功能行为必须与今天完全一致。
3. 线程铁律（AGENTS.md）：后台线程不得碰 GUI/JS 桥；事件源线程只入队不阻塞。
4. 只在 `dev-feishu` 分支提交，不合并、不推送（合到 dev/推送需用户明确要求）。
5. 遵守仓库惯例：配置键登记、密钥加密、测试名 `tests/test_*.py` 与 `*.test.ts` 成对、版本号与 CHANGELOG 首条一致（`tests/test_gui_changelog.py` 强制）。

## 三、方案与取舍

### 3.1 入站通道：长连接（非 webhook）

- 长连接 = 我们主动连飞书并保持，飞书事件推过来；免公网 IP、免 verification_token/encrypt_key。
- 回调地址 = 飞书访问我们的 HTTP 端点，必须公网可达，还要自实现 URL 校验握手 + AES 解密 + 签名校验。
- 结论：长连接（opencode-mobile 同款，`src/feishu/gateway.ts:109-168`）。

### 3.2 依赖冲突处理：搬运官方 SDK 传输层，不装 lark-oapi

lark-oapi（飞书官方 Python SDK）元数据锁 `websockets>=11,<16`，与星瑶装机的 17.1 冲突；同进程内一个库只能有一个版本（sys.modules 进程级），无法隔离共存。

| 路线 | websockets | 其它功能 | 可复现 | 结论 |
|---|---|---|---|---|
| 装官方包，websockets 降 15.x | 被改 | 可回归 | 好 | **排除（红线）** |
| 装官方包 + `--no-deps` | 保住 | 本机零影响 | 差（新机器静默降级） | 排除 |
| **搬传输代码进星瑶** | **保住 17.1** | 零（只新增 protobuf） | 好 | **采用** |
| 仅回调地址 | 保住 | 零 | 好 | 排除（需公网） |

为什么自维护可放心：传输层只负责"保持连接、收发帧、去重"，协议稳定；搬运目录保留上游仓库 + 版本 + 许可证标注。已核实 lark-oapi 传输代码只用 3 个 websockets 符号（`connect` / `WebSocketClientProtocol` / `InvalidHandshake`），三者在 17.1 里都在（`websockets/__init__.py:231-248` 废弃别名、`exceptions.py:206`）。

### 3.3 卡片界面

照搬 opencode-mobile 已实测界面（其 `README.md:11-226`），品牌名换成「星瑶」，底层映射到星瑶现有接口：

- **执行完成卡**：回合结束推送；内容 = `message_final.content`；卡上输入框 / 引用回复 → 同一会话 `send_user_message(turn_source="feishu")`。
- **权限审批卡**：源 = `permission_request`（`gui_bridge.py:4311`）；按钮 → `respond_permission`（choice 0/1/2）与 `respond_permission_choice`；动作名归一中文；目标 >5 条或单条 >300 字符折叠。
- **提问卡**：源 = permission_request（ask_user 类）；单选/布尔/多选/填空/自由输入自适应；必填校验；提交后原地变「已回答」结果卡。
- **卡住提醒卡**：10 分钟无输出推送，同会话 2 小时最多一次。
- **待拍板收件箱** `/inbox`：权限待批 + 提问待答聚合。
- **列表卡** `/list` `/model` `/agent`：当前项打标 + 点按钮切换 + 翻页；映射 `get_sessions`/`create_session`/`switch_session`/`get_models`/`set_model`。
- **功能面板** `/panel`：按钮即指令。
- **操作结果卡**：按钮回调后原地替换。
- **纯文本回执**：指令普通回执。
- 卡片 2.0 红线（写进测试断言）：无 `note` 标签；按钮 `behaviors:[{type:"callback",value}]`；回调结果卡包 `{card:{type:"raw",data}}`；`input.max_length ≤ 1000`；不用 `collapsible_panel`。

指令集：`/help /panel /status /new [标题] /list /switch <序号> /model [名] /agent [名] /inbox /stop`；其余消息 = 直接发给绑定会话。
