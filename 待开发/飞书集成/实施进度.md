## 三、规格与现实的差异

### 差异 1（T2）：假设 A3 不成立 → 手写帧编解码，新增依赖降为 0

计划里 A3 是「用官方 `protobuf` 包替换上游夹带的 protobuf 副本」，因此原计划要新增
一个依赖 `protobuf`。**实测否证**：上游 `pbbp2_pb2.py` 是 protoc 3.19 之前的老式生成
代码（手工构造 `_descriptor.FileDescriptor` / `Descriptor`），官方 protobuf ≥4.21 直接
拒绝加载：

```
$ venv/Scripts/python.exe -m pip install protobuf && python -c "import pbbp2_pb2"
ImportError: ... Descriptors cannot be created directly.
If this call came from a _pb2.py file, your generated code is out of date and must be
regenerated with protoc >= 3.19.0. ... 1. Downgrade the protobuf package to 3.20.x or lower.
```

（实验后已 `pip uninstall protobuf` 并清理残留的空 `google` 命名空间目录，环境还原。）

**处置**：改为自写 `core/feishu/_lark_ws/frame.py`——该协议只有 2 个消息、9 个字段，
且只用 varint 与长度前缀两种线格式，手写约 300 行、零依赖、可完整单测（含黄金字节
对照 protobuf 线格式）。上游夹带的 `pb/google/protobuf/**`（约 50 个文件）与
`pbbp2_pb2.py` / `gogo_pb2.py` 均不搬运。

**结果**：本次集成对 `requirements.txt` 的改动为 **零**（原计划新增 1 个 `protobuf`），
比计划更贴近「不影响其它功能」的目标；`websockets` 版本未动。

### T5（2026-09-29）

**实施中抓到并修掉两处真实缺陷**（T4 的测试当时自己伪造了载荷，所以没暴露）：

1. **表单提交回调没有 `action.value`**：飞书表单提交按钮只带 `action.name`
   （提交按钮不带 `behaviors`），T4 的分派只看 `value.kind` → 完成卡上的「发送」
   在真机上不会被处理。已改为 `value.kind or action.name` 两处取。
2. **表单提交不带 `request_id`**：提问卡的自由输入框提交后无法知道回答的是哪个请求。
   按 opencode-mobile 的方案（`gateway.ts:129-136` 提供 `context.open_message_id`），
   推卡时记录「卡片消息 id → 请求 id」映射（上限 500 条 FIFO），回调按消息 id 反查；
   查不到时明确回执「无法识别请求」，不瞎猜。

另修：`target_lines` 对列表参数改为**按条目展开**（此前把 8 个路径拼成一行，导致
「资源超过 5 条折叠」永不触发）。

设计取舍：**审批/提问不分来源**——桌面端发起的回合需要拍板时同样推飞书（人在外面
正是靠这条链路），与 opencode-mobile 一致；白名单为空时 fail-closed（不渲染按钮 +
卡片上写明原因）。

改为断言 `style` 属性，更精确且不依赖 VTU 实现细节。

### T11（2026-09-29，用户提问暴露的真实缺陷）

**用户提问**：「`computer_turn_source` 只允许受控值 local 或 lan 这是什么意思」。
这句话是 `core/llm.py:655` 的报错文案——**用户已经踩到了这个缺陷**。

**根因**：`turn_source` 是入口层受控值，但它在**两层各有一份硬编码白名单**：

| 层 | 位置 | 加入 feishu 前 |
|---|---|---|
| 入口层 | `gui_bridge.send_user_message` | `("local", "lan")` → 我改成了 `+ "feishu"` ✅ |
| 低层 | `core/llm.chat_with_model_events` 的 `computer_turn_source` 校验 | `("local", "lan")` → **我漏了** ❌ |

`gui_bridge.py` 把回合来源原样透传给低层（`computer_turn_source=turn_source`），
于是**飞书回合一旦发起模型请求就抛 `ValueError`**，表现为「飞书里发消息，收到执行出错卡，
内容是 computer_turn_source 只允许受控值 local 或 lan」。

计划 §3 其实预警过这个点（"新增来源必须同步修改三处"），但只列了 gui_bridge / lan_server /
capability 三处，**漏了 core/llm 这一处**——属于我的调研与实现都有缺口。

**修复**：
1. `core/llm.py`：新增模块常量 `COMPUTER_TURN_SOURCES = ("local", "lan", "feishu")`，
   校验改用它；报错文案改为列出全部受控值（`local|lan|feishu`），不再误导为"只有两个"。
2. `gui_bridge.py`：新增模块常量 `TURN_SOURCES`，入口校验改用它（两处各自声明，保留
   低层独立复核的设计，不互相 import）。
3. `core/computer/capability.py`：拒绝文案由「局域网或移动端」改为
   「局域网、手机或飞书等远程发起的回合」，与现状相符（判定逻辑 `!= "local"` 本就正确）。
4. **护栏**：新增 `tests/test_turn_source_consistency.py`——断言两处白名单集合相等、
   三个受控值都在、每个受控值都能通过低层校验（用哨兵异常在校验后中断，不真发请求）、
   非法值仍被拒且报错列出全部受控值；`tests/test_computer_capability.py` 增加
   「飞书回合也属远程 → 禁用电脑操控」用例。

### T12（2026-09-29，真机联调第二个真实缺陷）

**用户反馈**：「会话发出去了，没收到回复」。T10 补的入站日志直接定位：

```
20:31:04 INFO 飞书消息: chat=oc_f5e2… 内容='你好，你是谁'
20:31:04 INFO 飞书消息转回合: session=打开浏览器 搜索“昆山维
20:31:27 ERROR 发送飞书回合结果失败（chat=oc_f5e2…）
  FeishuApiError: Failed to create card content,
  ext=ErrCode: 11310; ErrPath: ROOT -> body -> elements -> [3](tag: form);
  ErrMsg: name(reply) duplicate; / code=230099 / http=400
```

**根因**：完成卡的表单里，输入框 `name` 与提交按钮 `name` **都叫 `reply`**，
飞书判定重名 → **整卡拒收**。回合其实正常跑完了，只是结果卡片发不出去，
所以用户看到的是「消息发出去了、没有任何回复」。

为什么之前没发现：只有**带表单的完成卡**会踩到；`/list`、`/status` 这类无表单卡片
一切正常（真机日志也证实它们发送成功），单测当时只断言了"输入框 name 是 reply"
这个错误事实本身——**测试把 bug 当成了规格**。

**修复**：
1. `core/feishu/cards.py`：完成卡输入框改名 `reply_text`，提交按钮保持路由名 `reply`
   （两者必须不同）；注释写明这条红线。
2. `core/feishu/bridge.py`：回调改取 `form_value["reply_text"]`。
3. **护栏**：新增 `tests/test_feishu_cards.py`——遍历全部 14 类卡片构造器（含开/关按钮、
   有/无表单分支），逐条校验平台红线：无 `note` 标签、按钮必须 callback 或表单提交、
   `input.max_length ≤ 1000`、**同一 form 内元素 name 唯一**、卡片可 JSON 序列化。
   已验证该护栏能抓到本缺陷（临时改回重名后 44 个用例中相关 2 个变红）。

```
$ venv/Scripts/python.exe -m pytest tests/test_feishu_cards.py -q
44 passed

$ venv/Scripts/python.exe -m pytest tests/test_feishu_*.py tests/test_turn_source_consistency.py \
      tests/test_computer_capability.py -q

```

**教训（记在文档里）**：单测断言必须来自**平台契约或真机现象**，不能来自自己的实现；
当时那条 `name == "reply"` 的断言就是照着实现写的，于是把缺陷固化成了"规格"。
