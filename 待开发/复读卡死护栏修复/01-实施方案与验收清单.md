## 二、任务拆解

### T1 填充词判据（对应修复①，P0）

**实现步骤**

1. 在 `core/llm.py` 模块级新增 `_FILLER_TOKENS`（不可变集合，建议 `frozenset`），首版元素：
   `好, 好的, 嗯, 哦, 噢, ok, okay, 行, 可以, 收到, 明白, 了解, 继续, 输出, 完成, 完毕, yes, no`。
2. 新增辅助函数 `_is_filler_only(text) -> bool`：
   - 先按 `_is_meaningful_assistant_content` 同款正则剥离空白/标点/Markdown 符号，取剩余串 `s`；
   - `s` 为空 → 返回 False（空正文交给原判据处理，不由本函数判假，避免改变空串语义）；
   - **建议口径**：把剩余串按标点切分为片段，**所有片段均命中 `_FILLER_TOKENS`（比对前 `lower()`）** 且整体剩余长度 `≤6` 字符 → 返回 True；否则 False。
3. 改写 `_is_meaningful_assistant_content`：

   ```python
   def _is_meaningful_assistant_content(text):
       if not bool(re.sub(r"[\s`*_#>~\-\[\](){}|.,!?，。！？:：;；/\\]+", "", text or "")):
           return False
       return not _is_filler_only(text)
   ```

   （即"原判据为真 且 not _is_filler_only(text)"；**函数名与签名保持不变**。）

**边界与词表校准原则**

- 只命中"剥完只剩填充词"：`"好。" → 剥后 "好" → 命中`；`"好的，已完成" → 片段 ["好的","已完成"]，"已完成"未命中 → 判为有效正文`；`"OK，我来处理" → ["OK","我来处理"] → 有效`。
- **词表宁可漏判，不可误判**：拿不准的词绝不进表；宁可漏掉一个填充词，也不能让正常短回复被判为空正文。
- 不含实义的纯语气字符（如单独的标点）仍走原判据，由原逻辑判为空。
- 不引入语义模型、不做相似度打分（那是 T2 的指纹比对，且只比"相同/近似"）。

### T2 退化检测（对应修复②，P0）

**实现步骤**

1. 在流式装配层（`:2413` 得到 `raw_content_meaningful` 之后、慢步熔断判断 `:2453` 之前）维护两个滑窗：最近 3 步的**正文指纹**、**思考指纹**。指纹 = 去掉标点与空白后的字符串（正文取 `public_content` 促升前原文口径需与 `raw_content_meaningful` 保持一致；思考取 `reasoning_content`）。
2. 退化判定：**连续 3 步相同**（指纹逐位相等）**且** `单步长度 ≤ 20 字符`；或退化等价条件——**两两相似度 ≥ 0.9**（相似度按字符集重叠/编辑距离比例计算，不引第三方库）。
3. **首次命中**：
   - 复用 `SLOW_STEP_NUDGE_TEXT`（`:1086`）经与慢步熔断**同一通道**追加为 `user` 消息（同时 `messages.append` 与 `pending_persistence.append`，见 `:2463-2471` 同款处理）；
   - `_notify_event(event_callback, "notice", {"message": "检测到模型连续复读…已要求其立即收敛"})`。
4. **二次命中**：
   - `_notify_event(event_callback, "error", {...})`；
   - **走慢步熔断同一收尾路径**（`:2483-2496`）：发 error 事件 → 若已促升思考则 `yield from _yield_content(public_content)` → `flush_persistence()` → `current_step.mark_assistant_ready()` / `complete()` → `harness_runtime.complete()` → `computer_exit_kind = "completed"` → `return`。
5. 退化计数在**回合开始初始化区**（`:1256-1264` 附近）建为 `0`，随回合生命周期重置。

**边界**

- **必须发事件让用户可见，不得静默收尾**（首次 notice、二次 error）。
- 不得复用/篡改 `progress_guard.py`；退化检测只读正文文本，与 `progress_guard` 的"不读正文"分工不冲突。
- 指纹/计数**仅存于当前回合内存**，不写 Journal、不入库（与 `read_signatures` 同策略，避免污染缓存与历史）。

### T3 额度类 fail-fast（对应修复③，P1）

**实现步骤**

1. 在 `core/llm.py` 顶部引入 `map_llm_error`：`from core.llm_error_mapper import map_llm_error`（若已 re-export 则复用既有导入）。
2. 在退避重试决策分支入口（`:2099` `if attempt < max_api_retries - 1:` 之前，或在异常处理 `api_err` 就位处）计算类别：

   ```python
   _cat = map_llm_error(api_err).category
   if _cat in {"insufficient_quota", "auth_invalid", "permission_denied", "model_not_found"}:
       # 确定性失败：不再退避重试，直接抛/收尾
       raise api_err
   ```

3. 瞬时类（`rate_limit` / `service_overloaded` / `gateway_error` / `network_error` / `internal_server_error` 等）保持现有退避分支不变。

**边界**

- 不改 `max_api_retries`（`：1761` 仍为 5），只让确定性失败**提前跳出**。
- 不改现有 429 退避时长口径（`:2102-2112`）。
- `context_overflow`（`:214`）已由历史压缩路径处理，不纳入本 fail-fast 集合。
- 分类失败/`unknown_error` 时**保持原重试行为**（保守兜底，不因分类异常改变既有路径）。
- **本任务不改 `core/llm_error_mapper.py`**，仅调用其既有 `category`。

## 五、回归红线

- **不得修改 `progress_guard.py` 的判据**：不读正文是有意设计，本次修复禁止让它去读模型自然语言。
- **正常短回复不得被误判为空正文**：`"好的，已完成"`、`"OK，我来处理"` 等含实义短句必须仍算有效正文（用例 2 守着）。
- **不得改动 prompt 稳定字节**：`test_prompt_byte_stability.py` 的 sha256 golden 守着缓存命中率，`system_prompt*.md` 与稳定前缀拼接顺序零改动。
- **不改 `_is_meaningful_assistant_content` 的函数名与签名**。
- **不引入第三方依赖**；**不做通用内容质量判断**。
- **三项修复独立可验收、独立可回滚**：①（判据）②（退化检测）③（fail-fast）互不依赖，任一项可单独回退。
- **所有熔断/止损路径必须发事件让用户可见**，禁止静默结束回合。
- **不得修改 `core/`、`tests/` 下与本修复无关的既有文件**；本方案涉及的既有文件改动仅限 `core/llm.py`。
