# 明天开工提示词（渠道请求形态覆盖）

用法：在新电脑上打开本项目会话，把下面代码块整段粘贴给星瑶即可。

**开工前环境准备（人工，2 分钟）**

1. 拉取仓库到新机器，确认 `待开发/网关请求形态覆盖/设计规格与实施计划.md` 存在；
2. 项目 `venv` 可用：`venv\Scripts\python.exe -m pytest -q` 能跑通；
3. `config.json`（用户级 `~/.ycode/config.json`）里已配好 tokenrhythm provider 与其 API Key（实测 Task 4 需要真实调用）。

---

```text
项目：Y-CODE / 星瑶（仓库根目录以本机实际路径为准）
任务：实施「渠道请求形态覆盖（route_request_overrides）」

第一步：完整读 待开发/网关请求形态覆盖/设计规格与实施计划.md（重点看 §4 设计、§5 实施计划、§6 验收标准、§7 风险）。

第二步：只问我一个问题——配置落点选哪个方案（A 顶层专用段 / B 顶层通用覆盖层【文档推荐】/ C provider 级键）。
定下来之前不要写任何实现代码。

第三步：按 §5 的 Task 1 → Task 4 顺序实施，严格 TDD：
  写失败测试 → 跑出 RED → 最小实现 → 跑出 GREEN → 单独提交（一个 Task 一个 commit）。
  写失败测试 → 跑出 RED → 最小实现 → 跑出 GREEN → 单独提交（一个 Task 一个 commit）。

硬约束（违反即返工）：
1. 只做请求形态覆盖（额外请求头 + 额外请求体参数），不碰账本、保活、工具字母序、缓存断点等任何机制判定；
2. 未配置覆盖的渠道，请求字节必须零变化——证据是 tests/test_provider_payload_golden.py 全绿且 golden 未改
   ＋ tests/test_llm_native_transport.py 的 headers 快照断言；
   test_prompt_byte_stability.py 也要全绿，但它守的是系统提示词与工具 schema，**不算本项证据**（别拿它交差）；
3. 白名单拒绝是「键级剔除」而不是整条丢弃，请求必须照常发出：
   headers 禁改 authorization / content-type / accept / host / content-length；
   body 禁改 model / messages / tools / tool_choice / stream / stream_options /
   max_tokens / max_completion_tokens / api_key / api_base；
4. 日志与诊断只记键名或 sha256，绝不记值；覆盖值支持 ${env:VAR} 引用；
5. 覆盖对所有 cache_scope 统一生效（main / subagent / compression / keepalive / benchmark）；
6. 注入落点只有一个——core/llm_dialects.py 的 _provider_request_options 返回值（headers 走 extra_headers、body 走 extra_body）。
   **不要改 core/llm_native_transport.py 的任何代码**：那里「tokenrhythm 专用头 → extra_headers」的合并顺序已经满足「配置优先于硬编码」，
   改传输层属于重复造轮子（原 Task 2 方案已废弃，理由见文档 §5 Task 2）；
7. 覆盖合并点必须放在 _assert_reasoning_request_consistent(...) 之后、return result 之前——
   覆盖值不参与一致性校验，配置错误才不会抛错阻塞对话。

每个 Task 完成后向我汇报：改了哪些文件（file:line）、跑了什么测试命令、真实输出、commit hash。
不允许用「应该能过」「看起来没问题」这类表述——没跑就等于没做。

验收：按 §6 的 V1~V6 逐条给证据（测试输出、诊断表的 SQL 查询结果、Task 4 的 A/B 实测数字）。

收尾：把这轮的实际偏差、实测数字与新发现的未决问题，回填进文档 §5 Task 4 的「实测记录」
与 §7 风险表，并提交文档更新。
```
