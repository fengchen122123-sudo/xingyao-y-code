# 星瑶按回合撤销：完整设计规格

## 1. 文档地位

本文档是“星瑶按回合撤销”的唯一实施需求基线。实施 Agent 不得用 MVP、占位按钮、内存状态或强制覆盖替代本规格的持久化、冲突检查、事务恢复与记忆语义。

本功能修复的核心产品缺口是：GUI 的“N 个文件已更改”卡片表达的是一整轮文件修改，但现有 `undo_last_edit()` 只能恢复当前会话最后一个文件，且 GUI 以 `force=True` 跳过新建文件删除的后端确认。新功能必须消除这个语义错位。

## 2. 目标

1. 用户可从 GUI 文件卡片一键撤销该回合的全部受控文件修改，且会话改名后仍能精确定位。
2. CLI 提供语义一致的 `/undo`、列表、预览、状态和中断恢复操作。
3. 用户直接用自然语言明确要求撤销时，模型侧经结构化工具和现有权限管线进入同一服务，不自行重写旧文件。
4. 撤销前验证实际磁盘状态，不覆盖用户、后续回合或外部软件的新修改。
5. 保留完整聊天与工具审计记录，同时使模型持久识别已撤销回合的文件结果已失效。
6. 在多会话、子代理、应用重启、撤销中断和用户外部修改下保持一致、可审计、可恢复。

## 3. 非目标与明确边界

1. 不撤销进程、网络请求、远程 Git、数据库、系统配置或其他非文件副作用。
2. 不依赖 Git；非 Git 目录、未跟踪文件和忽略文件在受控工具写入时同样可记录。
3. 不通过解析命令字符串、文件监听或回合后扫描来猜测通用终端命令的文件副作用。
4. 不提供“强制撤销”或“忽略冲突继续”。
5. 默认不提供部分文件撤销；操作单位是完整回合。
6. 不保证对所有操作系统的外部进程实现绝对文件系统原子性；但必须通过多次指纹检查、内部互斥、每文件原子替换和持久化日志缩小竞态并暴露剩余风险。
7. 截图中的“审核”只是布局参考，本需求不新增独立审核功能；现有 diff 展开能力必须保留。

## 4. 现状盘点与缺口

### 4.1 现有能力

- `core.memory.LAST_UNDO_STATE` 按会话保留最近一个文件的修改前内容。
- `core.agent_service.undo_last_edit()` 可恢复一个文件，并调用 `manager.undo_last_interaction()` 删除最后互动记忆。
- `core.memory.begin_turn_checkpoint()` / `end_turn_checkpoint()` 会将一轮中受控工具的首次修改前快照收集到内存。
- 子代理可绑定父回合检查点。
- CLI `/checkpoint restore <turn_id>` 可按内存快照逐文件回写。
- GUI `ChangedFilesPanel.vue` 会从当轮 `diff_ready` 数据收集文件和增删行数。

### 4.2 必须修复的缺口

- 现有检查点仅在进程内存，重启即丢失。
- 没有“星瑶最后一次成功修改后”指纹，无法判断用户后续修改。
- 旧检查点直接逐文件恢复，可以部分成功却没有持久化事务状态。
- GUI 撤销调用单文件接口，并固定 `force=True`。
- 前端回合分组依赖用户消息边界，没有权威 `turn_id`。
- 当前 GUI/CLI 都在生成 `turn_id`、开启检查点之前先持久化用户消息；GUI 还会先发出不含 `turn_id` 的 `turn_start`。新协议若不重排生命周期，会留下无法原子归组的消息和事件。
- 撤销通过删除互动记忆处理模型认知，与按回合审计需求冲突。
- 旧 `/checkpoint restore` 允许 `--force`，可覆盖新状态。

## 5. 核心领域模型

### 5.1 回合撤销状态

`TurnUndoStatus` 使用严格枚举：

- `recording`：回合运行中，正在记录。
- `ready`：回合已结束，快照完整，可预检。
- `no_changes`：回合已结束，但没有产生受控文件修改；这是不可撤销的正常终态，不显示文件撤销卡片。
- `unavailable`：记录不完整或存在不支持的受控文件操作。
- `conflicted`：最近一次预检发现文件已变化。
- `reverting`：已消费确认令牌，正在恢复。
- `reverted`：全部文件已验证恢复，撤销事实已提交。
- `interrupted`：撤销事务未进入终态且进程已中断。
- `recovering`：用户已确认继续或取消中断事务，独立恢复操作正在执行。
- `failed`：在没有进入不可确定文件状态前明确失败。

`prechecking` 只是前端发出预检请求后的短暂 UI 状态，不属于 `TurnUndoStatus`，不持久化到检查点。

`conflicted` 不是一次永久失败。用户处理磁盘变化后可重新预检；服务以当次真实检查结果更新状态。

快照保留状态与撤销生命周期正交，使用 `SnapshotAvailability`：

- `available`：所需 blob 存在且校验有效。
- `expired`：已按公开保留策略回收。
- `missing`：非预期缺失。
- `corrupt`：内容哈希或结构校验失败。
- `not_required`：`no_changes` 回合没有文件快照。

不得用 `expired` 覆盖 `reverted`。例如已撤销回合的 diff blob 后来过期，生命周期仍是 `reverted`，界面显示“已撤销，原 diff 已过期”；只有尚未撤销的 `ready + expired` 才表现为“撤销记录已过期”。

### 5.2 回合身份

- 新回合使用完整 128 位随机 UUID 生成不透明、全局唯一 `turn_id`，不再将可改名的会话名嵌入身份语义。
- 可以为兼容显示读取现有带会话前缀的旧 `turn_id`，但始终将它当作不透明字符串，不从格式推导身份。
- CLI 只截取 `turn_id` 用于人类显示，后端只在当前会话唯一匹配时解析短 ID。

### 5.3 撤销操作状态

`UndoOperationStatus` 与回合状态分离：

- `previewed`
- `preparing`
- `prepared`
- `applying`
- `verifying`
- `committed`
- `failed`
- `cancelled`
- `interrupted`
- `compensated`
- `recovery_required`

每个文件的操作进度独立记录，不用一个计数器猜测已处理文件。

### 5.4 文件状态

文件快照至少包含：

- 规范化绝对路径、展示用相对路径和工作区根。
- 检测到的结点种类：`missing`、`regular_file`、`symlink`、`directory` 和 `special`。
- 是否存在、大小、SHA-256、内容快照引用。
- 可靠获取时的基本权限位。
- 可靠获取时的卷/设备号与文件 ID（POSIX 可用 `st_dev + st_ino`，Windows 使用卷标识与 File ID）及硬链接计数。
- 符号链接自身目标，仅用于冲突识别，不跟随链接读取内容。
- 修改来源：主代理、子代理、工具名和 `tool_call_id`。

严格可撤销节点只有 `missing` 和普通文件。最终路径本身是符号链接、目录、设备文件、管道、特殊文件或链接计数大于 1 的硬链接时，受控修改应在写入前被拒绝，不生成“部分可撤销”记录。可以解析工作区根和中间目录的符号链接，但解析后的规范化路径必须始终留在已授权范围，且执行前身份不得改变。

本功能的“恢复文件状态”指内容字节、存在性和可靠获取的基本权限位。不承诺恢复修改时间、创建时间、Windows ACL、扩展属性或备用数据流；GUI、CLI 和文档不得将其描述为完整文件系统元数据恢复。

### 5.5 状态迁移约束

检查点只允许以下有向迁移；同状态幂等读取不算迁移：

```text
recording  -> ready | no_changes | unavailable
ready      -> conflicted | reverting | unavailable
conflicted -> ready | unavailable
failed     -> ready | conflicted | unavailable
reverting  -> reverted | interrupted | failed
interrupted-> recovering | unavailable
recovering -> reverted | ready | interrupted | unavailable
```

- `no_changes`、`unavailable` 和 `reverted` 是生命周期终态；快照过期只更新 `SnapshotAvailability`。
- `reverting -> failed` 只允许在尚未触碰任何目标文件且磁盘状态仍确定时发生；一旦有文件可能已变化，必须进入 `interrupted`。
- `recovering -> ready` 只表示 `cancel_revert` 已完整验证恢复到用户点击撤销前的状态；`recovering -> reverted` 表示 `continue_revert` 已完成剩余撤销。
- 每次影响恢复集合、最终 `after`、生命周期或确认范围的提交都递增 `record_version`。预检令牌绑定当时版本；执行以 compare-and-swap 校验版本并在同一短事务中消费令牌、进入 `reverting`。
- 未列出的迁移、跳过状态或未知枚举必须显式失败，不能在 DAO 层任意赋值。

撤销操作只允许：

```text
previewed    -> preparing | cancelled | failed
preparing    -> prepared | failed
prepared     -> applying | failed
applying          -> verifying | interrupted
verifying         -> committed | interrupted
interrupted       -> recovery_required | committed | compensated
recovery_required -> committed | compensated
```

权限拒绝或预检令牌自然过期时，尚未写文件的 `previewed` 操作进入 `cancelled`。`preparing` 只生成回滚快照和阶段文件，不触碰目标路径，因此失败必须是确定性的 `failed`；开始应用后任何不确定性都进入 `interrupted` 或 `recovery_required`。

`continue_revert` 和 `cancel_revert` 每次确认都新建带 `parent_operation_id` 的独立操作，不覆盖原中断行。恢复子操作提交后，在同一事务把原操作标记为 `committed`（继续）或 `compensated`（取消），并记录 `resolved_by_operation_id`；恢复子操作再次中断时，可继续形成可审计的父子链。服务拒绝跨检查点父子关系和循环引用。

## 6. 模块与职责

新增 `core/turn_undo/` 包：

```text
core/turn_undo/
  __init__.py
  models.py          # 严格枚举、值对象、DTO
  storage.py         # SQLite 元数据、内容寻址快照与 GC
  recorder.py        # 受控文件修改前后记录
  coordinator.py     # 工作区互斥、活跃回合检查和路径冻结
  transaction.py     # 多文件恢复事务
  recovery.py        # 崩溃中断检测和显式恢复
  prompt_context.py  # 模型动态纠正上下文
  service.py         # GUI、CLI、模型工具共用的编排入口
```

`gui_bridge.py`、`main.py` 和前端只处理输入输出与状态绑定，不自行读写快照或拼接恢复逻辑。

### 7.5 `turn_undo_confirmations`

至少保存：

```text
confirmation_id TEXT PRIMARY KEY
token_hash TEXT NOT NULL UNIQUE

operation_id TEXT NOT NULL

workspace_identity TEXT NOT NULL

```

原始令牌不写日志、聊天、事件或数据库。当前进程 `boot_id` 只在内存生成；重启后与旧记录不匹配，从而使未消费令牌全部失效，启动清理可再删除这些旧记录。

### 7.6 `workspace_corrections`

作为模型可见的持久化纠正事实，至少记录 `correction_id`、规范化 `workspace_root`、来源 `session_id + turn_id`、已提交 `operation_id`、影响文件摘要、时间和未覆盖副作用，并以 `operation_id` 唯一约束保证幂等。未提交成功的撤销不能生成“已撤销”纠正记录。

### 7.7 `message_turn_links`

GUI 要在页面刷新和应用重启后把消息、diff 与撤销卡片重新绑定到权威回合，仅靠实时 `turn_start` 事件不足。新增结构化关联表：

```text
message_id INTEGER PRIMARY KEY
checkpoint_id TEXT NOT NULL
position_kind TEXT NOT NULL
FOREIGN KEY(message_id) REFERENCES messages(id) ON DELETE CASCADE
FOREIGN KEY(checkpoint_id) REFERENCES turn_undo_checkpoints(checkpoint_id) ON DELETE CASCADE
```

- 用户消息、中间 assistant、最终 assistant 和必要的回合内 notice/error 在持久化时同时关联当前 `turn_id`。
- `position_kind` 使用严格枚举 `user`、`assistant_intermediate`、`assistant_final`、`tool`、`notice`、`error`；任何实际持久化但无法分类的回合内角色必须显式扩展迁移和测试，不能塞入默认值。
- 回合检查点必须在本轮首条消息关联写入前创建。关联表只保存 `checkpoint_id`，通过检查点取得权威 `sessions.id + turn_id`，避免在关联表重复存储后产生身份不一致。
- 每条 `messages` 记录与对应 `message_turn_links` 必须在同一个 SQLite 事务中提交或回滚，禁止崩溃后留下已显示却无法精确归组的新消息。
- Harness 路径已有 `messages + harness_events` 原子提交时，必须在同一事务再写 `message_turn_links`；用户消息等非 Harness 提交路径也必须显式传入当前 `checkpoint_id`，禁止事后按时间或消息范围回填。
- 关联表不将 GUI 分组生命周期耦合到 Harness Journal 清理策略；Harness Journal 仍不保存正文或文件快照。
- 关联表只存储身份与位置元数据，不存储消息正文。`messages` 仍是会话内容的唯一事实源。
- GUI 历史加载接口可将 `turn_id` 作为界面元数据合并返回，但 Provider 请求构造必须忽略该元数据，不得因此改变历史消息字节。
- 功能上线前的旧消息没有关联时，前端可仅为历史展示保留旧分组启发式，但这些组不得显示新撤销按钮。禁止用启发式结果生成持久化回合关联。

### 7.8 数据库要求

- 使用幂等迁移建表，按现有 `MemoryManager` 事务和锁规范执行。
- 每个写入函数都必须显式 `commit()`。
- 长时间文件 I/O 期间不持有 SQLite 连接锁；状态通过短事务前后推进。
- 字段转换、未知枚举和非法状态迁移必须显式失败。

## 8. 内容寻址快照仓库

原始文件字节不写入 Harness Journal、消息正文或 GUI 事件。它们保存在 `YCODE_DATA_DIR` 优先的本地目录：

```text
undo_blobs/
  ab/
    abcdef...          # 完整 SHA-256 作为文件名
undo_transactions/
  <operation_id>/      # 运行中事务的隔离文件和阶段文件
```

要求：

- 以流式读写计算 SHA-256，不将大文件整体读入内存。
- 先写临时文件、刷新、校验，再原子命名到内容地址。
- 相同内容只保存一份；数据库保持引用。
- 目录权限限制为当前用户；前端不直接获取快照绝对路径。
- 快照丢失、哈希不符或未知 `schema_version` 时更新 `SnapshotAvailability` 并停止读取。尚未撤销的回合转为 `unavailable`；已经 `reverted` 的回合保留其审计终态，只将原 diff 标记为不可查看，不尝试猜测修复。

### 8.1 保留与配额

- 默认每个会话保留最近 50 个完整检查点，与现有检查点数量上限保持一致。
- 配额和保留数量必须是可配置值，并在 GUI/CLI 说明超限后较旧检查点的 `snapshot_availability` 会进入 `expired`，但不覆盖 `reverted` 等生命周期事实。
- 不回收 `interrupted`、`recovery_required` 或仍被事务引用的快照。
- 不回收仍被未过期确认令牌、进行中恢复操作或惰性 diff 请求持有引用的快照。
- GC 只删除已无任何数据库引用的内容块，使用专门锁并二次确认引用。
- 在文件修改前无法为新快照预留空间时，本次受控修改失败，不降级为“修改但不可撤销”。

## 9. 受控文件修改记录

### 9.1 回合生命周期

1. GUI/CLI 必须先解析并确认规范化工作区、确保会话行存在、生成全局唯一 `turn_id`，然后创建持久化检查点；只有检查点创建成功后，才能提交首条用户消息并发出携带 `session_id + turn_id` 的 `turn_start`。会话后续改名不改变检查点归属。
2. 回合线程与同步等待完成的前台子代理通过显式上下文绑定同一检查点，不依赖全局“最后回合”。
3. 回合结束时验证每个已记录文件仍等于星瑶最后一次受控修改后指纹。
4. 有受控文件修改且记录全部完整时进入 `ready`；没有受控文件修改时进入 `no_changes`；记录失败、不支持类型或未解释变化进入 `unavailable` 或明确冲突状态。

### 9.2 子代理与后台任务归属

- 同步前台子代理的生命周期不超过父回合，文件修改归入父回合检查点。
- 任何可能在父回合返回后继续运行并写文件的后台子任务，启动时必须创建独立检查点、独立全局 `turn_id`，并以 `owner_kind=background_task` 和 `parent_checkpoint_id` 关联发起回合；禁止把迟到写入追加到已封闭的父检查点。
- 后台任务完成后生成独立的文件变更卡片和 CLI 列表项。GUI 可借助 `parent_checkpoint_id` 将它显示在发起回合附近，但撤销身份始终是后台任务自己的 `session_id + turn_id`，不得冒充父回合。
- 服务创建后台检查点时必须验证父、子检查点属于同一 `session_id` 和同一规范化工作区；前端不能直接指定任意 `parent_checkpoint_id`。
- 已封闭检查点不能再签发新的 `MutationHandle`；工具必须在真正写入前再次确认句柄和检查点仍有效，因此迟到写入在触盘前失败。
- 后台任务没有受控文件修改时同样进入 `no_changes`，不生成空撤销卡片。

### 9.3 修改计划与写入前准备

`prepare_mutation()` 接收工具在真正写文件前计算出的完整 `PlannedPathMutation` 集合。每个路径必须同时声明当前预期状态和计划写入后状态。该方法必须：

- 检查回合处于 `recording`。
- 规范化路径并执行现有沙箱与授权流程。
- 拒绝不支持节点、符号链接逸出和路径歧义。
- 对该路径首次修改保存完整修改前状态；同一回合后续修改不覆盖 `before` 快照。
- 在写入前将工具计算出的计划修改后字节同样写入内容寻址仓库，记录计划 `after` 节点、大小、哈希和 blob 引用。删除操作的计划 `after` 为 `missing`。
- 同一文件一轮多次修改时，保留最初 `before` 并用新计划替换最终 `after` 引用；被替换 blob 只在无其他引用时可由 GC 回收。
- 在 `before`、计划 `after` 与数据库记录全部持久化成功后返回不可伪造的 `MutationHandle`。不能在写入前确定完整后置状态的工具不符合严格可撤销契约。

计划 `after` 必须精确声明由工具控制的节点种类、存在性、内容、大小和基本权限。由操作系统在最终就位时分配的 File ID 不要求工具提前预测，但 `verify_after_mutation()` 必须捕获实际身份、确认硬链接计数仍为 1，并把它纳入后续预检指纹。

### 9.4 修改后

`verify_after_mutation()` 必须在工具声称成功前：

- 立即读取实际节点种类、存在状态、大小和 SHA-256。
- 将实际后置状态与 `MutationHandle` 中已持久化的计划 `after` 精确比较，一致后更新来源、时间和验证状态。
- 记录实际 File ID、硬链接计数和基本权限；后续预检除内容哈希外也比较这些可可靠获得的属性，防止同字节替换或节点身份切换被误认成未变化。
- 如果实际结果与计划不一致、验证落库失败或文件在验证前被外部改变，不得声称工具成功；检查点标记为不可安全撤销并显式报错。

回合封闭时从每个文件的最初 `before` 和最终计划 `after` blob 生成权威净 diff 与净增删行数。实时 `diff_ready` 可继续展示每次工具修改，但回合完成卡片、重启后卡片和撤销后审计必须使用这份净 diff，避免多次改回同一行造成统计重复累加。

### 9.5 工具覆盖

所有第一方文件工具必须走统一记录器，包括写入、编辑、删除、移动、重命名、复制覆盖、补丁应用及日后新增的受控文件变更工具。

工具注册元数据必须显式声明文件变更契约。新工具声明可撤销却不接入记录器时，测试和启动校验必须失败。

## 10. 通用终端命令边界

任意终端命令可以在工作区外写入、启动进程、修改数据库或发生网络副作用。不能用以下方法伪造完整撤销：

- 从命令字符串猜测输出路径。
- 命令结束后仅依赖文件监听器。
- 只记录 Git diff。
- 默认复制整个工作区并忽略大目录、虚拟环境或工作区外路径。

现阶段规则：

- 通用命令不进入严格撤销集合。
- 回合执行过通用命令时记录 `has_uncovered_command_effects=true`。
- GUI、CLI 和模型权限卡在确认时显示“仅恢复列出的受控文件，命令其他副作用不撤销”。
- 日后某个专用命令工具只有在执行前能提供精确快照契约时，才可接入 `FileMutationRecorder`。

要覆盖任意命令的完整文件副作用，必须单独建设写时复制或隔离工作区执行层，不属于本功能。

## 11. 预检与确认令牌

### 11.1 预检输入

只接收 `session_id + turn_id`。GUI 不提交目标路径列表，后端从持久化检查点取得唯一恢复集合。

### 11.2 预检内容

- 检查回合归属、工作区、状态和快照完整性。
- 对每个路径重新获取节点种类、存在状态、大小和 SHA-256。
- 将实际状态与星瑶最后一次受控修改的 `after` 状态精确比较。
- 对平台可靠提供的基本权限、File ID、硬链接计数和符号链接目标一并比较；字段不可获取时必须以明确的 `unsupported`/`unknown` 能力标记处理，不用空值假装相等。
- 任一不一致返回结构化冲突，不生成可执行令牌。
- 无冲突时生成影响摘要：恢复内容、删除新建、恢复删除、恢复路径状态的数量与文件。

### 11.3 令牌规则

- 使用安全随机值，数据库仅保存哈希。
- 绑定会话、回合、工作区、操作种类、检查点版本和全部实际指纹集。
- 默认 5 分钟过期，只能消费一次。
- 服务重启、预检版本改变、文件改变或工作区身份改变后失效。
- 执行时在工作区锁内再次验证所有指纹，然后原子消费令牌。
- 令牌记录绑定当前随机 `boot_id`；数据库中存在哈希不代表跨进程重启仍可执行。

## 12. 多文件恢复事务

### 12.1 正常流程

```text
验证输入
  -> 获取工作区锁
  -> 锁内复核活跃回合与检查点版本
  -> 验证令牌但暂不消费
  -> 再次检查全部文件并重算指纹集
  -> 短事务 CAS 版本、消费令牌，检查点进入 reverting，操作进入 preparing
  -> 保存撤销开始前恢复快照
  -> 生成并校验每个目标阶段文件
  -> 将操作标记为 prepared
  -> 按确定性顺序逐文件应用
  -> 每项验证并短事务记录
  -> 验证全部目标状态
  -> 提交撤销、回合状态和记忆纠正事实
  -> 释放锁
  -> 发送 UI 事件
```

### 12.2 文件应用

- 恢复普通文件：在目标目录写入阶段文件，刷新并校验后 `os.replace`。
- 删除本轮新建文件：先移到事务隔离位置，不直接不可恢复删除。
- 恢复本轮删除文件：从已校验快照生成阶段文件并原子就位。
- 重命名：按旧、新两个路径的明确目标状态执行，不依赖名称相似性猜测。
- 每个路径应用前再次检查是否仍等于事务记录的预期当前状态。

### 12.3 整轮原子性表述

不得声称跨多个文件存在操作系统级单次原子提交。本设计提供的是：

- 应用前整体预检。
- 每个文件的原子替换。
- 每步持久化日志。
- 全部验证后才宣告撤销成功。
- 中断后可确定继续或取消。

## 13. 崩溃与中断恢复

启动时扫描未终态撤销操作，将它们标记为 `interrupted`。根据项目崩溃恢复规则，不自动重放文件写入或命令。

在用户明确选择前：

- 锁定该事务影响的文件路径，星瑶文件修改工具对这些路径显式拒绝。
- 允许只读检查和展示恢复详情。
- GUI 和 CLI 显示已处理文件、剩余文件和未知文件。

用户可选：

1. `continue_revert`：使用本轮开始前快照完成剩余撤销。
2. `cancel_revert`：使用撤销开始前恢复快照，把已处理路径恢复到用户点击撤销之前。

两种操作都必须先预检并使用独立一次性确认令牌。如果崩溃后文件已进入事务未知状态，进入 `recovery_required`，不直接写入，展示当前状态、两份已校验快照和人工处理指引。

## 14. 外部修改与竞态

星瑶可以严格锁定自身工作区修改流程，但无法跨平台强制阻止所有外部编辑器或进程写文件。实现必须：

- 预检时检查。
- 工作区锁内消费令牌前检查。
- 每个文件应用前检查。
- 每个文件应用后校验。
- 发现未解释变化后立即停止后续文件，进入中断恢复，不误报整体成功。

用户界面确认中明确建议撤销时暂停其他工具对目标文件的写入。

## 15. 模型记忆与审计语义

### 15.1 保留历史

撤销成功后：

- 不调用 `manager.undo_last_interaction()`。
- 不删除用户或 assistant 消息。
- 不改写 reasoning、工具参数、工具结果、diff 或历史中间字节。
- 原始 diff 仍在 GUI 中可查看，但标识为“原修改·已撤销”。

### 15.2 持久化纠正记录

文件最终校验成功后，在同一数据库事务中提交检查点 `reverted`、操作 `committed` 和 `workspace_corrections` 记录。

纠正记录表达：

- 哪个回合的文件结果已失效。
- 影响的文件和撤销时间。
- 原回合的对话仍表示历史上曾执行过操作。
- 通用命令和非文件副作用不因文件撤销而消失。
- 继续相关工作前必须重新读取当前文件。
- 目标回合之后是否还存在其他已完成修改回合；存在时提示这些后续结果可能在语义上依赖已撤销内容，需要重新检查或运行测试。

### 15.3 动态上下文

`build_dynamic_prompt` 从纠正表构造紧凑块，示例：

```text
<workspace_correction_ledger>
回合 7f0c7724（完整 ID：7f0c7724-6087-4e08-9c87-c2e65f2bf669）的文件修改已由用户撤销。
影响文件：core/tools.py、gui_bridge.py 等 4 个文件。
该回合历史消息仍表示曾执行过操作，但它的文件结果已失效。
终端命令和外部副作用没有随文件恢复。
继续相关工作前必须重新读取磁盘文件。
</workspace_correction_ledger>
```

- 这是按当前规范化工作区变化的动态信息，禁止进入稳定 system prompt。同一工作区的其他会话也必须看到相关纠正，不能因切换会话重新相信已撤销结果；不同工作区不得串入。
- 最近记录可列文件；较旧记录使用回合 ID、时间和数量摘要，完整详情通过状态查询取得。
- `interrupted` 时动态块必须表达“工作区可能处于部分恢复状态”，工具管线同时拒绝修改受影响路径。
- 不因纠正上下文调整 Provider 历史字节、tools 顺序或缓存亲和材料。

## 16. GUI 设计

### 16.1 回合身份

- 后端 `turn_start` 事件必须携带完整 `turn_id`。
- 本轮的用户消息、assistant 消息、工具跟踪和 diff 全部绑定同一 `turn_id`。
- `TurnGroupInfo` 增加权威 `turnId`，不使用数组下标或“当前最近回合”定位。
- 消息与回合的关联必须持久化到 `message_turn_links`，会话历史加载后仍能按相同 `turn_id` 还原卡片；不得只保存在 Pinia 或实时事件内。
- 会话历史加载后批量获取撤销状态和每轮净变更摘要，不为每张卡片发生 N+1 请求。
- 回合运行中可使用实时 `diff_ready` 展示过程；检查点进入 `ready` 后，卡片的文件数、净增删数和文件列表必须以 `turn_undo_files` 的最初 `before` -> 最终 `after` 摘要为准，不继续累加前端临时 diff。
- 历史 diff 在用户展开单个文件时按 `file_id` 惰性请求，由后端从 `before`/`after` blob 生成有上限的统一 diff。前端不提交任意路径来读取快照。

### 16.2 卡片布局

`ChangedFilesPanel` 头部拆分为展开区和独立操作区，禁止在一个 `<button>` 内嵌套撤销按钮：

```text
+-------------------------------------------------------+
| [file] 已编辑 4 个文件                   撤销  ↶ |
|        +10 -10                                       |
+-------------------------------------------------------+
```

左侧点击展开现有 diff，右侧撤销按钮只调用按回合预检。本功能不要为模仿截图额外创建无需求的“审核”功能。

### 16.3 GUI 状态

| 服务状态 | 显示 | 可操作 |
|---|---|---|
| `recording` | 不显示撤销 | 否 |
| `ready` | `撤销 ↶` | 可预检 |
| `no_changes` | 不显示文件撤销卡片 | 否 |
| 前端请求中 | `正在检查…` | 否 |
| `conflicted` | `撤销受阻` | 可查详情/重新检查 |
| `reverting` | `正在撤销…` | 否 |
| `recovering` | `正在恢复撤销事务…` | 否 |
| `reverted` | `已撤销` | 不可重复写入 |
| `interrupted` | `撤销中断` | 查看恢复选项 |
| `failed` | `撤销失败` | 可重新预检 |
| `unavailable` | `不可撤销` | 只看原因 |
| `ready + snapshot expired` | `撤销记录已过期` | 否 |
| `reverted + snapshot expired` | `已撤销 · 原 diff 已过期` | 否 |

### 16.4 确认弹窗

无冲突时显示：

- 回合标识与简短描述。
- 文件总数、恢复原内容、删除本轮新建、恢复本轮删除的数量。
- 将删除的新建文件清单。
- “聊天历史保留，模型将记住文件结果已失效”。
- 如果有通用命令，必须显示未覆盖副作用警告。
- 如果目标之后还有该工作区的完成回合，显示后续回合数量与“可能存在语义依赖，撤销后请重新检查/测试”；不伪称系统能自动判断跨文件依赖。
- 建议暂停外部编辑器写入。
- 默认焦点不在破坏性按钮上；确认文案为“撤销本轮修改”，不用模糊的“确定”。

有冲突时不显示执行按钮，显示冲突文件、预期状态、当前状态和“本次没有修改任何文件”。不提供强制覆盖。

### 16.5 成功后

- 卡片标题改为“已撤销 N 个文件”。
- 原增删统计前加“原修改”，diff 仍可展开。
- 按钮变为不可点击的“已撤销”，展示撤销时间。
- 显示一次轻量通知，不伪造新的用户或 assistant 聊天消息。
- 页面刷新、会话切换和应用重启后状态不变。

### 16.6 前端线程与可访问性

- 工作线程只推送事件；`evaluate_js` 仍只由 `gui-js-dispatcher` 单消费线程执行。
- 首次点击立即进入检查中，但幂等保证必须来自后端。
- 按钮提供 `aria-label="撤销本轮文件修改"`，支持 Enter/Space。
- 弹窗打开时焦点进入弹窗，关闭时回到原操作位置。
- 不存在嵌套交互元素，支持 `prefers-reduced-motion`。

## 17. CLI 设计

### 17.1 回合结束摘要

当检查点进入 `ready` 时，在最终回答后显示：

```text
文件修改

4 个文件已编辑  +10 -10
core/tools.py                         +4 -2
gui_bridge.py                         +3 -3
frontend/src/components/App.vue       +2 -4
tests/test_turn_undo.py               +1 -1

可撤销本轮修改：/undo 8f4a2c1d
```

- 文件超过 5 个时显示前 5 个和“还有 N 个文件”。
- 有通用命令时补充未覆盖副作用警告。
- 不创建本项目之前不存在的 `/review` 命令。
- 后台回合线程不直接 `print_formatted_text`，通过 prompt_toolkit 主循环线程安全调度。

### 17.2 命令

```text
/undo                         # 预检并确认最近可撤销回合
/undo <turn_id>               # 预检并确认指定回合
/undo list                    # 列出当前会话检查点
/undo preview <turn_id>       # 只预览影响
/undo status <turn_id>        # 查看详细状态
/undo recover <operation_id>  # 预览中断恢复选项
```

`/undo` 确认默认为 `N`。不提供 `--force` 或永久 `--yes`。本功能不开放可将确认令牌写入命令行或日志的非交互脚本化执行；如日后需要 headless API，必须单独设计本地身份认证和密钥传递，不复用 CLI 人机确认令牌。

短 `turn_id` 只在当前会话内唯一时接受；存在多个匹配时显式要求完整 ID。

无参数 `/undo` 只选择最近一个 `ready` 检查点，跳过 `recording`、`no_changes`、`unavailable`、已撤销和后台仍运行的检查点；`/undo list` 仍如实展示这些状态。后台任务使用独立回合标识和“后台任务”来源标签。

### 17.3 冲突与幂等输出

- 冲突时显示每个文件的预期节点和当前节点，明确“本次没有修改任何文件”。
- 撤销成功时显示恢复、删除新建和恢复删除的数量，提示聊天历史保留。
- 重复调用已 `reverted` 回合返回幂等成功摘要，不再修改文件。
- 中断时显示操作 ID、已处理文件和 `/undo recover` 指引，不静默重试。
- 撤销非最新回合时显示后续回合依赖警告，与 GUI 和自然语言权限卡一致。

## 18. 自然语言操作

当用户明确说“撤销刚才这轮文件修改”时，不让模型使用 `write_file`/`edit_file` 根据历史 diff 自行反向编辑。

如现有工具注册表没有可复用的结构化应用操作入口，新增单一 `undo_turn` 工具：

- 参数只允许“最近已完成回合”或明确 `turn_id`，不接收文件路径、`force` 或任意撤销参数。
- 工具选择检查点后由 `TurnUndoService` 预检。
- 影响摘要进入现有权限中介卡片；用户同意后，管线在内部消费一次性令牌。
- 权限卡必须展示目标之后的已完成回合数量和语义依赖警告，不能只报告路径冲突。
- 令牌不返回给模型，不进入工具结果或消息历史。
- 权限拒绝后零文件变化。
- 工具只返回结构化结果摘要，模型不自行补救或强制恢复。

新工具会影响 tools schema，实施前必须先运行 Provider 请求 byte-golden 与 prompt byte-stability 回归，保持工具顺序和稳定字节。如现有黄金字节规则与必需的新工具存在不可兼容冲突，开发 Agent 必须停止并报告，不得为迁就实现擅自改写黄金基线。

## 19. 服务 API

```python
class TurnUndoService:
    def begin_turn(self, session_id: int, turn_id: str, workspace_root: str, *, owner_kind: OwnerKind, parent_turn_id: str | None = None): ...
    def finish_turn(self, session_id: int, turn_id: str): ...
    def preview(self, session_id: int, turn_id: str) -> TurnUndoPreview: ...
    def execute(self, session_id: int, turn_id: str, preview_token: str) -> TurnUndoResult: ...
    def list_turns(self, session_id: int) -> list[TurnUndoSummary]: ...
    def get_status(self, session_id: int, turn_id: str) -> TurnUndoDetails: ...
    def get_file_diff(self, session_id: int, turn_id: str, file_id: str) -> TurnFileDiff: ...
    def preview_recovery(self, session_id: int, operation_id: str, action: RecoveryAction) -> RecoveryPreview: ...
    def execute_recovery(self, session_id: int, operation_id: str, action: RecoveryAction, preview_token: str) -> RecoveryResult: ...
```

### 19.1 GUI Bridge 窄接口

```text
list_turn_undo_states(session_id)
get_turn_undo_status(session_id, turn_id)
get_turn_undo_file_diff(session_id, turn_id, file_id)
preview_turn_undo(session_id, turn_id)
execute_turn_undo(session_id, turn_id, preview_token)
preview_turn_undo_recovery(session_id, operation_id, action)
execute_turn_undo_recovery(session_id, operation_id, action, preview_token)
```

Bridge 验证会话可访问性，将前端会话名解析为现有 `sessions.id`，但不复制文件检查和事务逻辑。前端会话 DTO 应补充稳定 `session_id`，同时保留 `session_name` 作为展示字段。`list_turn_undo_states` 批量返回状态和文件摘要，不携带大块 diff；`get_turn_undo_file_diff` 只接受归属于该检查点的 `file_id`，返回有展示上限的 diff 或二进制摘要。

所有状态 DTO 同时返回 `status`、`snapshot_availability` 和 `record_version`；前端不得把组合展示状态反写成新的后端生命周期枚举。

### 19.2 结构化错误

所有入口返回稳定 `code`，例如：

- `checkpoint_not_found`
- `checkpoint_unavailable`
- `checkpoint_expired`
- `file_conflict`
- `workspace_busy`
- `token_expired`
- `token_already_used`
- `token_scope_mismatch`
- `operation_scope_mismatch`
- `snapshot_missing`
- `snapshot_corrupt`
- `unsupported_node_kind`
- `revert_interrupted`
- `recovery_required`
- `recovery_operation_cycle`
- `invalid_state_transition`

GUI 和 CLI 不从人类文本解析业务状态。

## 20. 事件协议

### 20.1 `turn_start`

增加 `turn_id` 和稳定 `session_id`，同时保留当前 `session_name` 用于展示和现有前端路由。所有后续回合事件使用这两个显式字段，禁止再从 `turn_id` 字符串前缀推导会话。现有 `_session_from_turn_id()` 不得作为新撤销协议的身份源。

### 20.2 `turn_undo_updated`

```json
{
  "session_id": 42,
  "session_name": "当前会话名",
  "turn_id": "7f0c7724-6087-4e08-9c87-c2e65f2bf669",
  "operation_id": "undo-operation-id",
  "status": "reverted",
  "file_count": 4,
  "reverted_at": "2026-09-03T21:36:00+08:00",
  "message": "本轮 4 个文件修改已撤销"
}
```

事件只包含展示摘要，不包含原始快照、确认令牌或敏感文件内容。数据库提交成功后才发送 `reverted`。

后台任务事件额外包含只读 `owner_kind=background_task` 和父回合完整 `parent_turn_id`，两者均由后端检查点关系生成，不接受前端回传值。

## 21. 并发与锁

固定顺序：

```text
获取规范化工作区独占协调锁
  -> 锁内查询活跃回合/进程状态
  -> 短数据库事务验证状态与令牌
  -> 文件 I/O
  -> 短数据库事务推进状态
  -> 释放工作区锁
  -> 发送 UI/CLI 事件
```

- 同一工作区的不同会话共享同一锁和活跃回合判定。
- 所有受控文件工具在 `prepare -> 实际写入 -> verify` 的完整区间也使用同一个工作区协调器；开始新修改和开始撤销必须在同一把锁内互斥判定，不能依赖锁外先查状态。
- 不同工作区允许并行。
- 数据库连接锁内禁止等待工作区锁。
- GUI 队列锁、`_delta_lock` 或终端渲染锁内禁止执行恢复。
- 中断事务冻结每个目标路径及会间接影响它的父/子路径操作：修改目标文件、删除或移动其父目录、将目录覆盖到其上级位置等都必须拒绝。冻结判定使用规范化路径包含关系，不只比较字符串相等。
- 中断事务存在时，星瑶在该工作区的通用终端命令也必须拒绝，因为命令可绕过文件工具冻结。这不能阻止用户在外部终端修改，因此恢复预检仍必须检测外部变化。
- 冻结不无限扩大到整个用户主目录或无关工作区。
- 工作区锁的身份必须来自规范化真实路径和平台大小写规则，覆盖相对路径、目录符号链接、Windows 驱动器号大小写和可识别的 UNC 别名，避免同一目录获得多把锁。

## 22. 权限、路径与隐私

- GUI 点击和 CLI 显式确认只授权恢复该检查点中已记录的精确规范化路径。
- 不用一个广泛 `sandbox_bypass()` 包裹前端提供的任意路径。
- 工作区外的历史授权写入只能恢复原检查点中的同一规范化路径，不能转移到新路径。
- 执行前重新解析路径。大小写折叠、符号链接变化、路径穿越或工作区身份变化全部视为冲突。
- 日志不包含原始文件内容、令牌、凭据或不必要的工作区外绝对路径。
- GUI 对文件的展示优先使用工作区相对路径。

## 23. 旧功能迁移

### 23.1 旧内存检查点

旧 `_session_checkpoints` 没有修改后指纹、持久化快照与事务日志，不能伪造成新格式。

- 功能上线前产生的历史卡片显示“不可撤销”。
- `/checkpoint restore` 对新检查点改为调用 `TurnUndoService`。
- 旧记录显示“缺少安全校验信息”，不沿用 `--force`。

### 23.2 旧单文件撤销

1. 先将 GUI、CLI 和回合检查点全部迁移到新服务。
2. 在同一完整功能交付中删除 `LAST_UNDO_STATE`、`undo_last_edit()` 的单文件恢复逻辑和 GUI `undo_last_edit` Bridge 入口。不留一个无明确结束条件的“兼容周期”。
3. 如存在经证实的外部 Python 调用方依赖函数名，可保留同名废弃适配器，但它只能返回明确迁移错误，不得执行文件写入或跳过新的两段式确认。
4. 新实现不存在旧、新两个撤销系统同时写文件的旁路。

## 24. 启动与运行时恢复

- 启动数据库迁移后，校验非终态操作和快照引用。
- 将未终态操作标记为中断，不自动进行文件写入。
- 检查到快照缺失或损坏时保留元数据和明确错误，不删除证据。
- GUI 启动后显示中断操作提醒；CLI 在进入主交互后显示一次摘要。

## 25. 测试设计

### 25.1 单元测试

- 状态值对象与非法迁移。
- 路径规范化、大小写、目录符号链接、UNC 别名、最终路径符号链接和特殊文件拒绝。
- 内容寻址写入、去重、哈希校验、引用和 GC。
- 同一文件一轮修改一次和多次。
- 新建、删除、重命名、空文件、非 UTF-8 和二进制文件。
- 一次性令牌过期、重复、跨会话、跨回合和指纹变化。
- 恢复操作 ID 跨会话调用被 `operation_scope_mismatch` 拒绝。
- 结构化错误码和敏感数据脱敏。

### 25.2 服务与事务测试

- 多文件全部成功。
- 任一文件预检冲突时零写入。
- 预检后、执行前文件变化。
- 在 `prepared`、第 N 文件、最终验证和提交前注入崩溃。
- 中断后继续撤销与取消撤销。
- 崩溃后文件外部变化进入 `recovery_required`。
- 快照失败、磁盘空间不足、数据库失败和最终校验失败。
- 已撤销重复调用幂等。

### 25.3 并发测试

- 同会话重复点击。
- 会话改名后依靠 `sessions.id` 仍能撤销原回合，且不从 `turn_id` 前缀推导旧会话名。
- 消息持久化时同步写入 `message_turn_links`，重启后 GUI 仍能精确重建回合卡片，而 Provider 消息字节不变。
- 消息正文和关联行在同一事务提交；任一写入失败时两者一起回滚。
- 不同会话指向同一工作区。
- 不同工作区并行撤销。
- 主回合和子代理正在运行。
- 同步前台子代理将修改记录到父回合。
- 后台写文件任务从启动时使用独立检查点，并通过 `parent_checkpoint_id` 关联来源回合。
- 父回合完成后的迟到写入不能取得有效句柄，且在触盘前失败。
- 零受控文件修改回合进入 `no_changes`，不会被无参数 `/undo` 选中，也不显示空卡片。
- GUI 切换会话时事件不串卡片。

### 25.4 记忆与 Harness 回归

- 动态上下文包含准确纠正，不夸大非文件副作用。

### 25.5 GUI 测试

- 撤销按钮与展开区不嵌套、不互相触发。
- 全部状态、弹窗、冲突、失败、中断和成功卡片。
- 重复点击、事件幂等、页面刷新、会话切换和应用重启。

### 25.6 CLI 测试

## 28. 完成定义

只有同时满足以下条件才算完成：

- GUI、CLI 和自然语言入口共用同一服务且实际恢复磁盘文件。
