# 星瑶按回合撤销工作包

状态：待开发  
设计日期：2026-09-03  
目标：为星瑶 GUI、CLI 和用户自然语言操作增加安全、持久化、可审计的“按回合撤销文件修改”能力。

## 文件说明

- [01-完整设计规格.md](01-完整设计规格.md)：产品语义、数据模型、快照记录、恢复事务、记忆处理、GUI、CLI、并发、安全、迁移和测试的唯一需求基线。
- [02-Agent开发提示词.md](02-Agent开发提示词.md)：可直接交给主开发、代码评审、修复和最终验收 Agent 的提示词。
- [03-验收清单.md](03-验收清单.md)：功能、安全、并发、崩溃恢复、记忆、GUI、CLI 和回归验收项。

## 使用顺序

1. 开发 Agent 先完整阅读本 README、完整设计规格与验收清单。
2. 使用“主开发 Agent 提示词”执行实施，实施过程维护持久化计划与进度。
3. 开发完成后，使用独立代码评审 Agent 按规格检查，不边评边改。
4. 修复已确认问题后，使用最终验收 Agent 逐项关闭 [03-验收清单.md](03-验收清单.md)。
5. 只有所有适用验收项通过，才能声称功能完成。

## 不可改变的产品决定

1. “撤销”以现有 `sessions.id` 不可变主键与全局唯一 `turn_id` 为单位，一次恢复该回合记录的全部受控文件修改；会话改名不影响归属，不从 `turn_id` 前缀推导会话。
2. GUI、CLI 和自然语言操作共用同一个 `TurnUndoService`，不维护多套恢复逻辑。
3. 撤销前必须检查所有目标文件的实际指纹；任一冲突都拒绝整轮执行，不强制覆盖、不自动部分撤销。
4. 文件修改前必须先持久化原始字节快照；快照失败时文件修改也必须失败。
5. 只对能在修改前取得精确快照的受控文件工具提供严格撤销保证。通用终端命令和其他外部副作用必须明示为不在撤销范围内。
6. 撤销后保留聊天历史、reasoning 和工具结果，不调用 `undo_last_interaction()` 删除对话，不改写历史中间字节。
7. 撤销事实持久化到数据库，并通过动态上下文告知模型该回合的文件结果已失效。
8. 多文件恢复使用持久化事务日志和每文件原子替换；崩溃后不自动重放文件写入，必须显式显示中断状态并由用户选择继续或取消。
9. GUI 高风险确认与 CLI 交互确认都不是唯一安全门禁；后端必须验证一次性预检令牌并再次检查文件。
10. 旧回合缺少持久化快照和修改后指纹时显示“不可撤销”，不猜测、不伪造、不沿用旧 `--force` 覆盖；完整交付中删除旧单文件恢复逻辑，不留双写兼容期。
11. 撤销成功后原始 diff 仍可审计，GUI 卡片改为“已撤销”，CLI 重复调用返回幂等成功而不再写文件。
12. 不实施 MVP 或分版缩水；开发可分阶段提交，最终交付必须闭合完整规格。
13. 遵守 Let it crash：不静默降级、不模糊后处理、不误报撤销成功。
14. 撤销生命周期与快照保留状态分开；快照过期不能抹掉“已撤销”审计事实。
15. 同一工作区的模型纠正跨会话生效但不串工作区；撤销较早回合时明确警告后续回合可能存在语义依赖。

## Git 分支约束

项目 `AGENTS.md` 规定日常代码拉取与提交只在 `dev` 分支进行。开发 Agent 开始修改前必须检查当前分支和工作区；若不在 `dev`，不得在当前分支提交，不得擅自合并、重置或丢弃用户修改。

该任务属于中大型实施，必须先写持久化实施计划、再按可验证阶段开发，但阶段不代表可删减任何已确认需求。
