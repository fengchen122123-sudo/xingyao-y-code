# Agent 开发提示词

以下提示词按角色分开使用。相对路径均以 Y-CODE 项目根目录为基准。

## 一、主开发 Agent 提示词

```text
请在当前 Y-CODE 项目中完整实现“星瑶按回合撤销”。

开始前必须完整阅读：
1. AGENTS.md
2. 待开发/星瑶按回合撤销/README.md
3. 待开发/星瑶按回合撤销/01-完整设计规格.md
4. 待开发/星瑶按回合撤销/03-验收清单.md

分支与工作区：
- 先执行 git status 和 git branch --show-current。
- 项目规定日常开发与提交只在 dev 分支进行。若不在 dev，不得在当前分支提交，不得擅自合并、重置或丢弃用户修改，请先报告。
- 保留所有无关已有修改，只对本功能做小而可审查的改动。

工程方法：
- 这是中大型任务。先按设计规格写可执行实施计划，并持续更新 `待开发/星瑶按回合撤销/实施进度.md`。
- 实施前盘点 core/memory.py、core/agent_service.py、core/tools.py、core/harness/、core/tool_pipeline.py、gui_bridge.py、main.py、frontend/src/stores/appStore.ts、frontend/src/utils/turnGroups.ts、TurnGroup.vue、ChangedFilesPanel.vue 和相关测试。
- 必须使用测试驱动开发：先写能正确失败的测试，再实现最小严格逻辑，然后重构。
- 不做 MVP、不使用内存状态假装持久化、不用 Git diff 代替原始快照。
- 严格遵守 Let it crash：状态错误、快照错误、指纹冲突、数据库错误和恢复中断全部显式失败，不静默降级或事后猜测补救。

不可改变的语义：
- 撤销单位是现有 sessions.id 不可变主键 + 全局唯一 turn_id 下的整轮受控文件修改。新 turn_id 使用完整 128 位随机 UUID 并作为不透明值；会话改名不影响归属，不从 turn_id 前缀推导会话。
- 任一文件当前状态与该回合最后修改后指纹不一致时，本次零文件撤销。不强制、不部分执行。
- 文件工具必须在写入前成功持久化原始字节和元数据。快照失败则修改失败。
- 只对受控工具提供严格保证。通用终端命令与其他非文件副作用必须明示为不可撤销。
- 撤销不删除聊天、reasoning、工具结果或 diff，不调用 undo_last_interaction()。
- 撤销事实持久化到独立纠正记录，由 build_dynamic_prompt 告知模型，不放入稳定 system prompt。
- 崩溃后不自动重放文件写入。必须标记 interrupted，冻结影响路径，由用户显式选择继续或取消。
- GUI、CLI 和自然语言工具共用 TurnUndoService。

实施要求：
1. 新增职责清晰的 core/turn_undo/ 包，不将业务逻辑堆进 gui_bridge.py 或 main.py。
2. 新增幂等 SQLite 迁移，外键使用现有 sessions.id，并用 message_turn_links 将消息规范化关联到 checkpoint_id，再由检查点取得 turn_id。重排 GUI/CLI 开始顺序：先解析工作区、确保 session、生成 turn_id 并创建 checkpoint，再原子提交用户消息+link，随后发送含稳定 ID 的 turn_start。Harness 的 messages+events 提交事务也同步写 link，禁止按时间回填。按项目约定锁和 commit；不将原始文件字节、令牌或敏感信息写入 Harness Journal。Provider 历史构造必须忽略 GUI 回合元数据，保持消息字节不变。
3. 实现流式 SHA-256 内容寻址快照，原子写入、校验、去重、引用与安全 GC。撤销生命周期与 SnapshotAvailability 正交，快照过期不得覆盖 reverted 审计事实。
4. 实现 FileMutationRecorder。受控工具在写入前必须提供完整 PlannedPathMutation，记录器先持久化最初 before 和计划 after blob，再返回写入句柄；写入后立即验证实际状态与计划一致。同一文件一轮保留最初 before 和最终 after。
5. 接入所有第一方文件修改工具和子代理；同步前台子代理共享父检查点，可能迟于父回合结束的后台写文件任务必须从启动时拥有独立检查点和 turn_id，并关联 parent_checkpoint_id。封闭检查点在触盘前拒绝迟到写入。新工具声明可撤销却未接入时必须有校验失败。
6. 实现按规范化真实路径互斥的 coordinator，正确处理相对路径、大小写、目录符号链接和可识别 UNC 别名。受控工具的 prepare/write/verify 与撤销共用同一协调锁并在锁内判定活跃状态；同工作区多会话不能并行修改/撤销，不同工作区允许并行。
7. 实现两段式 preview + 一次性令牌。令牌绑定会话、回合、工作区、record_version、指纹和当前 boot_id，后端锁内重算指纹后以 CAS 消费；重启后旧令牌失效。
8. 实现持久化多文件事务、每文件原子替换、隔离新建文件、每步落库、最终校验和中断恢复。continue/cancel 每次建立带 parent_operation_id 的独立恢复操作；提交时原子解决父操作，拒绝跨检查点关系与循环链。
9. 不宣传多文件操作系统级绝对原子性；外部编辑竞态需多次检查并明确暴露剩余边界。中断恢复期间必须拒绝对影响路径有父/子包含关系的文件工具操作，并拒绝该工作区的通用终端命令。
10. GUI 卡片使用权威 turn_id，回合完成后使用持久化 before/after blob 生成的净 diff 和净增删统计，历史文件 diff 按 file_id 惰性读取。头部展开区与撤销按钮分离，不创建与本需求无关的“审核”功能。撤销非最新回合时，GUI、CLI 和自然语言权限卡统一提示后续回合可能存在语义依赖。
11. GUI evaluate_js 只能走现有 gui-js-dispatcher。后台线程禁止直接操作全局布局或在 _delta_lock 内触碰 JS。
12. CLI /undo 升级为按回合撤销，默认确认为 N，不提供 --force。/checkpoint restore 迁移为新服务兼容入口。
13. CLI 后台状态使用 app_instance.loop.call_soon_threadsafe(...) 调度到 prompt_toolkit 主线程。
14. 自然语言入口使用单一结构化 undo_turn 工具与权限管线，模型不接触一次性令牌，不允许任意路径或 force。
15. 涉及 tools schema 前先运行 Provider byte-golden 与 prompt byte-stability。如与黄金基线存在不可兼容冲突，停止并报告，不擅自改写黄金字节。
16. 更新 frontend/src/types/pywebview.d.ts、Pinia store、事件类型、组件测试、/help 和用户可见文档。

验证：
- 完成设计规格第 25、26 节所有适用测试。
- 运行 Python 语法检查、新增单元/事务/崩溃测试、现有 Agent/GUI/子代理/消息/Harness 回归、前端测试和 npm run build。
- 对文件操作的崩溃注入要覆盖每个状态边界，不能只测试理想路径。
- 最终逐项更新 03-验收清单.md，每个勾选项附真实测试或人工验证证据。

交付报告必须包含：
- 结果摘要
- 架构与关键安全落点
- 变更文件列表
- 自动化验证命令和实际结果
- 验收清单状态
- 风险、假设和未完成项（没有则明确写“无”）
- 实际使用的 skill

功能未完整、事务/冲突/崩溃测试未通过或验收清单未闭合时，不要声称完成。
```

## 二、代码评审 Agent 提示词

```text
请对当前分支中“星瑶按回合撤销”做严格只读代码评审，不要直接修改代码。

必须完整阅读：
- AGENTS.md
- 待开发/星瑶按回合撤销/README.md
- 待开发/星瑶按回合撤销/01-完整设计规格.md
- 待开发/星瑶按回合撤销/03-验收清单.md

先检查 git status、当前分支、完整 diff、实施进度、新增测试和实际测试输出。

重点评审：
1. 是否用内存 checkpoint、Git diff、终端命令猜测、TODO 或占位按钮冒充完整实现。
2. GUI、CLI、自然语言是否真正共用 TurnUndoService，而非存在多套文件恢复逻辑。
3. sessions.id + turn_id 是否是权威定位，会话改名和应用重启后是否仍正确；GUI/CLI 是否在用户消息和 turn_start 之前创建 checkpoint，message_turn_links 是否在消息同事务覆盖本轮持久化消息，是否仍存在事后按时间回填、从 turn_id 前缀推导会话、“最近修改”或数组下标串回合风险。
4. 原始字节快照是否在写入前原子持久化、校验，失败时是否真的阻止文件修改。
5. 同一文件一轮多次修改是否保留最初 before 并更新最终 after。
6. 所有第一方文件工具、子代理、删除、重命名和补丁路径是否接入记录器；后台写文件任务是否拥有独立检查点，封闭检查点是否在触盘前拒绝迟到写入。
7. 是否把通用终端命令副作用错误宣称为可撤销，或在 GUI/CLI/权限卡遗漏警告。
8. 预检是否覆盖存在性、节点类型、内容哈希、符号链接和工作区身份；任一冲突是否零写入。
9. 一次性令牌是否绑定全部上下文、只保存哈希、过期、单次消费、锁内再检查，且不进入模型历史和日志。
10. 多文件事务是否保存撤销开始前状态、每文件原子替换、每步落库、最终验证后才宣告成功。
11. 所有状态边界是否有崩溃注入，启动是否仅标记中断而不自动重放文件写入。
12. continue_revert 和 cancel_revert 是否都显式校验 session_id + operation_id 归属、使用新预检与一次性令牌；未知状态是否进入 recovery_required。
13. 锁顺序是否存在数据库/工作区/GUI 死锁；相对路径、大小写、目录符号链接或 UNC 别名是否能让同一工作区获得多把锁；不同工作区是否被误阻塞。
14. 路径穿越、大小写折叠、符号链接变化、工作区外历史授权和前端伪造路径是否可导致越权恢复。
15. 撤销是否保留原消息与 diff，纠正记录是否只在文件验证成功后提交；纠正是否按工作区跨会话可见但不串工作区，动态上下文是否遗漏“非文件副作用不撤销”和后续回合语义依赖。
16. GUI 是否存在嵌套按钮、重复点击竞态、事件串会话、刷新状态丢失、非 dispatcher evaluate_js 或在 _delta_lock 中触碰 JS。
17. CLI 是否仍保留 --force、确认默认 Y、后台线程直接渲染，或创建了规格之外的 /review 命令。
18. undo_turn 工具是否只允许回合标识、通过权限管线、不向模型暴露令牌，并保持 Provider/tools/prompt 稳定性要求。
19. 旧 LAST_UNDO_STATE、undo_last_edit() 的单文件写入逻辑和 GUI Bridge 入口是否在完整交付中删除；/checkpoint restore 是否存在旧 force 或把旧内存快照伪造成新安全记录。
20. 零受控文件修改回合是否进入 no_changes，且不会显示空卡片或被无参数 /undo 选中；消息与 message_turn_links 是否同事务提交。
21. 状态机是否拒绝非法跳转，record_version 是否真实存在并用 compare-and-swap 约束令牌消费，快照过期是否错误覆盖 reverted。
22. 测试是否包含真实文件系统、线程竞态、重启、故障注入和完整回归，而非仅 mock 理想路径。

只报告可操作、有证据的问题，按严重级别排序。每个问题包含：文件与精确行号、触发场景、用户/数据风险、违反的规格和最小修复方向。如无问题，明确说明仍存在的测试或环境不确定性。

报告本次实际使用的 skill。
```

## 三、评审修复 Agent 提示词

```text
请根据已有“星瑶按回合撤销”代码评审结论修复已确认问题。

必须完整阅读 AGENTS.md、设计规格、验收清单、实施 diff 和原始评审意见。不要盲目接受评论；先用代码、测试和最小复现验证每个问题，只修复技术上成立的问题。

要求：
- 保持 GUI、CLI、自然语言入口共用 TurnUndoService，不因修复引入快捷旁路。
- 不引入 force、部分撤销、自动重放、静默降级或后发式补救。
- 冲突、快照、令牌、事务、路径和记忆语义修复必须有先失败后通过的针对性回归测试。
- 不修改无关代码，不重置、丢弃或覆盖用户已有修改。
- 如评审意见与设计冲突，或修复需要扩大权限/范围，停止并报告，不自行改变产品语义。

修复后运行针对性测试、相关回归、前端测试与构建，并报告：逐条评审意见的验证结论、修复文件、测试证据、剩余风险和实际使用的 skill。
```

## 四、最终验收 Agent 提示词

```text
请对“星瑶按回合撤销”做最终只读验收。不要修改代码，不要因为时间或测试成本而跳过高风险项。

必须完整阅读：
- AGENTS.md
- 待开发/星瑶按回合撤销/README.md
- 待开发/星瑶按回合撤销/01-完整设计规格.md
- 待开发/星瑶按回合撤销/03-验收清单.md
- 实施进度、代码评审结论与修复记录

验收流程：
1. 检查 git status、当前分支、改动范围和无关用户修改是否被保留。
2. 建立规格条目到实现文件、测试和验证证据的映射。
3. 实际运行设计规格第 25、26 节的所有适用自动化测试，包括崩溃注入、并发、重启、Provider/prompt 稳定性、前端测试和构建。
4. 实际人工验证 GUI 卡片、预检弹窗、冲突、已撤销、中断恢复、会话切换和重启状态。
5. 实际人工验证 CLI /undo 系列、默认 N、短 ID 歧义、无 force、GUI/CLI 同步和主线程渲染。
6. 验证自然语言 undo_turn 走权限管线、不暴露令牌、不能传任意路径或 force。
7. 逐项核对 03-验收清单.md。只有存在实际证据的项目才能标记通过。

必须特别验证：
- 快照失败时文件没有被修改。
- 任一文件冲突时整轮零写入。
- 预检后变化文件会使执行失败。
- 崩溃后不自动重放，受影响路径被冻结，继续/取消均有二次预检。
- 撤销不删除聊天，模型后续看到纠正记录并重读文件。
- 通用命令副作用不被误报为已撤销。
- GUI、CLI 和自然语言不存在任意路径、force 或旧单文件旁路。
- 重启后检查点、已撤销卡片、中断事务和记忆纠正都持久存在。

最终报告格式：
- 结论：通过 / 不通过
- 阻断问题（文件、行号、复现、风险）
- 自动化验证命令与真实输出摘要
- 人工验收结果
- 验收清单未关闭项
- 剩余风险和环境限制
- 实际使用的 skill

任一核心安全语义、崩溃恢复、持久化记忆、GUI/CLI 实际入口或回归测试未闭合，结论必须为“不通过”。
```
