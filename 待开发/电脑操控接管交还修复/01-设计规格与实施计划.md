>
> 工作包：**电脑操控"接管—交还"修复**——让用户手动接管结束后，星瑶在下一回合能自动交还并继续操控同一页面，且任意收尾路径都不留下活租约。

---

## 一、现象

用户在右侧面板手动接管（模型调用 `request_user_takeover`）→ 用户操作完成 → 在对话里说"继续" → 星瑶**所有 `computer_action` 调用失败**（表现为"被我接管无法操作"），必须用户在界面上**手动点一次停止**才能恢复。

关键特征：故障不是一次性的调用报错，而是**整个会话的电脑操控能力持续失效**，且缺少任何自愈出路。

---

## 二、根因（已用代码与日志双重确认）

根因是一条完整的失效链，共 5 环：

| 环 | 位置 | 事实 |
| --- | --- | --- |
| 1 | `core/computer/controller.py:1005-1011` | `request_user_takeover` 把 run 转为 `waiting_for_user` 并置 `require_observe=True`（**此步正确**） |
| 2 | `core/llm.py:2991-2992` | 回合以正常文本收尾时，把 `computer_exit_kind` 置为 `completed` |
| 3 | `core/llm.py:1464-1467`、`core/computer/controller.py:1050`、`:1075`、`core/computer/controller.py:57-59`、`core/llm.py:1473-1477` | 对 `completed` 一律调 `complete_run`；而 `complete_run` 第一步是 `_transition(run, COMPLETING)`；转移表中 `waiting_for_user` 只允许 `running`/`stopping`/`failed`，`completing` 非法 → 抛 `computer_invalid_state`，被吞成一条 warning，**run 既未终结也未清理** |
| 4 | `core/computer/controller.py:397-400`、`:640-646`、`core/computer/tool_adapter.py:94-98` | 排他租约只在终态释放；run 仍活着时下一回合 `start_run` 抛 `computer_session_busy` → 该 Turn 的 lease 被降级为禁用态 → `computer_action` 全部返回稳定失败 |
| 5 | `frontend/src/stores/appStore.ts:960-966`、`core/computer/controller.py:413-420`、`:1023-1041` | 无自愈出路：前端 `waiting_for_user` 不提供"恢复"按钮，且 `controller.resume` 只改状态不换 owner，跨回合仍被 owner 校验拒绝——**所以只有 stop 能释放租约** |

逐环说明：

1. **接管态建立（正确）**：`core/computer/controller.py:1005-1011`——`request_user_takeover` 把 run 转为 `waiting_for_user`，并置 `require_observe=True`，后续动作前必须先观察。
2. **回合收尾打标**：回合以正常文本收尾时，`core/llm.py:2991-2992` 把 `computer_exit_kind` 置为 `completed`（语义上把"接管中的会话"当成了"正常完成的会话"）。
3. **非法转移被吞**：`core/llm.py:1464-1467` 对 `completed` 一律调 `complete_run`；而 `complete_run` 第一步是 `_transition(run, COMPLETING)`（`core/computer/controller.py:1050`、`:1075`）。转移表 `core/computer/controller.py:57-59` 中 `waiting_for_user` 只允许 `running`/`stopping`/`failed`，`completing` 非法 → 抛 `computer_invalid_state`，被 `core/llm.py:1473-1477` 吞成一条 warning，**run 既未终结也未清理**。
4. **租约被占死**：排他租约只在终态释放（`core/computer/controller.py:397-400`）；run 仍活着时下一回合 `start_run` 抛 `computer_session_busy`（`core/computer/controller.py:640-646`）→ 该 Turn 的 lease 被降级为禁用态 → `computer_action` 全部返回稳定失败（`core/computer/tool_adapter.py:94-98`）。
5. **无自愈出路**：前端 `waiting_for_user` 不提供"恢复"按钮（`frontend/src/stores/appStore.ts:960-966`），且 `controller.resume` 只改状态不换 owner，跨回合仍被 owner 校验拒绝（`core/computer/controller.py:413-420`、`:1023-1041`）——所以**只有 stop 能释放租约**。

**日志证据**：`C:\Users\冯晨昊\.ycode\logs\gui-runtime.log`

- 第 11174 行（2026-10-01 14:14:30）
- 第 11519 行（2026-10-01 14:26:03）

两处均为：

```
WARNING [core.llm] 电脑操控 run 收尾失败（run=… kind=completed）：非法状态转换：waiting_for_user → completing
```

## 三、修复目标

1. 用户接管结束后，只需在对话里说一声，**下一回合即可继续操控同一页面**，无需任何手动停止。
2. **结构性保证**：回合结束时不可能留下活租约（任意状态、任意异常路径）。
3. 一并修掉同类缺口：**stop 的可重入性**、**租约占用错误可诊断**、**UI 文案不误导**。

---

## 四、设计（四层）

### L1 语义修复：接管态回合收尾按"完成"处理

| 项 | 内容 |
| --- | --- |
| 转移表 | `_TRANSITIONS["waiting_for_user"]` 增加 `"completing"`。原表为计划逐字给定，此处**有意放宽**，需在注释写明理由 |
| 收尾分支 | `core/llm.py::_finalize_computer_run`：`exit_kind == completed` 时统一走 `complete_run(run_id, owner, retain_browser_session=True)`；接管态（`waiting_for_user`）无需特判——转移表放行后它自然走通同一条路径（初版曾特判 `retain=False`，已在第二轮修正中撤销） |
| 其他 exit_kind | `cancelled`/`failed`/`stopped` 保持调用 `stop()`（`waiting_for_user → stopping` 本就合法） |

**为何 `retain` 必须保持 `True`（第二轮修正）**：初版曾对 `waiting_for_user` 特判 `retain_browser_session=False`，独立审查判定这是**真回归**——`complete_run(retain=False)` 会走 `backend.close()`，而在**外部 Edge/Chrome** 上关闭 backend 会连用户此刻正在手动操作的浏览器窗口一起关掉（接管场景恰恰正在用那个窗口）。内置浏览器上 `close()` 虽只断 CDP 连接（`core/computer/browser_backend.py:1189-1193` 的 `_owns_context=False`、`core/computer/embedded_browser_backend.py` 模块 docstring），但保留会话同样无害（面板页面属于 GUI 的 WebView2 控件，与 run 无关），还能让下一回合直接复用 retained session、免去重连。故接管态与普通收尾完全一致：`retain=True`。

**下一回合路径**：新 run → `prepare_automation` 幂等返回同一 CDP endpoint（`gui_browser_mixin.py:283`）→ 新 backend 经 CDP 重连面板当前页面 → `require_observe` 保证先观察再动作。

### L2 兜底：回合结束绝不留活租约

| 项 | 内容 | 落点 |
| --- | --- | --- |
| 兜底 stop | `_finalize_computer_run` 的 **`except Exception`** 分支（第二轮修正：初版只捕获 `ComputerControlError`，非领域异常会逃逸出去并打断回合收尾）：除 warning 外，若快照仍非终态则调 `stop(run_id, "turn_end_finalize_fallback", cancel_owner=False)`，整段用 `try/except` 包裹 | `core/llm.py::_finalize_computer_run` |
| `stop` 签名扩展 | `controller.stop(run_id, reason, *, cancel_owner: bool = True)`：为 `False` 时**跳过** `owner.cancel_event.set()` 与 `_abort_streams` | `core/computer/controller.py::stop` |
| stop 幂等 | `stop` 对已处于 `stopping` 的 run **幂等返回当前快照**（现状会抛"非法状态转换：stopping → stopping"，中断清理链；日志 2026-09-10 有两条实例） | `core/computer/controller.py::stop` |

**为何 `cancel_owner=False`**：`gui_bridge.py:6220` 与 `:6377` 用该 `cancel_event` 判定回合是否被取消，收尾兜底**不得把正常结束的回合误标成"已取消"**。

**兜底覆盖面**：该兜底分支同时覆盖 `paused` 与 `starting`/`completing`/`stopping` 等一切"非终态但 `complete_run` 不可达"的情况——`paused` 只允许 `running`/`stopping`/`failed`，`complete_run` 从 `paused` 会被拒（既有契约由 `tests/test_computer_controller.py::test_complete_run_from_paused_is_rejected` 钉住），故回合结束时若用户仍按着暂停，走 L2 兜底 `stop(cancel_owner=False)` 视为停止并交还租约。这是本设计"回合结束绝不留活租约"的结构保证。**第二轮修正补充**：`except` 由 `ComputerControlError` 放宽为 `Exception`，使 `RuntimeError` 等非领域异常同样落入兜底并被 warning 记录，而不是逃逸出回合 `finally`（那会同时丢掉兜底释放和回合收尾）。

### L3 可诊断性

- `start_run` 的 `computer_session_busy` 错误：
  - `message` 追加"（当前状态：X）"；
  - `details` 增加 `owner_run_status`；
  - **保留既有** `owner_session_label`。

### L4 文案

- `frontend/src/components/ComputerControlPane.vue` 中 `waiting_for_user` 的原因行改为：

  `等待你接管：<pause_reason> · 在右侧面板操作完成后，直接在对话里说一声，星瑶会重新接管继续。`

- **不改按钮语义**（不放开"恢复"按钮，避免用户手动 `resume` 出一个 owner 已结束的 `running` run）。

## 五、状态 × 回合收尾处理对照表

| run 状态 | exit_kind=completed | 其他 exit_kind | 说明 |
|---|---|---|---|
| running | complete_run(retain=True) | stop() | 现状不变 |
| waiting_for_user | complete_run(retain=True)（**本次修复**） | stop() | 用户接管中：租约交还、浏览器会话保留（不得关闭用户正在操作的窗口） |
| paused | complete_run 被拒（既有契约不变）→ L2 兜底 stop(cancel_owner=False) | stop() | 回合结束时用户仍按着暂停：视为停止并交还租约，run 显示"已停止" |
| provider_safety_required | 不终结、保持活动 | 不终结 | 设计 11.5：等用户显式停止，UI 只给停止 |
| starting/completing/stopping/failed | 兜底 stop(cancel_owner=False) | 同 | L2 保证收敛 |

## 八、第二轮修正（2026-10-01 独立审查后）

第一轮实现通过全部回归后，独立审查（只读）发现两处问题，均已修正：

| 序 | 问题 | 判定 | 修正 |
| --- | --- | --- | --- |
| 1 | 接管态收尾特判 `retain_browser_session=False`，会走 `backend.close()` | **真回归**：外部 Edge/Chrome 上会关掉用户正在手动操作的浏览器窗口（接管场景正在用该窗口） | `core/llm.py` 撤销特判，`completed` 统一 `retain=True`；用例改为断言 `retain=True`、`backend.close_count == 0` |
| 2 | 兜底仅捕获 `ComputerControlError`，`RuntimeError` 等非领域异常会逃逸出回合 `finally` | 缺口：既丢兜底释放，又打断回合收尾 | `except` 放宽为 `Exception`（warning 记录异常类型），非领域异常同样走兜底 stop；新增 `test_turn_end_finalize_fallback_survives_non_domain_error` |

审查同时确认（无需改动）：`cancel_owner=False` 只作用于收尾兜底（其他调用方走默认 `True`）；`provider_safety_required` 的"既不 complete 也不 stop"语义未被兜底破坏；`stop` 的 `stopping` 幂等不会让 run 永久停在 `stopping`（`stopping` 只在 `stop` 锁内设置，该清理链末尾必然 `_finalize_locked`）；前端只改原因行、未放开"恢复"按钮。
